## 一、問題描述

### 根因分類
**類型**：現有機制未完整擴展至關鍵 Agent（LT-05）

### 問題陳述
系統中已存在「動態範疇機制」
（Dynamic Scope Mechanism），
目前僅實作於 `lead.md` 與 `planner.md`，
但尚未擴展至 `architect.md`。

#### 動態範疇機制定義
```
動態範疇機制：
Agent 在接收任務時，
能夠根據任務的實際內容
動態判斷「本次任務的工作範疇邊界」，
而非套用固定的預設範疇。

已實作位置：
- lead.md：協調範疇依任務類型動態調整
- planner.md：Sprint 範疇依需求複雜度動態調整

缺失位置：
- architect.md：設計範疇固定，
  無法根據任務規模動態調整設計深度
```

#### 具體問題
```
現況（architect.md 固定範疇）：
@Architect 接收任何設計任務時，
均套用相同深度的設計流程：
需求分析 → 技術選型 → 規格輸出 → 審查

問題場景一（小型任務過度設計）：
任務：「調整一個函式的回傳格式」
現況：@Architect 仍執行完整設計流程，
      輸出完整技術規格文件
影響：設計工作量遠超任務實際需要，
      浪費執行資源

問題場景二（大型任務設計不足）：
任務：「新增 Telegram Mini App 完整策略管理模組」
現況：@Architect 使用與小任務相同的設計深度，
      可能遺漏跨模組整合設計
影響：設計產出不足以支撐 @Backend / @Frontend
      的實作需求，導致後續複審退回

問題場景三（範疇邊界不清）：
@Architect 無法明確判斷
「這個設計任務應該輸出什麼層級的規格文件」，
導致與 @Lead 對設計產出的預期不一致。
```

### 問題影響層級
- 影響範圍：@Architect 每次執行設計任務
- 風險分類：設計效率與品質一致性
  （過度設計浪費資源，
   設計不足導致實作失敗，
   兩個方向均有影響）
- 風險等級：🟢 低風險（P3）
  （觸發時機：MT-03 完成後，
   架構師任務量增加時）

## 二、根因分析

### 直接根因
`architect.md` 設計時採用「通用設計流程」，
未依任務規模區分設計深度。
動態範疇機制在 `lead.md` 和 `planner.md`
已被驗證有效，但尚未移植至 `architect.md`。

### 系統根因
系統中的動態範疇機制缺乏統一的
「機制移植規範」，
導致相同機制在不同 Agent 中的實作
各自獨立、缺乏一致性。
PROPOSAL-003（RULES_DESIGN_GUIDE）
建立後應將動態範疇機制
列為標準設計模式供各 Agent 參照。

### 前置依賴
- PROPOSAL-009（architect.md 數值化終止升級）：
  複雜度量化門檻已定義，
  本提案的任務規模分級可直接引用。
- PROPOSAL-011（architect.md 業務脈絡錨點）：
  功能域定義已建立，
  本提案的範疇判斷可引用功能域分類。

## 三、提案內容

### 修改項目：architect.md 動態範疇機制

```markdown
// 修改位置：architect.md 任務接收章節（新增）

## 動態範疇機制

@Architect 接收設計任務後，
在開始設計前必須先執行範疇評估，
依任務規模選擇對應的設計深度。

***

### 任務規模分級

#### 規模判定標準

| 規模 | 判定條件（滿足任一） | 設計深度 |
|------|-------------------|---------|
| S（小型）| 僅涉及單一函式或單一 API 端點修改 | 輕量設計 |
|         | 不新增模組或跨模組依賴 | |
|         | 預估 @Backend 實作時間 ≤ 30 分鐘 | |
| M（中型）| 涉及單一功能模組新增或重構 | 標準設計 |
|         | 新增 1~2 個 API 端點 | |
|         | 涉及 1~2 個現有模組的介面調整 | |
| L（大型）| 涉及跨模組整合（≥ 3 個模組）| 完整設計 |
|         | 新增 ≥ 3 個 API 端點 | |
|         | 引入新的系統層級資料結構 | |
|         | 或觸發 PROPOSAL-009 複雜度門檻 | |

***

### 各規模設計深度定義

#### S 輕量設計
```
適用：單一函式 / 單一端點的小幅修改

必要產出：
- [ ] 修改說明（1~3 句話描述變更內容）
- [ ] 輸入 / 輸出格式定義（如有變更）
- [ ] 影響範圍確認（確認無跨模組影響）

不需要：
- 完整技術規格文件
- 架構圖
- 效能評估

回報格式：
【@Architect 輕量設計】✅
規模評估：S
修改說明：{1~3 句話}
影響範圍：{無跨模組影響 / 具體說明}
```

#### M 標準設計
```
適用：單一功能模組的新增或重構

必要產出：
- [ ] 功能需求摘要（來自 @Planner Ticket）
- [ ] 技術選型說明（為何選擇此實作方式）
- [ ] API / 函式介面定義
      （端點路徑 / 參數 / 回傳格式）
- [ ] 資料結構定義（如有新增或變更）
- [ ] 錯誤處理策略
- [ ] 影響模組清單

不需要：
- 完整系統架構圖（非架構性變更）
- 效能壓測規格

回報格式：
【@Architect 標準設計】✅
規模評估：M
功能模組：{模組名稱}
介面定義：{API / 函式清單}
資料結構：{新增 / 變更說明或「無」}
影響模組：{列表}
```

#### L 完整設計
```
適用：跨模組整合或系統層級變更

必要產出：
- [ ] 功能需求完整描述
- [ ] 架構決策說明（含替代方案比較）
- [ ] 完整 API 規格（所有新增端點）
- [ ] 資料結構與 Schema 定義
- [ ] 模組依賴關係圖（文字描述或 ASCII 圖）
- [ ] 錯誤處理與降級策略
- [ ] 效能考量（Oracle VM 限制下的可行性）
- [ ] 實作拆分建議（可拆為幾個 Sprint Ticket）

回報格式：
【@Architect 完整設計】✅ / 🟡
規模評估：L
架構決策：{核心決策摘要}
API 規格：{端點數量} 個端點（詳見規格文件）
實作拆分：建議拆為 {n} 個 Ticket
需 User 確認：{是 / 否，原因}
```

***

### 範疇升級機制

設計過程中發現實際規模超過初始評估時，
@Architect 必須執行範疇升級：

```
觸發條件：
設計進行中發現以下任一情況：
① 原評估為 S，但發現有跨模組影響
② 原評估為 M，但發現需要架構性決策
③ 任何規模下，發現觸發 PROPOSAL-009
   複雜度或技術風險門檻

升級動作：
1. 暫停當前設計
2. 向 @Lead 回報範疇升級：
   【@Architect 範疇升級通知】🟡
   原評估規模：{S/M}
   實際規模：{M/L}
   升級原因：{具體描述}
   建議處理：{繼續完整設計 / 拆分任務}
3. 等待 @Lead 確認後繼續
```

***

### 範疇判定輸出要求

@Architect 每次接收任務後，
必須在開始設計前輸出範疇評估：

```
【@Architect 範疇評估】
任務：{任務描述}
規模判定：S / M / L
判定依據：{觸發的判定條件}
設計深度：輕量 / 標準 / 完整
預估產出：{必要產出清單}
```

禁止：
跳過範疇評估直接輸出設計結果。
範疇評估是 @Architect 任務的第一個強制步驟。
```

## 七、備註

- 本提案中 S/M/L 三個規模的設計深度定義
  是最具實用價值的產出：
  現有系統大多數任務屬於 S 或 M 規模，
  輕量設計與標準設計的明確定義
  能夠顯著減少 @Architect 的設計開銷，
  讓設計工作量與任務規模真正對稱。

- L 規模完整設計中的
  「實作拆分建議」條目
  是 @Architect 與 @Planner 協作的介面：
  @Architect 建議拆分方式，
  @Planner 在下次 Sprint 規劃時採用，
  形成設計層到規劃層的自然交接。

- 範疇評估強制輸出
  （【@Architect 範疇評估】）
  對齊 PROPOSAL-017 的通知格式設計，
  @Lead 可透過標頭快速識別
  @Architect 的設計前準備狀態。

- 本提案新增約 +280 tokens，
  `architect.md` 為非 AlwaysOn 文件，
  Token 預算寬鬆。
  三個設計深度定義的詳細描述
  優先於 Token 精簡，
  因為設計深度定義需要足夠的精確性
  才能被 LLM 可靠執行。
