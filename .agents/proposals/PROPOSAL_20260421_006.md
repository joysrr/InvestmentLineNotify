## 一、問題描述

### 根因分類
**類型**：關鍵流程缺乏量化定義（QW-05）

### 問題陳述
`retro.md` 定義了 @Retro 的審計週期與任務觸發條件，
但「任務週期」的定義採用定性描述（如「定期」、「適時」），
缺乏可量化的觸發標準。

#### 具體問題條文
```
現況（定性描述）：
「@Retro 應定期執行靜態規則審計」
「適時提交改善提案」
「在系統發生重大變更後進行審查」

問題：
「定期」未定義為幾個 Sprint / 幾次對話 / 幾天
「適時」無法被 LLM 或 @Lead 客觀判斷
「重大變更」缺乏明確的量化門檻定義
→ 導致 @Retro 的觸發時機完全依賴主觀判斷，
  可能出現「從未觸發」或「過度頻繁觸發」兩種極端
```

### 問題影響層級
- 影響範圍：@Retro 每次執行週期判斷
- 風險分類：流程可預測性（@Retro 為品質保障機制，
  若觸發不穩定，整個 Rules 品質維護體系的可靠性下降）
- 風險等級：🟡 中風險

---

## 二、根因分析

### 直接根因
`retro.md` 初版設計時
預設 @Retro 由 User 手動觸發，
因此未建立自動觸發的量化標準。

隨著系統規模擴大（19 份 Rules + 提案體系），
手動觸發的可靠性不足，
需要明確的量化觸發條件作為補充。

### 系統根因
缺乏「Agent 週期定義規範」，
各 Agent 的週期性任務（@Retro 審計、
@Assistant 巡邏）採用不同定義標準，
造成系統層級的週期管理不一致。

## 三、提案內容

### 修改項目一：定期審計週期量化

```markdown
// 修改位置：retro.md 觸發條件章節

// 修改前
@Retro 應定期執行靜態規則審計，
適時提交改善提案。

// 修改後
@Retro 靜態規則審計觸發條件（滿足任一即觸發）：

條件一（時間週期）：
距上次完整審計已超過 10 個工作對話
（工作對話定義：包含任務派發或執行的對話，
 純聊天 / 確認對話不計入）

條件二（提案累積量）：
已執行提案累積 ≥ 5 份，
且本次提案執行後未進行增量審計

條件三（手動觸發）：
@Lead 或 User 明確發出審計指令
（關鍵字：「@Retro 審計」、「規則審查」）

條件四（重大變更觸發）：
以下任一情況發生後，下次對話自動觸發：
- 新增 Rules 文件 ≥ 1 份
- system-prompt.md 有實質性修改
- 任何 Rules 文件 Token 增加 ≥ 20%
```

### 修改項目二：「重大變更」量化定義

```markdown
// 修改位置：retro.md 重大變更定義章節（新增）

## 重大變更量化定義

以下任一情況視為「重大變更」，
觸發 @Retro 增量審計：

| 變更類型 | 量化門檻 |
|---------|---------|
| Rules 文件新增 | ≥ 1 份新文件 |
| 單份 Rules Token 增加 | ≥ 20%（相較上次審計） |
| 系統業務功能新增 | 任何新增核心功能 |
| Agent 角色定義變更 | 任何 Persona 或邊界修改 |
| HITL 機制修改 | 任何終止條件或升級條件變更 |

增量審計範圍：
僅針對發生變更的 Rules 文件
及其直接相關的 Rules（上下游 Agent）
```

### 修改項目三：「適時」替換為明確動作

```markdown
// 修改位置：retro.md 提案提交時機章節

// 修改前
識別改善項目後，適時提交改善提案。

// 修改後
識別改善項目後，依以下規則提交提案：

即時提交（當次審計完成前）：
- P0 項目：必須在本次審計輸出中包含完整提案

批次提交（下次對話開始前）：
- P1 項目：審計完成後，@Lead 確認後本次對話提交
- P2 / P3 項目：累積後由 @Lead 統一安排提案輸出

禁止：P0 / P1 項目以「待辦」方式記錄而不提交提案。
```
