## 一、問題描述

### 根因分類
**類型**：任務完成條件缺乏自評機制（MT-04）

### 問題陳述
`backend.md`、`frontend.md`、`qa.md` 三份 Rules
均定義了任務完成條件（DoD，Definition of Done），
但缺乏「Agent 在回報完成前的強制自評步驟」。

#### 具體問題
```
現況：
@Backend / @Frontend / @QA 完成任務後
直接向 @Lead 回報「任務完成」，
未被要求在回報前執行自評 Checklist。

影響場景一：
@Backend 完成實作後直接回報，
@Reviewer 審查時發現遺漏錯誤處理，
需要打回重工——自評機制可在回報前攔截。

影響場景二：
@Frontend 完成 UI 實作後回報，
@QA 測試時發現 Telegram Mini App
相容性未驗證——自評機制可作為第一道品質把關。

影響場景三：
@QA 完成測試後回報通過，
但未覆蓋 P0 必測項目
（PROPOSAL-011 定義）——
自評機制可強制確認必測覆蓋率。
```

### 問題影響層級
- 影響範圍：@Backend / @Frontend / @QA
  每次回報任務完成時
- 風險分類：任務品質可靠性
  （缺少自評導致品質把關責任
   完全落在 @Reviewer 和 @QA 身上，
   形成單點依賴）
- 風險等級：🟡 中風險

---

## 二、根因分析

### 直接根因
三份 Rules 的 DoD 設計為「完成條件清單」，
但未要求 Agent 在回報前主動對照清單自評，
清單形同虛設。

### 系統根因
系統設計假設 @Reviewer 和 @QA
能攔截所有品質問題，
但未在執行層 Agent（@Backend / @Frontend）
建立「第一道自我品質把關」機制。
DoD 自評是在問題進入審查流程前的最低成本攔截點。

## 三、提案內容

### 統一 DoD 自評框架

以下為三份 Rules 共用的自評觸發機制：

```markdown
// DoD 自評標準流程（Standard DoD Self-Review）

觸發時機：任務執行完成，準備向 @Lead 回報前
執行方式：對照本 Rules 的 DoD Checklist 逐項確認
輸出格式：回報訊息中必須包含自評結果摘要
禁止：未完成自評直接回報「任務完成」
```

### backend.md 修改項目

```markdown
// 修改位置：backend.md 任務完成條件章節末尾新增

## DoD 自評機制

@Backend 回報任務完成前，
必須執行以下自評 Checklist：

### 實作自評 Checklist
- [ ] 所有新增函式有對應的錯誤處理（try/catch）
- [ ] 關鍵業務路徑覆蓋
      （對照 PROPOSAL-007 關鍵路徑 Checklist）
- [ ] 無 require() / 絕對路徑 / 硬寫金鑰
- [ ] 資料異動超過 PROPOSAL-009 門檻者
      已獲得 @Lead 授權記錄
- [ ] File-based 寫入有防重複寫入保護
- [ ] 新增套件已確認無安全性已知漏洞

### 回報格式要求
回報 @Lead 時必須包含：
```
【@Backend DoD 自評】
任務：{任務描述}
自評結果：✅ 全數通過 / ⚠️ {n} 項需說明
待說明項目：{具體描述或「無」}
```

禁止：
自評有未通過項目時，
不得以「待後續修正」方式直接回報完成。
未通過項目必須修正後重新自評，
或向 @Lead 說明豁免原因並獲得確認。
```

### frontend.md 修改項目

```markdown
// 修改位置：frontend.md 任務完成條件章節末尾新增

## DoD 自評機制

@Frontend 回報任務完成前，
必須執行以下自評 Checklist：

### 實作自評 Checklist
- [ ] 所有 UI 元件使用 Telegram 主題變數
      （var(--tg-theme-*)）
- [ ] 無直接呼叫後端 API
      （所有通訊透過 Telegram WebApp SDK）
- [ ] 視窗尺寸適配確認
      （非全螢幕、內嵌視窗相容）
- [ ] 互動操作有 Loading 狀態與錯誤提示
- [ ] 無引入需額外安裝的原生套件
- [ ] strategyWeight 顯示值與後端資料來源一致

### 回報格式要求
回報 @Lead 時必須包含：
```
【@Frontend DoD 自評】
任務：{任務描述}
自評結果：✅ 全數通過 / ⚠️ {n} 項需說明
待說明項目：{具體描述或「無」}
```

禁止：
未在 Telegram WebApp 環境（或模擬環境）
確認基本渲染正常前回報任務完成。
```

### qa.md 修改項目

```markdown
// 修改位置：qa.md 任務完成條件章節末尾新增

## DoD 自評機制

@QA 回報測試完成前，
必須執行以下自評 Checklist：

### 測試覆蓋自評 Checklist
- [ ] P0 必測項目全數執行
      （對照 PROPOSAL-011 qa.md 必測清單）
- [ ] 本次 Sprint 涉及的功能域必測項目已覆蓋
- [ ] 錯誤路徑測試至少執行 1 個情境
- [ ] 測試結果有明確的通過 / 失敗紀錄
      （非「應該沒問題」等推測性描述）
- [ ] 失敗項目已回報 @Lead 並等待修正確認

### 回報格式要求
回報 @Lead 時必須包含：
```
【@QA DoD 自評】
測試範圍：{Sprint Ticket 列表}
P0 必測覆蓋：✅ 全數 / ⚠️ 缺少 {項目}
測試結果：通過 {n} 項 / 失敗 {n} 項
失敗項目：{具體描述或「無」}
```

禁止：
P0 必測項目有任何未執行時，
不得回報測試完成。
P0 未覆蓋視為 @QA 任務未完成，
必須補測後重新回報。
```

## 七、備註

- 本提案與 PROPOSAL-011（qa.md 必測清單）
  存在強依賴關係：
  qa.md DoD 自評的 P0 必測項目
  引用 PROPOSAL-011 定義的清單，
  建議執行順序：PROPOSAL-011 先執行，
  本提案作為配套機制後執行。
- 三份 Rules 的回報格式採用一致的
  「【@{Agent} DoD 自評】」標頭，
  方便 @Lead 在對話中快速識別自評結果。
- 本提案為 PROPOSAL-009（數值化終止升級）
  的互補機制：
  PROPOSAL-009 定義「何時必須升級」，
  本提案定義「回報前必須自評什麼」，
  兩者共同降低任務回報的品質風險。
- 三份文件合計新增約 +250 tokens，
  均為非 AlwaysOn 文件，Token 預算寬鬆。
