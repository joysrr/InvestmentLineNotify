## 一、問題描述

### 根因分類

**類型**：提案採納與執行之間缺乏「整合性預檢」機制，導致多提案並存時產生隱性衝突

### 問題陳述

於 2026-04-22 整合性分析中發現：當 `active/` OPEN 提案累積多份（本次 4 份）時，若 User 直接下達採納指令，`@Lead` 會依序執行，但執行過程中可能出現以下問題：

1. **跨提案衝突**：提案 A 改動檔案 X，提案 B 也改動檔案 X 的鄰近章節，依序執行時可能互相覆寫
2. **語意回退**：新提案推翻舊提案設計意圖，但無明文繼承關係
3. **Token 預算累積超標**：單份提案 Token 增量看似可接受，多份疊加後突破 `TOKEN_ONDEMAND_LIMIT`
4. **文件同步缺失**：多提案執行後，`docs/agents-overview.md` 等派生視圖未同步更新
5. **執行順序依賴不明**：提案間有隱性順序依賴（例：001 需 002 先執行），但 User 不知情

### 具體觀察（本次分析事件）

本次 User 要求分析 002→003→001→004 時，手動派遣子 Agent 進行整合性分析，識別出 8 項風險（3 高 + 5 中），若未執行此分析直接採納，預估：

- 🔴 `assistant.md` Token 爆量至 295%（系統性阻斷）
- 🔴 PROPOSAL-011 被隱性推翻（歷史設計資產失落）
- 🟡 `lead.md` 膨脹回退 PROPOSAL-015 精簡目標
- 🟡 WORKSPACE 缺失時系統凍結無降級路徑
- ... 等

此分析為**臨時人工發起**，無制度化機制，若 User 未主動要求，`@Lead` 將直接依採納指令執行，風險將實際發生。

### 問題影響層級

- **系統性風險**：🔴 高（本次若非 User 明確要求分析，4 提案直接採納將導致 Token 爆量）
- **制度性缺口**：🔴 高（無正式機制強制執行整合性分析）
- **重現機率**：🔴 高（未來提案累積到多份時必然再發生）
- 綜合風險等級：🔴 高（制度性預防缺失）

## 二、根因分析

| 根因層級 | 代碼   | 分析說明                                                                                                            |
| -------- | ------ | ------------------------------------------------------------------------------------------------------------------- |
| 系統架構 | `ARCH` | 提案生命週期從 OPEN 跳至 IN_PROGRESS 之間無「預檢關卡」；`@Lead` 收到 User 採納指令後直接執行，未觸發任何整合性驗證 |
| 需求層   | `REQ`  | 系統初期提案數少（每日 1~2 份），整合問題不明顯；進入 2026-04-22 單日 4 份提案後暴露制度缺口                        |

### 直接根因

`retro.md §提案生命週期` 的狀態轉移定義為：

```
OPEN → (User 採納) → IN_PROGRESS → (@Lead 執行完成) → DONE
```

中間**無預檢節點**。`@Lead` 依 `lead.md §s10 行為準則`「採納提案後的 `.agents/` 文件更新」直接執行，速度優先於品質檢驗。

### 系統根因

**提案粒度規則**（`retro.md` + `agents-overview §6.3`）要求「每份提案只能修改一條規則 / 一個 Agent」，此原則在**單一提案層級**運作良好，但**跨提案層級**無對應的品質守門機制。當多份提案並存時：

- 單份提案符合粒度規則 ✅
- 但多份提案合併執行可能觸發衝突 ⚠️

系統缺少「**提案組合驗證**」（Proposal Combination Validation）層級的規範。

# Task: Proposal Integration Analysis (提案整合性分析)

> 當 User 於 OPEN 提案 ≥ 2 份時下達採納指令，`@Lead` 執行本 task 前必須先詢問 User 是否執行本分析。
> 分析流程依以下步驟執行，對應模板位於 `.agents/skills/templates/proposal-integration-analysis-template.md`。

## 觸發時機

- **強制觸發**：User 下達「採納提案 PROPOSAL_XXX」指令時，`active/` 中 OPEN 提案 ≥ 2 份
- **建議觸發**：`active/` OPEN ≥ 3 份時，`@Lead` 主動提醒 User 執行分析
- **跳過條件**：User 明確表示「已審閱，直接採納」（`@Lead` 記錄此決定於 `PENDING_ACTIONS.md` 豁免區塊）

## 分析流程（5 階段）

### Stage 1：範圍界定

- 列出本次 User 指令涉及的採納提案清單
- 列出所有其他 active/ 中 OPEN 提案（是否一併納入分析？）
- 確認分析範圍（單純本次採納 vs 全部 OPEN 池）

### Stage 2：文件依賴盤點

- 掃描每份提案的「預計影響範圍」章節
- 建立「檔案 × 提案」矩陣（列出哪些檔案被哪些提案同時修改）
- 標記高風險檔案（被 ≥ 2 份提案修改）

### Stage 3：並行衝突分析（派遣子 Agent）

- 對每個高風險檔案，派遣獨立 Explore 子 Agent 執行深度檢查
- 子 Agent 依 `skills/templates/proposal-integration-analysis-template.md §子 Agent 提示詞模板` 執行
- 子 Agent 回報 5 項檢查結果：
  1. 章節插入位置是否碰撞
  2. 語意設計是否衝突
  3. 執行順序敏感性
  4. Token 預算累積影響
  5. 與既有 DONE 提案的意圖回退風險

### Stage 4：風險彙整

- 整合所有子 Agent 回報
- 按嚴重度分類：🔴 高 / 🟡 中 / 🟢 低
- 標記每項風險的處理建議：
  - 修訂現有 OPEN 提案內容
  - 建立新補強提案
  - 接受風險繼續採納

### Stage 5：報告輸出

- 依 `skills/templates/proposal-integration-analysis-template.md §報告模板` 產出分析報告
- 於對話中呈現給 User
- 等待 User 決策（修訂 / 新增提案 / 繼續採納 / 暫緩）

## DoD 自評（`@Lead` 執行本 task 前確認）

- [ ] 已列出本次採納範圍與全 OPEN 提案清單
- [ ] 已建立「檔案 × 提案」矩陣
- [ ] 對所有高風險檔案派遣了獨立子 Agent
- [ ] 所有子 Agent 已回報並完成風險彙整
- [ ] 報告依標準模板產出
- [ ] User 已收到報告並做出決策

## 禁止行為

- **絕對禁止** 在 OPEN ≥ 2 份時直接執行採納，未詢問 User 是否做整合性分析
- **絕對禁止** 子 Agent 回報結果未彙整即向 User 產報告
- **絕對禁止** 以「時間緊迫」為由跳過分析（如需緊急，使用 Hotfix 通道而非本提案採納流程）
