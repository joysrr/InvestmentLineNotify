## 一、問題描述

### 根因分類
**類型**：系統性技術債根源（設計規範缺失）

### 問題陳述
PROPOSAL-001（模板外部化）與 PROPOSAL-002
（frontend.md 重構）均指向同一個系統根因：

> 整個 `.agents/` 目錄缺乏「新增 Rules 前置設計規範」，
> 各 Rules 的設計品質完全依賴設計者的個人判斷，
> 無法在設計階段攔截已知的高頻問題。

### 已知高頻問題（審計報告識別）
| 問題類型 | 受影響 Rules 數 | 發生概率 |
|---------|--------------|---------|
| 模板嵌入 | 6 / 11 | 極高 |
| HITL 觸發點不足 | 4 / 11 | 高 |
| 業務脈絡錨定不足 | 6 / 11 | 高 |
| 數值化終止條件缺失 | 5 / 11 | 高 |
| Token 超標（> 1,000）| 7 / 11 | 高 |

### 問題影響
若不建立設計規範，未來新增 Rules
（如 `devops.md`、`database.md`、`security.md`）
將以極高概率重複以上五類問題，
技術債持續累積，系統審計分數長期停滯於 B+ 以下。

## 二、根因分析

### 直接根因
`.agents/` 目錄目前只有 `rules/` 和 `skills/` 子目錄，
缺少系統層級的設計指引文件。
現有 Rules 的設計者在建立文件時沒有可參照的標準，
只能參考其他 Rules 的現有設計——
而現有 Rules 本身存在的設計缺陷，
就這樣透過「參考現有設計」的方式代代相傳。

### 系統根因
整個 Multi-Agent 系統具備自我執行（@Lead）、
自我保護（@Assistant）、自我審查（@Reviewer）、
自我進化（@Retro）的能力，
但缺少「自我規範設計標準」的機制——
每次新增 Rules 時，系統無法自動驗證
新 Rules 是否符合最低設計品質要求。

### 防重犯閉環分析
```
現況（缺口）：
設計者新增 Rules → 無設計規範參照 → 重複犯相同問題

目標（閉環）：
設計者新增 Rules
→ 參照 RULES_DESIGN_GUIDE.md
→ 依前置審查 Checklist 自我驗證
→ @Retro 在下次 Retro 時確認符合規範
```

## 一、Rules 標準結構

每份 Rules 必須依以下順序包含六個章節：

```
1. 任務目標（含業務脈絡三層次）
2. 核心工作流程（含 Agent 呼叫關係）
3. 產出物規範（含格式定義與 DoD 自評）
4. 禁止行為清單（含零容忍條款）
5. HITL 觸發條件（含數值化終止條件）
6. @Assistant 自動化兜底（或等效機制）
```

章節順序固定，不可省略任何章節。
AlwaysOn 文件（system-prompt.md）豁免，
以精簡為最高原則。

***

## 二、Token 預算規範

### 硬性上限
| 文件類型 | Token 上限 | 超標處理方式 |
|---------|-----------|------------|
| AlwaysOn 文件 | 500 tokens | 強制精簡，無豁免 |
| 按需載入 Rules | 1,000 tokens | 模板外部化或結構精簡 |
| Skill 文件 | 無上限 | 依實際需求 |

### Token 估算方式
中英混合文件：位元組數 × 0.6 ÷ 4 ≈ Token 數
純中文文件：字數 × 1.5 ≈ Token 數
純英文文件：字數 ÷ 0.75 ≈ Token 數

### 超標時的精簡優先順序
```
Step 1：模板外部化（移至 .agents/skills/）
Step 2：DoD 條目合併（同語意合為一條）
Step 3：流程說明壓縮（保留結構，精簡說明文字）
Step 4：重複語意消除（相同意思只保留一處）
```

## 三、模板外部化強制規定

### 規定
所有產出物模板（報告格式、User Story 格式、
提案格式、Checklist 格式）一律存放於
`.agents/skills/` 目錄。

Rules 主文件只保留參照路徑，
**禁止在 Rules 主文件內嵌入任何模板**。

| 模板類型 | 路徑 |
|---------|------|
| User Story | .agents/skills/user-story-template.md |
| Draft Features | .agents/skills/draft-features-template.md |
| TEST_SPEC | .agents/skills/test-spec-template.md |
| TEST_REPORT | .agents/skills/test-report-template.md |

新增模板時，先確認此索引是否已有對應文件，
避免重複建立。

## 四、HITL 最低設計要求

### 最低標準（Level 2）
新增任何 Rules 必須達到以下最低 HITL 標準：

```
✅ 顯式觸發點 ≥ 4 個
✅ 數值化終止條件 ≥ 1 個
✅ 觸發後行動明確定義（停止 / 升級 / 等待指示）
```

### 建議標準（Level 3）
```
✅ 顯式觸發點 ≥ 5 個
✅ 數值化終止條件 ≥ 2 個
✅ @Assistant 自動化兜底 ≥ 1 個偵測項目
```

### HITL 成熟度等級定義
| 等級 | 觸發點 | 數值化終止 | 自動化兜底 | 狀態持久化 |
|------|-------|----------|----------|----------|
| Level 1 | ≤ 3 | 無 | 無 | 無 |
| Level 2 | ≥ 4 | ≥ 1 | 可選 | 可選 |
| Level 3 | ≥ 5 | ≥ 2 | ✅ | 可選 |
| Level 4 | ≥ 6 | ≥ 2 | ✅ | ✅ |

新增 Rules 最低達到 Level 2，
建議目標 Level 3。

## 五、業務脈絡三層次規範

任務目標章節必須包含以下三個層次：

### Layer 1：系統定位說明（What）
描述這個 Agent 在 InvestmentLineNotify 中
保護或負責什麼業務價值。

範例：
```
// 優秀範例（backend.md）
「確保後端服務穩定運行、
 量化投資訊號正確且及時推送至 Telegram」

// 不足範例
「負責後端開發任務」
```

### Layer 2：業務觸發場景（When）
列舉在本系統中最常被呼叫的具體業務情境，
而非通用的「當有任務時」。

範例：
```
// 優秀範例（consultant.md）
「strategyWeight 調整、
 通知觸發條件異動、
 Oracle VM Free Tier 資源限制評估」

// 不足範例
「當需要策略建議時」
```

### Layer 3：技術棧錨定（How）
將 Agent 的執行方式與系統技術選型綁定，
防止通用建議與系統約束衝突。

範例：
```
// 優秀範例（backend.md）
「Yahoo Finance API 排程、
 File-based 資料儲存冪等性、
 Node.js ESM 模組系統、
 Oracle Free Tier 記憶體限制」

// 不足範例
「根據最佳實踐進行後端開發」
```

## 六、負面約束設計四原則

### 原則一：零容忍條款必須明文聲明
不只說「禁止」，要說「絕對禁止」或「無豁免空間」，
讓 LLM 無法推測例外情況。

```
// 標準語言
「絕對禁止 X，無例外」
「X 屬於零容忍違規，無豁免空間」
```

### 原則二：跨角色邊界必須正向定義
不只說「不做什麼」，
要說「遇到 X 情境必須呼叫 Y Agent」，
明確合法的替代路徑。

```
// 標準語言
「遇到 X 情境，必須呼叫 @Y，不可自行處理」
```

### 原則三：數值化終止條件優於定性描述
```
// 正確
「退件 ≥ 2 次 → 強制暫停」

// 不足
「多次退件後 → 考慮暫停」
```

### 原則四：業務安全邊界優先於技術規範邊界
InvestmentLineNotify 的業務安全禁區
（靜默失敗、金鑰暴露、策略參數誤改、
 initData 驗證缺失）
應比通用技術規範（代碼格式、命名慣例）
具備更高優先級的禁止條款語言。

## 七、產出物 DoD 自評規範

每份 Rules 的產出物章節必須包含
3~5 條 DoD 自評條目，
供 Agent 在通知 @Lead 前進行自我品質核查。

### DoD 自評格式
```markdown
## 產出物 DoD 自評
在通知 @Lead 前，@[AgentName] 必須確認：
- [ ] [最關鍵的產出物完整性條件]
- [ ] [業務安全條件（若適用）]
- [ ] [外部文件同步條件]
- [ ] [下游 Agent 可消費條件]
```

### DoD 條目設計原則
- 條目數：3~5 條（不超過 8 條）
- 每條必須可被客觀驗證（非「品質良好」等主觀判斷）
- 至少一條涉及業務安全或外部文件同步
- 合併同語意條目（不重複）

## 八、新增 Rules 前置審查 Checklist

在正式提交新增 Rules 的 RULE_UPDATE_PROPOSAL 前，
設計者必須自行完成以下 Checklist：

### 結構完整性
- [ ] 六個標準章節均已包含
- [ ] 章節順序符合規範

### Token 預算
- [ ] Token 估算 ≤ 1,000（按需載入）
- [ ] 所有模板已外部化至 .agents/skills/
- [ ] DoD 條目 ≤ 8 條

### Persona 品質
- [ ] 任務目標包含業務脈絡三層次（What / When / How）
- [ ] 技術棧描述反映 InvestmentLineNotify 實際技術選型

### HITL 設計
- [ ] 顯式觸發點 ≥ 4 個
- [ ] 數值化終止條件 ≥ 1 個
- [ ] 每個觸發點的後續行動已明確定義

### 負面約束
- [ ] 零容忍條款使用「絕對禁止」語言
- [ ] 跨角色邊界有正向定義（遇到 X 呼叫 Y）
- [ ] 業務安全邊界優先於技術規範邊界

### 長程一致性
- [ ] 至少一個外部文件錨定機制
- [ ] 有 @Assistant 自動化兜底或等效機制
