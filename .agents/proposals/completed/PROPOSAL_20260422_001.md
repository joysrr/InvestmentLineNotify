## 一、問題描述

### 根因分類

**類型**：主路由 Agent 認知負擔過重 + 狀態控制權未剝離（單一職責違反 + 狀態持久化缺失）

### 問題陳述

Gemini 評估指出：現行 `.agents/rules/lead.md` 將 `@Lead` 賦予**雙重角色**：

1. **狀態機角色**：記住 10 階段 Workflow 全貌、推論當前階段、預測下一階段、追蹤 Gate Check 條件
2. **資料合併者角色**：動態讀取 `REVIEW_REPORT.md` / `SECURITY_REPORT.md` 等實質內容並合併為「統一退件清單」

此耦合設計造成兩類實際問題：

#### 問題一：Claude Code 長對話情境下的指令遵從度急遽下降

長對話上下文下，LLM 對「10 階段全貌 + 多份報告原文 + Gate Check 條件 + 資源映射表」**同時保持清晰**的能力會退化。實務觀察：

- 在第 15 輪對話後，`@Lead` 開始將「已完成階段」誤判為「待執行階段」
- 在合併 REVIEW_REPORT 與 SECURITY_REPORT 時，偶發遺漏某份報告的 BLOCKER
- 在 Gate Check 輸出時，將下一階段的 Gate 條件誤填為當前階段

#### 問題二：阻礙未來 LangGraph 架構導入

專案 Roadmap 中規劃導入 **LangGraph（狀態機驅動的 Multi-Agent Orchestrator）**。現行 `@Lead` 的雙重角色違反「**控制反轉（Inversion of Control）**」原則：

- **現況**：狀態儲存於 `@Lead` 的上下文推論中（Agent 持有狀態）
- **LangGraph 要求**：狀態儲存於外部 State 物件（Orchestrator 持有狀態，Agent 僅處理當前節點）

若不先剝離 `@Lead` 的狀態職責，導入 LangGraph 時需重寫 `lead.md` 大半規則，遷移成本極高。

#### 問題三：Token 浪費與幻覺風險

`@Lead` 目前實際執行「複製 REVIEW_REPORT 原文 → 與 SECURITY_REPORT 原文合併 → 產出退件清單」的動作，每次消耗 500~1,500 tokens 於純文本重組，屬低價值高風險操作。

### 具體觀察（引用自現行 lead.md）

| 位置                                        | 現行條款                                       | 問題             |
| ------------------------------------------- | ---------------------------------------------- | ---------------- |
| `lead.md §s05` 10 階段派發順序              | 要求 `@Lead` 記憶全部 10 階段流程與 Gate 條件  | 狀態過載         |
| `lead.md §s06` 防線 2 第 3 步               | 「`@Lead` 合併兩報告為『統一退件清單』」       | 資料合併職責耦合 |
| `lead.md §s09` Gate Check 輸出格式          | 格式含「確認條件 + 下一步 + 階段名稱」完整敘述 | 長文本傳遞       |
| `assistant.md §PENDING_ACTIONS.md 標準格式` | 無 `[CURRENT_STAGE]` 狀態錨點                  | 狀態無持久化來源 |

### 問題影響層級

- **Token 消耗**：每次合併動作 ~1,000 tokens ，長 Sprint 累積明顯
- **幻覺風險**：🟡 中（資料合併時遺漏 BLOCKER 機率隨對話長度上升）
- **遷移阻力**：🔴 高（未來 LangGraph 導入的根本性障礙）
- **可維護性**：🟡 中（`@Lead` rule 已達 v1.2，持續擴充會惡化狀態耦合）
- 綜合風險等級：🟡 中偏高（短期非立即危害，中期嚴重）

## 二、根因分析

| 根因層級 | 代碼   | 分析說明                                                                                                                                                                                                              |
| -------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 系統架構 | `ARCH` | 未充分利用 CLI Agent 平台的檔案 I/O 特性作為硬性狀態鎖（State Lock）。將屬於「資料處理」的合併工作交由主路由 Agent 以純文本推論執行，且尚未將「狀態控制權」從 Agent 身上剝離，違反單一職責與無狀態（Stateless）原則。 |
| 需求層   | `REQ`  | 初期設計時未預見長對話情境下的 LLM attention 退化；`@Lead` Gate Check 機制同時承擔「路由 + 資料合併 + 狀態追蹤」三重責任                                                                                              |

### 直接根因

`lead.md` 從 PROPOSAL-015 架構性精簡以來，雖然已刪除大量冗餘敘事，但**仍保留「`@Lead` 持有完整狀態 + 直接處理 Agent 產出物內容」的隱含契約**。此契約在當時為了「降低 Agent 間耦合」而設計（避免 `@Backend` 需讀懂 `@Reviewer` 的退件 markdown），但副作用是將耦合轉移至 `@Lead` 本身。

### 系統根因

缺乏「**狀態控制反轉（Inversion of State Control）**」原則：

- **現況模型**：Agent 的行為規則內嵌狀態管理（`@Lead` 既是執行者又是狀態機）
- **理想模型**：Agent 僅提供「當前節點的處理邏輯」；狀態由外部持久化機制（本提案：`PENDING_ACTIONS.md` + `[CURRENT_STAGE]` 錨點 / 未來：LangGraph State 物件）統籌

此原則一旦確立，`@Lead` 與未來任何 Orchestrator（Claude Code / LangGraph / LangChain Multi-Agent / 自建腳本）都能無縫銜接。

### 與既有設計的承襲關係

本提案**不推翻** PROPOSAL-015（lead.md 架構性精簡）、PROPOSAL-017（通知分級）、PROPOSAL-020（@Security 角色 + 系統參數單點配置）、PROPOSAL-021（Rules 結構標準化）等既有設計，而是**在其基礎上將 `@Lead` 的狀態職責進一步外部化**。

## 三、提案內容

### 3.1 `lead.md` 新增章節（狀態錨點與無狀態路由限制）

於 `lead.md` §s05「核心工作流引擎」**之前**插入新章節，作為強制攔截器，確保後續所有工作流邏輯執行前先通過狀態錨點檢查。

#### 新章節位置與編號

- **位置**：§s04「通知接收與處理優先級」之後、§s05「核心工作流引擎」之前
- **新章節 id**：`s_state_anchor`（避免重編既有 s01~s13 造成 diff 污染）
- **priority**：`critical`
- **immutable**：`true`（零容忍狀態控制反轉原則）

#### 新章節原文（完整寫入 lead.md）

```markdown
<section id="s_state_anchor" priority="critical" immutable="true">
## 狀態錨點與無狀態路由限制 (State Anchor & Stateless Routing)

為了在現階段維持工作流的極致穩定，並為未來的外部狀態機（Orchestrator，例：LangGraph）打下基礎，`@Lead` 在執行任務派發時，**絕對必須**遵守以下「無狀態」限制：

### 1. 強制狀態讀取（State-Driven）

`@Lead` 每次啟動對話或派發任務前，**首要動作必須是讀取** `PENDING_ACTIONS.md` 中的 `[CURRENT_STAGE]` 標籤。

- `@Lead` 將自身視為「無記憶的路由器」，僅需關注「當前階段的下一步是什麼」
- **絕對禁止** 在 Prompt 推論或思考過程中去回顧或預測超過 **1 個步驟**以上的流程
- 10 階段 Workflow 表（§s05）作為**查表工具**使用（依 `[CURRENT_STAGE]` 直接 lookup 下一階段），**不得**作為推論記憶

### 2. 禁止文本合併作業（No Content Merging）

當進入階段 6 / 6.5 平行審查或任何跨 Agent 交接時，`@Lead` **絕對禁止** 自行讀取並合併 `REVIEW_REPORT.md`、`SECURITY_REPORT.md` 等實質內容。

- `@Lead` 的唯一判斷職責是：「報告檔案內是否含有 `🔴 BLOCKER` 符號」（grep 級別的掃描，不讀完整內容）
- 若任一報告含 BLOCKER → `@Lead` 僅需回報退件狀態，並將「報告檔案路徑」提供給 `@Backend` / `@Frontend`，由負責實作的 Agent 動態讀取（Artifact-Driven Read）並修復
- **絕對禁止** 在對話中複製貼上 REVIEW_REPORT / SECURITY_REPORT 原文
- **絕對禁止** 自行撰寫「統一退件清單」markdown；該清單由 `@Backend` / `@Frontend` 讀檔後自行整合

### 3. 短指令交接（Short Command Handoff）

跨 Agent 傳遞資訊時，`@Lead` 只傳遞以下三類內容：

1. **專案環境變數路徑**：`PROJECT_CONTEXT` 指向 `workspaces/<active>.md`（依 PROPOSAL-022）
2. **產出物檔案路徑**：`Artifact Paths` 指向具體 `.md` / `.mjs` / `.vue` 檔案路徑
3. **簡短的下一步指令**：不超過 3 行，僅含動詞 + 目標檔案 + 約束

**絕對禁止**：

- 將上一位 Agent 的冗長報告或程式碼片段複製貼上在對話中
- 在交接指令中內嵌業務邏輯推理或分析摘要
- 交接指令超過 5 行純文字（超標視為違反短指令原則）

### 4. 違反處理

以下任一情況視為違反本章節，由 `@Retro` 於審計時識別並提案補強：

- `@Lead` 在單次派發中引用超過 2 個歷史階段的內容（違反「1 步原則」）
- `@Lead` 對話中出現 REVIEW_REPORT / SECURITY_REPORT 原文片段（違反「禁止合併」）
- `@Lead` 單次交接指令超過 5 行純文字（違反「短指令」）

違反累積 ≥ 3 次 → `@Retro` 提案強化 / 觸發 `system-prompt.md §全局緊急阻斷` 條件一（協調失敗）。

### 5. LangGraph 遷移預留

本章節的三項限制設計為**可機器替換**：

| 當前實作               | LangGraph 對應                        |
| ---------------------- | ------------------------------------- |
| 讀取 `[CURRENT_STAGE]` | 讀取 State 物件的 `current_node` 欄位 |
| 產出檔案路徑交接       | State 物件的 `artifacts` list 欄位    |
| 短指令輸出             | LangGraph Node 的 structured output   |

導入 LangGraph 時，本章節可整體替換為「依 Orchestrator State 物件執行路由」單句，其他 Agent rules 不受影響。

<!-- END: 狀態錨點與無狀態路由限制 -->
</section>

### 3.3 `lead.md §s06` 平行審查規則調整

原 §s06「平行審查與衝突仲裁規則」防線 2 第 3 步：

> 3. `@Lead` **合併**兩報告為「統一退件清單」（不分開退件）

**修改為**：

> 3. `@Lead` **輸出**兩報告的檔案路徑清單（不分開退件，不合併內容）：
>
>    ```
>    退件通知 ❌ BLOCKED
>    報告檔案路徑：
>    - REVIEW_REPORT.md
>    - SECURITY_REPORT.md
>    請 @Backend / @Frontend 動態讀取並一次性修正所有 BLOCKER。
>    ```
>
>    `@Backend` / `@Frontend` 收到後使用 Read 工具讀取兩份報告原文，自行整合修復清單，不依賴 `@Lead` 代為合併。

### 3.4 `lead.md §s09` Gate Check 輸出格式調整

原 §s09「Gate Check 輸出格式」：

```
✅ Gate Check 通過：<當前階段> → <下一階段>
確認條件：<對應 Gate 條件一句話>
下一步：呼叫 <@Agent> 執行 <階段名稱>
```

**修改為（符合短指令原則）**：

```
✅ Gate Check ✔ S<當前>→S<下一>
Next: @<Agent> | Artifacts: <paths>
```

其中：

- `S<當前>→S<下一>`：以階段編號表示，省略完整階段名稱
- `@<Agent>`：下一階段執行者
- `<paths>`：本次交接的檔案路徑 list（逗號分隔，不超過 3 個）

### 3.5 與既有規則的衝突處理

#### 衝突一：§s05 10 階段派發順序的「記憶」隱含要求

現行 §s05 要求 `@Lead` 記住 10 階段順序。**本提案不刪除此表**，但於 §s05 開頭新增說明：

```markdown
> **使用方式變更（PROPOSAL_20260422_001）**：以下 10 階段表為**查表工具**，僅在 `@Lead` 讀取 `[CURRENT_STAGE]` 後依當前編號 lookup 下一階段。`@Lead` **不得**在推論中記憶或預測跨 1 階段以上的流程（對齊 §s_state_anchor 第 1 條）。
```

#### 衝突二：§s09 Gate Check 條件表的「完整敘述」與短指令衝突

現行 §s09 的 Gate Check 條件表（詳列每個階段轉移的 Gate 條件）保留作為**查表工具**，但實際輸出時依 §3.4 新格式。於 §s09 表格前新增說明：

```markdown
> **輸出格式變更（PROPOSAL_20260422_001）**：以下條件表為 `@Lead` 內部判斷依據；實際對外輸出依 §3.4 新短指令格式。
```

#### 衝突三：§s04 通知接收與處理優先級的「多通知處理」

現行 §s04 允許 `@Lead` 同時處理多級別通知。本提案要求短指令，故於 §s04 末端新增：

```markdown
> **單次回覆範疇（PROPOSAL_20260422_001）**：即使存在多級別通知，`@Lead` 單次回覆處理**最高級別**並輸出短指令；其餘級別於下一輪對話處理（對齊 §s_state_anchor 第 3 條短指令原則）。
```

## 四、預期效益

### 量化效益

| 維度                            | 改善前                         | 改善後                            |
| ------------------------------- | ------------------------------ | --------------------------------- |
| `@Lead` 單次派發 Token 量       | ~1,500 tokens（含合併報告）    | ~300 tokens（僅路徑 + 短指令）    |
| 合併誤差率（遺漏 BLOCKER）      | 🟡 中（長對話下偶發）          | 🟢 零（不再合併）                 |
| 對話視窗累積負擔                | 隨 Sprint 線性膨脹             | 持平（Artifact 常駐檔案系統）     |
| LangGraph 遷移 lead.md 改動範圍 | 預估 ~60%（狀態邏輯外移）      | 預估 ~5%（僅替換 State 讀取來源） |
| `@Lead` 認知複雜度              | 10 階段 + Gate 條件 + 資源映射 | 僅「讀當前階段 + 查下一步」       |

### 質化效益

- **指令遵從度提升**：`@Lead` 不再需要「記住全流程」，專注於「眼前這一步」，長對話下穩定度顯著提升
- **職責單一化**：`@Lead` 純粹作為路由器；資料處理職責下放至實際處理 Agent（`@Backend` / `@Frontend` 等）
- **審計可追溯性**：`[CURRENT_STAGE]` 狀態錨點留存於 `PENDING_ACTIONS.md`，任何時點皆可回溯工作流實際狀態
- **未來可擴展性**：本次改造為 LangGraph 或任何外部 Orchestrator 的零痛點替換鋪路

### 非效益與取捨（避免過度承諾）

- **`@Backend` / `@Frontend` 稍增讀檔工作**：原本由 `@Lead` 合併產出整合清單，現改為開發 Agent 自行讀取兩份報告；增加 1~2 次 Read 工具呼叫（可忽略）
