## 一、問題描述

### 1.1 現象

目前 `.agents/proposals/` 同時收納兩類**本質不同**的提案：

| 類別 | 修改標的 | 跨專案適用性 | 範例 |
|------|---------|-------------|------|
| **Framework 提案** | `.agents/` 底下規則/技能/技術棧/任務/模板/測試 | ✅ 跨專案通用 | PROPOSAL_021（Rules 結構標準化）、PROPOSAL_022（tech-stacks 純淨分離）|
| **Project 提案** | 專案原始碼 / 業務邏輯 / 策略設定 / 某 workspace 實值填寫 | ❌ 僅該專案適用 | PROPOSAL_20260421_002（frontend.md 重構含 IMN 引用）、PROPOSAL_20260420_002（Policy 模組 Test Coverage）|

目前狀態：**二者混用同一目錄、共用編號空間、共用索引**。

### 1.2 具體污染統計

`grep -l` 偵測 7 份 completed 提案含專案特定關鍵字（InvestmentLineNotify / marginManager / entryScoringPolicy / sellScoringPolicy / Strategy.json / Oracle）：

```

.agents/proposals/completed/PROPOSAL_20260421_002.md   # frontend.md 重構（含 IMN 引用）
.agents/proposals/completed/PROPOSAL_20260421_003.md   # RULES_DESIGN_GUIDE（提及 IMN 情境）
.agents/proposals/completed/PROPOSAL_20260421_011.md   # 業務脈絡錨定（IMN 技術棧）
.agents/proposals/completed/PROPOSAL_20260421_019.md   # Rules 版本控制機制（IMN 歷史）
.agents/proposals/completed/PROPOSAL_20260421_020.md   # @Security 角色（含 IMN 部署參照）

**分類再細評**：
- 7 份中至少 3 份**核心為 framework 結構調整**（002 / 019 / 020）→ 應保留在 framework
- 另 4 份雖為 framework 類但**論證使用 IMN 範例**（003 / 011 / 002 其他引用）→ 保留 framework，但範例部分可考慮淨化
- **真正的純 Project 提案尚未正式納入追蹤**（例：Epic 1 Remediation 策略邏輯調整見於 `docs/TEST_REPORT.md`，但該類內容未以提案形式存在）

### 1.3 衝突與風險

| 問題類型 | 具體風險 | 嚴重度 |
|---------|---------|-------|

## 三、提案內容

### 3.1 Scope 分類定義

提案 **scope** 分為兩大類，互斥不重疊：

| Scope | 修改標的範圍 | 跨專案適用性 | 儲存位置 |
|-------|------------|-------------|---------|
| **framework** | `.agents/` 底下所有檔案（rules/ / skills/ / tech-stacks/ / domains/ / tasks/ / tests/ / proposals/ 本身結構 / workspaces/README.md + default_env.md + WORKSPACE_SCHEMA.yaml / CURRENT_WORKSPACE 機制 / 派生視圖結構）| ✅ 跨專案通用 | `.agents/proposals/` |
| **project** | 專案原始碼（`src/` / `tests/` / `scripts/`）、業務資料（`data/`）、專案文檔（`docs/`）、workspace 實值填寫（`workspaces/<project>.md` 欄位調整、非模板變更）、專案特定配置（`.env` 模板 / `ecosystem.config.cjs` 等）| ❌ 僅該專案適用 | `workspaces/<project>/proposals/` |

**判定原則（硬性規則）**：
1. 若修改標的**唯一** prefix 為 `.agents/`（排除 `.agents/workspaces/<project>.md` 的實值填寫）→ **framework**
2. 若修改標的 prefix 為 `src/` / `data/` / `docs/` / `scripts/` / `tests/` 或含 workspace 實值調整 → **project**
3. 若兩者**同時存在** → **強制拆分為兩份獨立提案**（禁止混合提案）

**例外邊界說明**：
- `.agents/workspaces/<project>.md` 的**欄位實值填寫/調整** → `project` scope（因綁定特定專案）
- `.agents/workspaces/default_env.md` 的模板欄位調整 → `framework` scope
- `.agents/WORKSPACE_SCHEMA.yaml` 結構調整 → `framework` scope

### 3.2 目錄結構改造

```

│       ├── active/

### 3.3 編號規則

| Scope | 編號格式 | 範例 |
|-------|---------|------|
| framework | `PROPOSAL_YYYYMMDD_NNN`（現行不變）| `PROPOSAL_20260422_022` |
| project | `<PROJECT_PREFIX>_PROPOSAL_YYYYMMDD_NNN` | `ILN_PROPOSAL_20260422_001`（InvestmentLineNotify）|

**Project 前綴規則**：
- 使用專案代號的 **3–5 字母大寫縮寫**
- 於 workspace 檔案的 frontmatter 新增 `proposal_prefix` 欄位明確定義（例：InvestmentLineNotify → `ILN`）
- 編號空間依 scope 獨立：framework 與 project 即使同日同序號，因前綴不同不衝突
- 跨專案切換時（切換 `CURRENT_WORKSPACE`），project 提案目錄隨之切換，不會誤讀其他專案的提案

### 3.4 提案 frontmatter 擴充

所有新提案必須於基本資訊區塊新增 **`scope`** 欄位（兩者擇一）：

```markdown
## 基本資訊
- 提案編號：<PROPOSAL_ID>
- scope：`framework` | `project:<project_name>`
- ...其餘既有欄位
```

**scope 值格式**：
- framework：純字串 `framework`
- project：`project:<project_name>`（冒號後為對應 workspace 名稱，例：`project:investmentlinenotify`）

`@Retro` 產出提案時**必須同時產出 scope 欄位**；遺漏視為格式違規，由 `@Auditor` §2.2 偵測。

### 3.5 既有提案回溯分類

## 七、備註

### 意圖繼承聲明（依 PROPOSAL_20260422_006 + 021）

本提案**延伸** PROPOSAL_20260422_002 + 022 意圖，**非推翻**：

- 002：workspaces/ 機制建立（欄位層分離）
- 022：tech-stacks 純淨分離（知識層分離）

### 設計原則總結

1. **二元分層**：scope 僅 framework / project 兩種，避免分類辯論
2. **機械化判定**：RULES_DESIGN_GUIDE §十七.B 明文 3 步流程
3. **強制拆分優於混合**：標的同時跨 scope 時禁止產出混合提案
4. **雙層偵測**：`@Retro` 產出前閘門 + `@Assistant` P-18 事後巡邏 + `@Auditor` §2.2 定期評審
5. **最小擾動**：既有提案僅補填 frontmatter，不移動檔案
6. **搬運語意一致**：與 002 + 022 同一原則（`.agents/` = 純通用資產）
