## 二、問題描述

### 2.1 User 觀察的痛點

> 「實際上運用時發現，各平台會有自己的特性導致不會完全依照 rules 中的規範，這樣不斷地修改好像也沒有什麼幫助」

### 2.2 根因分析（自然語言 Rules 的本質限制）

| 層級                         | 約束機制               | 可靠度                                  |
| ---------------------------- | ---------------------- | --------------------------------------- |
| **Rules（自然語言）**        | 提示性；LLM 自願遵守   | ~85-95%（drift_score 0.957 已接近極限） |
| **Tools（程式碼定義）**      | 結構化 input/output    | ~99%                                    |
| **State Graph（LangGraph）** | deterministic 條件轉移 | 100%                                    |

**邊際效益遞減**：rules 從 0→80% 收益高；80→95% 遞減；**95→100% 必須改用程式碼控制**（不再是 prompt 工程）。

### 2.3 跨平台一致性挑戰

當前 framework 在 Claude Code 與 Antigravity 平台執行時：

- **rules/\*.md 內容相同**（跨平台搬運的 framework 設計達成）
- **但平台特性差異導致行為不一致**
  - Claude Code (Opus 4.7)：精確遵循；但 sub-agent 機制有限
  - Antigravity (Gemini 3)：IDE 整合佳；對非 Google 風格 rules 可能誤解
- **結果**：同一份提案在兩平台執行可能產出不同結果

### 2.4 既有 framework 的 LangGraph friendliness（已具備）

7 個關鍵設計**已對齊 LangGraph 模型**（PROPOSAL_023/024 沉澱）：

| Framework 元素                                       | LangGraph 對應                                 |
| ---------------------------------------------------- | ---------------------------------------------- |
| `ROUTING_TICKET.md` schema (PROPOSAL_023)            | **State schema**（直接對應）                   |
| `PENDING_ACTIONS.md §🎯 [CURRENT_STAGE]`             | **Graph control flow**（state machine cursor） |
| `lead.md §s05` 10 階段派發順序                       | **Sequential edges**                           |
| `force_complex_scenarios` (rule_edit_large/critical) | **Conditional edges** with deterministic check |
| `skills/orchestrator-pattern.md` (ADR-0033)          | **Module 層 LangGraph 設計**（同精神）         |
| `Hub-and-Spoke` (PROPOSAL_026)                       | **Supervisor pattern**（標準 LangGraph 範式）  |
| `13 agents 扁平名冊`                                 | **Parallel nodes**                             |

**結論**：framework 已有 70% 結構就緒；POC 主要工作是**MCP server 包裝 + sampling 整合 + 自我進化機制保留設計**。

### 2.5 協作邏輯分析（User 提問回應）

> 「角色的協作邏輯是固定的先後順序，還是需要根據任務動態切換呢？」

依現有 framework 盤點：**~70% 固定 + ~30% 條件式動態**：

| 類型         | LangGraph 對應                             | Framework 範例                                                      |
| ------------ | ------------------------------------------ | ------------------------------------------------------------------- |
| **70% 固定** | `add_edge("a", "b")`                       | Workflow 10 階段 / Hotfix Step 0 / Audit 5 維度派遣                 |
| **30% 動態** | `add_conditional_edges("lead", router_fn)` | 複雜度評估 / force_complex_scenarios / Prior Art Gate / 6.5 SC 觸發 |

**設計含義**：LangGraph **混合 edge 設計**（static + conditional）；不需要全 deterministic，也不需要全 LLM judgement。

**B.2 LLM factory（雙環境核心）**：

```python
# poc/langgraph-mcp/llm_factory.py
import os
from langchain_core.language_models import BaseChatModel

def get_llm(state, complexity_tier="medium") -> BaseChatModel:
    backend = os.environ.get("LLM_BACKEND", "qwen")

    if backend == "qwen":
        from langchain_openai import ChatOpenAI
        # Qwen API（OpenAI-compatible）
        model_map = {
            "simple": "qwen-turbo",
            "medium": "qwen-plus",
            "complex": "qwen-max",
        }
        return ChatOpenAI(
            base_url=os.environ["QWEN_API_URL"],
            api_key=os.environ["QWEN_API_KEY"],
            model=model_map[complexity_tier],
        )

    elif backend == "gemini":
        from langchain_google_genai import ChatGoogleGenerativeAI
        return ChatGoogleGenerativeAI(
            model="gemini-3-pro" if complexity_tier == "complex" else "gemini-3",
            google_api_key=os.environ["GEMINI_API_KEY"],
        )

    elif backend == "sampling":
        # MCP sampling 模式（Antigravity 反向呼叫其 Gemini）
        from .mcp_sampling_adapter import MCPSamplingChatModel
        return MCPSamplingChatModel(ctx=state.get("mcp_context"))

    else:
        raise ValueError(f"Unknown LLM_BACKEND: {backend}")
```

**B.3 第一個 node 原型**：`@Lead` dispatch node

```python
# poc/langgraph-mcp/nodes/lead.py
def lead_dispatch_node(state: WorkflowState):
    llm = get_llm(state, complexity_tier=state.get("complexity_tier", "medium"))
    rule = read_rule_tool("lead")

    response = llm.invoke([
        SystemMessage(content=rule),
        HumanMessage(content=state["original_request"])
    ])

    dispatch = parse_dispatch_message(response.content)
    write_routing_ticket_tool({**state, **dispatch.dict()})

    return {
        "target_agent": dispatch.target,
        "tier_reason": dispatch.reason,
        "llm_backend": os.environ.get("LLM_BACKEND"),
        "llm_model": llm.model_name if hasattr(llm, 'model_name') else "unknown",
    }
```

### 4.3 HITL Interrupt 機制（保留 User 採納權）

LangGraph 的 `interrupt()` + MCP `elicit` capability 整合：

```python
def proposal_adoption_node(state):
    """User 採納提案 Gate；對齊 PROPOSAL_023+025 §s10"""
    # 暫停等待 User
    user_decision = interrupt({
        "type": "proposal_adoption",
        "proposal_id": state["proposal_id"],
        "title": state["proposal_title"],
        "options": ["採納", "修改", "拒絕"],
        "message": f"採納提案 {state['proposal_id']}？"
    })

    if user_decision == "採納":
        # status: OPEN → IN_PROGRESS
        return {"action": "adopt", "next": "execute_proposal"}
    elif user_decision == "修改":
        return {"action": "revise", "next": "retro_revise"}
    else:
        # status: OPEN → REJECTED
        return {"action": "reject", "next": "archive_rejected"}
```

**4 個必須 HITL interrupt 點**：

| #   | Interrupt 點                    | 對應 framework                  | 觸發條件                                  |
| --- | ------------------------------- | ------------------------------- | ----------------------------------------- |
| 1   | **提案採納 Gate**               | `lead.md §s_pre_adoption_check` | OPEN ≥ 2 份 / User 下「採納提案」指令     |
| 2   | **Prior Art Verification Gate** | `lead.md §s06b`                 | @Architect 第 3 階段完成後                |
| 3   | **strategyWeight 異動 Gate**    | `lead.md §s11`                  | force_complex_scenarios 之 strategyWeight |
| 4   | **Hotfix light 路徑授權**       | `tasks/hotfix-checklist.md`     | hotfix_tier=light + SC 全否（保守確認）   |

**設計鐵律**：以上 4 個 Gate **絕對禁止 LangGraph 自動繞過**；必經 User interrupt 確認。

   LangGraph 過濾 TypedDict 未宣告欄位 → 旗標寫了但 conditional edges 讀不到 → 死循環。
   18 個關鍵欄位（`review_quality_violation` / `prior_art_scan_triggered` 等）必須補上。

2. **Qwen3 reasoning model thinking mode**（hot-fix 3-4）
   不同部署認的參數位置不同（`extra_body.enable_thinking` vs `chat_template_kwargs.enable_thinking`）；
   POC 同時送兩個位置 + max_tokens 16K 才穩定。

3. **regex 必須容忍 markdown 變形**（hot-fix 5）
   LLM 常用 `**KEY**: value` / `KEY: **value**` / 全形冒號 → 嚴格 regex 抓不到。
   通用 pattern：`KEY[\s\*:：\-]+\**\s*\b(value)\b`。

4. **MemorySaver 不可跨進程**（hot-fix 8）
   HITL resume 必須用 `SqliteSaver` 寫入磁碟；CLI 重啟才能讀到中斷狀態。
