## 一、問題描述

### 根因分類

**類型**：系統規模擴展的長期維護機制缺失（LT-03）

### 問題陳述

本次審計共產出 19 份提案（PROPOSAL-001~019），
`.agents/proposals/` 目錄規模已達到
需要主動管理的程度。
`retro.md` 目前缺乏提案目錄的
規模管理與歸檔規範。

#### 具體問題

```
現況：
提案文件累積於 .agents/proposals/ 目錄，
無歸檔機制、無狀態索引、無規模上限定義。

預期問題（提案累積至 30+ 份後）：
問題一：目錄掃描效率下降
  @Lead 或 @Retro 需要掃描大量已完成提案
  才能找到當前 OPEN 狀態提案

問題二：歷史提案干擾當前決策
  大量已執行（DONE）的提案與
  待執行（OPEN）提案混在同一目錄，
  增加判讀負擔

問題三：提案狀態無集中索引
  無法快速獲取「目前有幾份 OPEN / DONE」
  的全局視圖，
  需逐一開啟文件確認狀態

問題四：提案命名規範缺失
  若多位 Agent 同時提案
  或跨審計週期提案，
  編號衝突風險上升
```

### 問題影響層級

- 影響範圍：@Retro 每次審計週期
  - @Lead 每次查詢提案狀態
- 風險分類：長期可維護性
  （當前 19 份尚可管理，
  但隨系統演進累積至 50+ 份後
  將顯著影響效率）
- 風險等級：🟢 低風險（P3）
  （觸發條件：提案累積 ≥ 20 份，
  目前剛達觸發門檻）

## 二、根因分析

### 直接根因

`retro.md` 設計時未預期提案體系
會在短時間內擴展至 19 份規模，
缺乏相應的目錄管理規範。

### 系統根因

提案體系是系統演進的記錄機制，
其本身也需要「元管理」——
管理提案的提案，
但系統設計初期未將此納入考量。

### 修改項目三：提案編號規範

```markdown
// 修改位置：retro.md 提案編號章節（新增）

## 提案編號規範

### 標準編號格式

PROPOSAL-{三位數序號}
範例：PROPOSAL-001、PROPOSAL-019、PROPOSAL-100

### 編號分配規則

1. 序號由 @Retro 在審計輸出時統一分配
2. 跨審計週期的提案序號接續，不重置
   （PROPOSAL-019 之後為 PROPOSAL-020）
3. 已廢棄的提案編號不重用
   （廢棄提案標注 CANCELLED 狀態，
   保留編號佔位）

### 特殊狀態定義

| 狀態        | 說明   | 目錄位置               |
| ----------- | ------ | ---------------------- |
| OPEN        | 待執行 | active/                |
| IN_PROGRESS | 執行中 | active/                |
| DONE        | 已完成 | completed/             |
| CANCELLED   | 已廢棄 | completed/（保留記錄） |
| ARCHIVED    | 已歸檔 | archived/              |
```
