## 一、問題描述

**根因分類**：`ARCH`（tech-stacks 設計初期未落實 Core Soul 純淨原則）

2026-04-22 對齊審計識別 `.agents/tech-stacks/` 與 `.agents/skills/` 共 **24 項污染**，導致：

1. **遷移阻礙**：新專案複製 `tech-stacks/` 後需逐行清洗（約 2~3 小時 / 5 份檔案）
2. **知識無法累積**：技術棧最佳實踐與專案路徑混雜，升級時容易誤傷專案特定內容
3. **跨專案共用受阻**：同份技術棧若服務多專案，每專案都需 fork 一份
4. **設計哲學矛盾**：與 PROPOSAL_002 Core Soul vs Project Context 分離原則不一致

### 核心設計缺口

- **缺乏契約 SSOT**：workspace 欄位無統一 schema，tech-stacks 引用無對齊基準

- **缺乏版本演進機制**：tech-stacks 升級 → workspace schema 同步的路徑未定義

## 二、根因分析

| 根因層級 | 代碼   | 分析說明                                                                                                                               |
| -------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| 系統架構 | `ARCH` | tech-stacks 建立時未區分「通用技術原則」與「專案特定實作路徑」；兩者混雜於同一份檔案，導致跨專案複用時必須逐行清洗                     |
| 需求層   | `REQ`  | 初期聚焦單一專案（InvestmentLineNotify），多專案支援需求未前置；PROPOSAL_002 建立 workspace 機制時僅處理 rules，未同步處理 tech-stacks |

### 直接根因

2026-04-21 之前，所有 `.agents/` 建立時假設單一服務對象；PROPOSAL_002（2026-04-22 採納）將 rules 通用化，但未同步處理 tech-stacks/skills 的污染。

### 系統根因

**缺乏「引用契約」原則**（Reference Contract Principle）：

- **現況**：tech-stacks 直接寫死專案細節 → 遷移靠人工審視
- **理想**：tech-stacks 僅含通用原則 + 指向 workspace 對應欄位 → 遷移靠 Schema 驅動自動化
