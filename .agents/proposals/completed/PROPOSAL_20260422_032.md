## 一、問題描述與根因分析

### 1.1 現象

**發現位置**：`.agents/rules/lead.md §s05` 10 階段派發順序 + 全局工作流定義。

**問題摘要**：系統存在「殺雞用牛刀」的過度設計。所有任務皆需通過完整 10 階段工作流與多重 Agent 審查，導致小規模修改的耗時與 Token 成本過高。

**詳細描述**：

- 當前工作流（`lead.md §s05`）定義 10 階段派發順序（需求→規劃→架構→實作→審查→安全→QA→收斂→進化→監控）
- 即使只是修改一個錯字或按鈕顏色，系統仍會喚醒 `@Planner` / `@Reviewer` / `@Security` 等角色進行全量審查
- 實際觀察：小任務耗時分鐘級 + Token 消耗 25k+ 起，顯著扼殺開發敏捷性
- 過度頻繁的 Agent 交接易讓底層模型產生幻覺與狀態迷失（對齊 PROPOSAL_001 §s_state_anchor 三鐵律之「禁止推論超過 1 步」意圖）

### 1.2 量化影響

| 任務類型          | 當前耗時 | 當前 Token | 實際需要         |
| ----------------- | -------- | ---------- | ---------------- |
| 修正錯字          | 分鐘級   | 25k+       | 10 秒 / 2k       |
| CSS 顏色微調      | 分鐘級   | 25k+       | 10 秒 / 2k       |
| 新增單元測試      | 分鐘級   | 25k+       | 30 秒 / 2k       |
| 新增 API endpoint | 數分鐘   | 30k+       | 2 分鐘 / 10k     |
| 資料庫重構        | 10+ 分鐘 | 50k+       | 符合全量審查成本 |

→ **約 70% 的 Agent 交接對低風險任務為冗餘開銷**。

### 1.3 根因分析

| 根因層級 | 代碼      | 分析說明                                                                                               |
| -------- | --------- | ------------------------------------------------------------------------------------------------------ |
| 系統架構 | `ARCH`    | 缺乏「任務複雜度分級」機制；工作流設計過於僵化，未實作基於風險評估的動態路由（Dynamic Routing Bypass） |
| 設計     | `ARCH`    | `lead.md §s05` 10 階段派發順序視為**全域強制**，無例外機制；僅 Hotfix 通道為唯一例外但限於緊急修復     |
| 流程     | `PROCESS` | 缺少「派發前風險評估閘門」；@Lead 僅依任務描述派發，未量化評估任務影響範圍                             |
| 監測     | `TEST`    | 無「快車道翻車」偵測機制；即使未來有分流，無回退保護                                                   |

### 1.4 意圖繼承聲明（依 PROPOSAL_20260422_006）

- **PROPOSAL_024（模型分層路由）**：共用 `complexity_thresholds` 評估基礎；**非推翻**，為平行擴充（同一評估產出兩個決策維度）
- **PROPOSAL_012（DoD Gate Check Auto-Audit）**：本提案快車道需明定「可跳過 / 強制保留」的 Gate，維持 Gate Check 審計完整性
- **PROPOSAL_001（@Lead 無狀態路由）**：快車道仍遵守短指令交接三鐵律；降級路徑不破壞 stateless-routing-pattern
- **Hotfix Fast Lane（既有）**：本提案的「快車道」與「Hotfix」為**不同語意**（Hotfix 為緊急修復；Fast-Track 為低風險日常），不衝突且可共存

## 二、多車道路由架構設計 (Multi-Lane Routing Architecture)

本提案將 `lead.md §s05` 單一 10 階段工作流，擴充為三條具備不同「阻力與審查層級」的車道。由 `@Lead` 依派發前風險評估（§三 20 指標）決定路由。

### 2.1 🏎️ 快車道 (Fast-Track)

| 項目                | 內容                                                     |
| ------------------- | -------------------------------------------------------- |
| **參與 Agent**      | `@Lead` → 單一實作 Agent（`@Backend` 或 `@Frontend`）    |
| **階段數**          | 3 階段（需求確認 → 實作 → 產出確認）                     |
| **審查**            | 零交叉審查（`@Reviewer` / `@Security` / `@QA` 均不介入） |
| **Gate Check**      | 僅保留「派發前風險評估」+「產出物路徑確認」兩個 Gate     |
| **預估 Token**      | ~2k                                                      |
| **Complexity 對應** | `simple`（對齊 PROPOSAL_024 三層映射）                   |

### 2.2 🚗 標準車道 (Standard-Track)

| 項目                | 內容                                                             |
| ------------------- | ---------------------------------------------------------------- |
| **參與 Agent**      | `@Lead` → `@Planner` → 實作 Agent → `@Reviewer`                  |
| **階段數**          | 5-6 階段（需求 → 規劃 → 實作 → 審查 → 收斂 → 進化）              |
| **審查**            | 單點防呆 `@Reviewer`；`@Security` / `@Consultant` / `@QA` 不介入 |
| **Gate Check**      | 完整保留 DoD Gate Check Auto-Audit（依 PROPOSAL_012）            |
| **預估 Token**      | ~8-12k                                                           |
| **Complexity 對應** | `medium`                                                         |

### 2.3 🚚 重裝車道 (Heavy-Track)

| 項目                | 內容                                                                           |
| ------------------- | ------------------------------------------------------------------------------ |
| **參與 Agent**      | 全量 10 階段（含 `@Consultant` / `@Architect` / `@QA` / `@Security` 平行審查） |
| **階段數**          | 完整 10 階段                                                                   |
| **審查**            | 跨領域戰略審查 + 平行安全稽核 + 嚴格退件迴圈（REVIEW_CYCLE_LIMIT）             |
| **Gate Check**      | 完整 + 強制觸發 @Security SC-01~SC-11 掃描                                     |
| **預估 Token**      | ~25k+                                                                          |
| **Complexity 對應** | `complex`（對齊 PROPOSAL_024 `force_complex_scenarios`）                       |

### 2.4 車道分流決策示意

```
User 新指令 / Gate Check 通過
         ↓
    @Lead 派發前風險評估
         ↓
   ┌─────┼─────┐
   ↓     ↓     ↓
 20項   20項   任一
 全綠   綠+紅  紅燈
   ↓     ↓     ↓
🏎️快    🚗標   🚚重
```

## 三、@Lead 快車道分流決策指標（20 項安全白名單）

任務必須**完全符合**以下 20 項指標，`@Lead` 方可路由至快車道。**觸發任一紅燈則自動升級車道**（標準或重裝，依違規項性質而定）。

本 checklist 由新建 `.agents/tasks/lane-routing-task-classification.md` 外部化（依 PROPOSAL_013 模板外部化強制規定），lead.md 僅保留對 task 檔的引用 + 分級決策邏輯。

### 3.1 [檔案與依賴層級]

1. 預估修改檔案數 ≤ 3 個
2. 不涉及新增、刪除或升級套件依賴（`package.json` / `requirements.txt` 等）
3. 不新增或修改對外部第三方服務（Telegram API / Google Gemini / Grok 等）的整合
4. 不涉及專案目錄結構重構或引入新設計模式

### 3.2 [資料與狀態層級]

5. 資料庫 / File-based Schema **絕對凍結**（無新增資料表 / 欄位 / JSON 結構變更）
6. API Request/Response 合約結構不變
7. 不修改前端全域狀態管理（Vuex/Pinia）或後端 Cache 機制
8. 客戶端快取（LocalStorage/Cookie）資料結構向下相容
9. 零資料遷移（Data Migration）或排程腳本修改需求

### 3.3 [系統與資安層級]

10. **與身分驗證、權限控管、Token 簽發完全無關**（對齊 `skills/security-audit.md` SC-01 / SC-02 / SC-05）
11. 無環境變數（`.env`）異動
12. 非同步、執行緒並發（Concurrency）與鎖的邏輯凍結（對齊 `skills/concurrency-guard-pattern.md`）
13. 生命週期鉤子（Lifecycle Hooks）凍結，無初始化序列變更
14. 不新增或修改中介軟體（Middleware）或路由攔截器（Interceptors）
15. 全域錯誤處理、Try-Catch 與 Log 機制維持不變
16. 核心計算演算法複雜度低（無新增遞迴 / 巢狀迴圈 / 狀態機）
17. 不碰觸 CI/CD（`.github/workflows`）與 Docker 基礎設施

### 3.4 [純粹性層級]

18. 僅限 CSS/SCSS 顏色、排版等**純表面樣式微調**
19. 僅修正靜態文本、註解、或 i18n 語系字串
20. 僅補充單元測試覆蓋率，不更動業務邏輯原始碼

### 3.5 紅燈觸發後的升級規則

| 違規類型                                             | 升級目標                        |
| ---------------------------------------------------- | ------------------------------- |
| 觸發第 10 / 11 / 12 項（資安 / 併發 / 環境變數）     | 🚚 **強制重裝車道**（安全優先） |

## 四、實際運作案例對比

以下為三種車道的具體觸發範例與 Token 成本差異。案例用於 `lane-routing-task-classification.md` 的 Few-Shot 引導 `@Lead` 做快速判斷。

### 4.1 🏎️ 快車道範例（高頻率、低風險；~2k Tokens）

僅需單一實作 Agent 獨立執行，無需 `@Reviewer` 介入：

1. **文案除錯**：將 Telegram 推播訊息中的「Invesment」拼字錯誤修正為「Investment」
2. **樣式微調**：將 Vue 儀表板的「暫停通知」按鈕從藍色改為警告橘紅色
3. **日誌優化**：在既有的價格擷取函數中，補上一行 `console.log` 印出時間戳記
4. **補齊測試**：針對既有 `calculateROI()` 函數，在不改動原始碼前提下於測試檔新增邊界值測試案例
5. **預設值修改**：將系統設定檔中「觸發通知的預設價格波動百分比」由 `1.5%` 改為 `2.0%`（workspace 內層設定，不涉 strategyWeight）

> ⚠️ **注意**：案例 5 的「預設值修改」若涉及 `strategyWeight` 則強制升級重裝車道（對齊 `consultant.md §核心禁止條款` + workspace `CRITICAL_PATHS.strategyWeight 異動路徑`）

### 4.2 🚗 標準車道範例（中頻率、中風險；~8-12k Tokens）

需 `@Planner` 拆解步驟 + `@Reviewer` 防呆：

1. **新增一般 API**：新增一個讀取本地 JSON 檔的 GET 端點，用於列出目前追蹤的股票代碼清單
2. **新增 UI 元件**：在前端開發新的折線圖 Component 並串接已存在的查詢 API
3. **常規業務邏輯擴充**：在通知發送前加入判斷式「若今天是週末則除非波動 > 5% 否則不發送」
4. **表單驗證強化**：在前端新增追蹤表單中加入正規表達式確保輸入代碼符合英數字格式
5. **重構單一函數**：將一個過長（> 100 行）的資料解析函數提取拆分為三個小私有函數（Clean Code 原則）

### 4.3 🚚 重裝車道範例（低頻率、極高風險；~25k+ Tokens）

強制啟動全量 10 階段 + 架構師介入 + 資安盤點：

1. **資料層大重構**：從本地 JSON 檔全面遷移至關聯式資料庫（PostgreSQL）
2. **身分驗證導入**：加上 OAuth2（如 Line Login 授權），涉及 Session 管理與 JWT Token 簽發
3. **金流串接**：加入訂閱制功能，對接外部第三方金流 API 進行信用卡扣款
4. **架構微服務化**：將「抓取價格排程引擎」與「發送 Telegram 訊息 Worker」從主程式抽離成獨立服務
5. **核心並發優化**：重寫價格抓取演算法，從單一迴圈改為能同時處理 10,000 檔標的的非同步並發佇列（Task Queue）

### 4.4 當前提案本身的車道判定範例（Meta）

本提案（PROPOSAL_032）若於執行時走哪條車道？

- 修改 `.agents/rules/lead.md` 工作流 → 觸發第 13 / 14 項（Lifecycle / Middleware 類比）
- 新增 `.agents/tasks/*.md` → 觸發第 1 項（檔案數）+ 第 4 項（結構重構）
- → **🚚 重裝車道**（對齊：本提案本身即為架構層變更，適合全量審查）

## 五、預期效果與降級防護網（Fallback Mechanism）

### 5.1 預期效果

#### 量化

- **極速反應**：日常維護與微調任務處理時間從**分鐘級降至 10 秒級**
- **成本銳減**：過濾掉約 **70% 的非必要審查交接**，API Token 消耗大幅降低
- **減少幻覺**：越短的工作流，LLM 忘記上下文或產生幻覺的機率越低（對齊 PROPOSAL_001 §s_state_anchor「禁止推論超過 1 步」核心意圖）
- **@Auditor 維度提升**：
  - 3.1 自我優化：4.5 → **預期 4.7**（閉環反應速度）
  - 5.1 指令遵循度：4.6 → **預期 4.8**（短鏈減少 drift）
  - 整體預估：4.41 → **預期 4.50**（+0.09）

#### 質化

- **開發者體驗**：日常微調不必等 10 分鐘審查，專注於真正需要深思熟慮的任務
- **對齊 2026 產業標準**：Multi-lane routing 為 LangGraph / CrewAI 等框架的主流設計
- **系統可用性**：降低資源不必要占用，User 感受到「系統反應快」

### 5.2 降級防護網（Fallback Escalation）

為防止「快車道翻車」，於快車道執行中引入**三重自動升級機制**：

#### 機制 1：編譯 / 執行報錯自動升級

- **觸發條件**：`@Backend` / `@Frontend` 完成修改後，語法檢查（linter）或測試套件（`run-all.sh` / `node:test`）返回紅燈
- **處置邏輯**：任務**強制升級至標準車道**，喚醒 `@Reviewer` 進行除錯
- **記錄**：於 `PENDING_ACTIONS.md` 寫入 `LANE_ESCALATION_AUTO` + 原始車道 + 升級原因

#### 機制 2：自我懷疑自動升級

- **觸發條件**：實作 Agent 於執行過程中發現**需修改 20 項指標外的其他檔案**
- **處置邏輯**：
  - 若擴展檔案 ≤ 5 份且無資安影響 → 升級**標準車道**
  - 若擴展檔案含資安敏感路徑（workspace `CRITICAL_PATHS` 或 `skills/security-audit.md §1` SC-XX）→ 升級**重裝車道**
- **記錄**：於 `PENDING_ACTIONS.md` 寫入 `LANE_ESCALATION_SELF_DOUBT`

### 9.2 設計原則總結

1. **白名單嚴格性**：快車道需 20 項**全綠**，任一紅燈自動升級
2. **降級優先於推進**：任何疑問 → 升級車道，而非強推快車道
3. **安全鐵律不妥協**：涉及 strategyWeight / 資安 / 併發 → 強制重裝車道
4. **User 可覆蓋**：User 可任意時刻升級或降級
5. **可觀察性**：升級記錄、P-20 巡邏、AUDIT_HISTORY drift_score 三重監控
6. **廠商中立**：lane_map 用語意名稱（fast/standard/heavy），不綁定特定執行框架

### 9.3 未來延伸（非本提案範圍）

- **可配置指標**：將 20 項指標從硬編碼改為可 workspace 覆蓋（某專案可調整閾值）
- **快車道機器學習分級**：累積升級歷史後訓練分類模型，輔助 @Lead 判斷
