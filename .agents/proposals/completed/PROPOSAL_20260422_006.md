## 一、問題描述

### 根因分類

**類型**：新提案未明文繼承歷史提案意圖，造成設計語意回退（Design Intent Regression）

### 問題陳述

在 2026-04-22 整合性分析（`@Lead` 整合性分析報告 §關鍵警示 1）中發現：

- **PROPOSAL-011**（2026-04-21 DONE）「業務脈絡錨定批次補強」明文要求 6 份 rules 在 Layer 3 綁定 IMN 技術棧（Node.js ESM / File-based / Oracle VM / Telegram Bot API），作為防止 LLM 產生偏離系統約束建議的**內化防護**
- **PROPOSAL_20260422_002**（OPEN）主張「硬編碼任一專案視為規範違反」，改為通用軟體協作描述 + workspace 動態注入

兩份提案對同一設計問題採取**相互矛盾**的方向：

| 維度 | PROPOSAL-011 | PROPOSAL_20260422_002 |
|------|-------------|---------------------|
| 錨定方式 | 硬編碼於 rules | Workspace 動態注入 |
| 變更範圍 | 6 份 rules 加 IMN 技術棧 | 6+ 份 rules 去 IMN 化 |
| 防護層級 | Rule 內化 | 外部注入 |
| 哲學 | Rule 為單點防護 | Rule 為通用框架 |

### 具體觀察

若直接採納 002 而不處理 PROPOSAL-011，會出現：

1. **同檔雙規範**：`backend.md` 既宣稱「遵守 PROPOSAL-011 的 Oracle VM 錨定」，又執行 002 的「通用化 + workspace 注入」
2. **歷史計數失真**：`PROPOSAL-011` 狀態保持 `DONE`，但其意圖實際已被 002 推翻
3. **審計盲區**：`@Retro` 下次審計時，無法辨識「011 仍有效」或「011 已被 002 取代」
4. **反覆問題計數觸發**：若未來某提案再次觸碰「IMN 技術棧錨定」議題，`@Retro` 計數器會將其視為第 3 次，觸發 🚨 反覆問題警告（誤判）

### 問題影響層級

- **系統規範一致性**：🔴 高（同時存在兩份矛盾的 DONE 規範意圖）
- **審計正確性**：🟡 中（反覆問題計數可能失準）
- **採納風險**：🔴 高（002 採納後 011 狀態未處理即成為歷史遺留隱患）
- 綜合風險等級：🔴 高

### 本提案的定位

本提案**不拒絕** PROPOSAL-011 的設計意圖，而是：

- **繼承 011 意圖**：「防止 LLM 產生偏離專案約束的建議」→ 此目標仍有效
- **調整實作方式**：由「硬編碼內化」改為「workspace 注入 + 缺失時保守升級」
- **明文銜接**：`PROPOSAL_INDEX.md` 標注繼承關係，避免語意失聯

### 3.2 改寫原則（對齊 PROPOSAL_20260422_002 精神）

每個受影響位置依下列三原則改寫，**同時保留 PROPOSAL-011 意圖**：

#### 原則一：保留「通用層次結構」

`RULES_DESIGN_GUIDE §五` 的三層次（Layer 1 系統定位 / Layer 2 業務觸發 / Layer 3 技術棧錨定）結構**保留**，但各層次的「內容填充」改為動態引用。

#### 原則二：Layer 3 改為動態引用

**改造前**（PROPOSAL-011 硬編碼）：

```markdown
### Layer 3：技術棧錨定（How）
- Node.js ESM 模組系統
- File-based 資料儲存冪等性
- Oracle Free Tier 記憶體限制
- Telegram Bot API 重試機制
```

**改造後**（本提案動態引用）：

```markdown
### Layer 3：技術棧錨定（How）
依 `@Lead` 注入之 `PROJECT_CONTEXT.tech_stack`（來源：`workspaces/<active>.md`）執行。
若 `CURRENT_WORKSPACE` 缺失或 `tech_stack` 欄位不完整，依 `lead.md §s_state_anchor 缺失判斷備案` 採保守升級態度（對齊 PROPOSAL_20260422_007 §降級機制）。

> 本層意圖繼承自 PROPOSAL-011「防止 LLM 產生偏離系統約束的建議」；
> 實作方式依 PROPOSAL_20260422_002 改為動態注入。
```

#### 原則三：每份 rules 的 Layer 3 改寫必含「意圖繼承聲明」

作為人類可讀的追溯標記，每份 rules 的 Layer 3 末段加入：
