## 一、問題描述

### 根因分類

**類型**：HITL 終止條件缺乏量化定義（QW-08）

### 問題陳述

`architect.md` 與 `backend.md` 的 HITL 終止條件
均採用定性描述，缺乏可客觀判斷的數值化門檻。

#### architect.md 具體問題

```
現況：
「設計複雜度過高時應升級 @Lead」
「技術風險較大的決策需 HITL 確認」

問題：
「複雜度過高」無量化標準
「技術風險較大」無量化標準
→ @Architect 對「是否需要升級」的判斷
  完全依賴當下 LLM 的主觀評估，
  可能在高壓執行情境下系統性低估風險
```

#### backend.md 具體問題

```
現況：
「涉及大量資料異動時需 HITL 確認」
「效能問題嚴重時升級 @Lead」

問題：
「大量資料異動」未定義數量門檻
「效能問題嚴重」未定義量化指標
→ @Backend 可能在「只是稍微多一點」的
  模糊地帶繼續執行而不升級
```

### 問題影響層級

- 影響範圍：@Architect 設計決策、@Backend 執行判斷
- 風險分類：HITL 觸發可靠性
  （量化門檻缺失導致升級行為不穩定）
- 風險等級：🟡 中風險

## 二、根因分析

### 直接根因

兩份 Rules 初版均以「判斷型描述」作為
HITL 觸發條件，預設 Agent 能正確評估風險程度。
但 LLM 在長程任務中的風險評估傾向於保守低估，
定性描述無法提供客觀的觸發基準。

### 共同根因

缺乏「HITL 觸發條件數值化規範」，
與 PROPOSAL-006（@Retro 週期量化）
同屬「關鍵流程缺乏量化定義」的系統性問題。

## 三、提案內容

### architect.md 修改項目

#### 修改一：設計複雜度量化門檻

```markdown
// 修改位置：architect.md HITL 升級條件章節

// 修改前
設計複雜度過高時應升級 @Lead。

// 修改後
以下任一情況視為「設計複雜度超標」，
必須升級 @Lead 進行 HITL 確認：

| 複雜度指標      | 量化門檻                    | 說明              |
| --------------- | --------------------------- | ----------------- |
| 涉及 Agent 數量 | ≥ 3 個 Agent 同時協作       | 跨 Agent 介面設計 |
| 新增 API 端點   | 單次設計 ≥ 5 個端點         | 批次 API 規格設計 |
| 資料結構變更    | 影響 ≥ 2 個現有 JSON Schema | 結構相容性風險    |
| 跨模組依賴      | 新增 ≥ 3 個跨模組呼叫關係   | 耦合度風險        |
| 設計迭代次數    | 同一設計修訂 ≥ 3 次         | 需求不明確信號    |

上述任一觸發後：
停止設計輸出 → 向 @Lead 說明複雜度指標
→ 等待 @Lead 確認後繼續或拆分任務
```

#### 修改二：技術風險量化門檻

```markdown
// 修改位置：architect.md HITL 升級條件章節

// 修改前
技術風險較大的決策需 HITL 確認。

// 修改後
以下任一情況視為「技術風險觸發」，
必須升級 @Lead 進行 HITL 確認：

1. 破壞性變更：
   新設計與現有系統介面不相容
   （需修改已部署的 API 合約或 JSON Schema）

2. 效能風險：
   設計中包含未知效能影響的操作
   （如：全量資料掃描、無索引搜尋、同步等待）

3. 外部依賴新增：
   引入現有系統未使用的第三方服務或 API
   （如：新 Telegram API 功能、外部資料來源）

4. 安全邊界相關：
   設計涉及 strategyWeight、金鑰管理、
   或 .agents/ 文件結構的任何變更
```

### backend.md 修改項目

#### 修改一：資料異動量化門檻

```markdown
// 修改位置：backend.md HITL 升級條件章節

// 修改前
涉及大量資料異動時需 HITL 確認。

// 修改後
以下任一情況視為「資料異動超標」，
執行前必須升級 @Lead 進行 HITL 確認：

| 異動類型            | 量化門檻                     |
| ------------------- | ---------------------------- |
| 批次寫入筆數        | 單次 ≥ 50 筆記錄             |
| 檔案覆寫            | 覆寫現有檔案（非新增）≥ 3 個 |
| strategyWeight 異動 | 任何數值變更（無論大小）     |
| 歷史資料修改        | 修改 30 天前的任何記錄       |
| 資料刪除            | 任何刪除操作（零容忍）       |

觸發後：
停止執行 → 向 @Lead 說明異動範圍與影響
→ User 明確確認後方可執行
```

#### 修改二：效能問題量化門檻

```markdown
// 修改位置：backend.md HITL 升級條件章節

// 修改前
效能問題嚴重時升級 @Lead。

// 修改後
以下任一情況視為「效能問題需升級」：

1. 預估執行時間超過 30 秒的同步操作
   → 升級 @Lead，評估是否改為非同步執行

2. 單次讀取資料量超過 10,000 筆記錄
   → 升級 @Lead，評估分頁或快取策略

3. 同一邏輯在 3 次嘗試後仍出現
   執行逾時或記憶體不足錯誤
   → 停止執行，升級 @Lead 進行架構評估

禁止：
@Backend 自行決定「效能問題可以忽略」，
任何達到以上門檻的情況必須升級。
```

## 七、備註

- 本提案同時修改兩份 Rules，
  建議在同一次執行作業中完成，
  確保 architect.md 設計門檻
  與 backend.md 執行門檻的數值一致性。
- strategyWeight 異動「任何數值變更均觸發 HITL」
  與 PROPOSAL-005（consultant.md 禁止直接修改）
  形成設計層→執行層的雙重保障：
  @Consultant 不得提出直接修改，
  @Backend 在任何異動前必須升級確認。
- 本提案兩份文件合計新增約 +200 tokens，
  均為非 AlwaysOn 文件，Token 預算寬鬆。
- backend.md 的「資料刪除零容忍」
  是本次提案最高風險保障條款，
  執行確認時應特別審查此條文語意。
