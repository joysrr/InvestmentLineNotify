## 一、問題描述

@Auditor 與 @Retro 兩 Agent 職責邊界：

- `@Auditor`：定期 5 維度評分 → AUDIT_HISTORY.md → 觸發 P-15
- `@Retro`：根因分析 → 提案 → User 採納

**潛在衝突場景**：

1. @Auditor 識別維度低分 → P-15 觸發
2. @Retro 同時手動觸發進行根因分析
3. 兩者建議可能不一致（Auditor 視為品質問題；Retro 視為單一事件）
4. User 不清楚應採納誰的建議

## 三、提案內容

### 3.1 新建 `.agents/tasks/audit-retro-coordination.md`

```markdown
# Task: @Auditor + @Retro 協作流程

> 由 PROPOSAL_20260422_031 建立。
> 明定兩 Agent 在共同識別系統改善時的優先級與分工。

## 觸發條件

任一情況觸發協作：

1. @Auditor 評審後任一維度 < AUDIT_DIMENSION_MIN_SCORE（3.0）→ P-15
2. @Retro 收到 TEST_REPORT / REVIEW_REPORT 啟動根因分析
3. User 同時手動觸發兩者

## 協作流程（5 步驟）

### Step 1：識別觸發來源

- **A 路徑**：@Auditor P-15 觸發 → 直接走 Step 2
- **B 路徑**：@Retro 收 TEST_REPORT → 先檢查 AUDIT_HISTORY.md 最新一行
  - 若該維度本次有低分 → 走 Step 2（合流）
  - 若該維度本次正常 → 純 @Retro 流程，跳過本協作

### Step 2：交接資訊（@Auditor → @Retro）

@Auditor 透過 @Lead 通知 @Retro 時，必須附帶：

- 觸發維度（如 3.2）
- 子 Agent 派遣輸出的 critical_risks 清單
- optimization_suggestions 摘要
- baseline_comparison Δ

### Step 3：@Retro 根因分析

@Retro 接收後執行 §s_root_cause：

- 將 @Auditor 的 risks 視為「症狀」
- 進行 REQ / ARCH / DEV / TEST 四層根因追溯
- 識別是否屬「反覆問題」（PROPOSAL_INDEX §🔗 比對）

### Step 4：提案產出（@Retro 主導）

- @Retro 是**唯一**有權產出提案的 Agent
- 提案內必須引用 @Auditor 觸發來源（如「依 AUDIT_HISTORY.md 2026-04-22 第三次評審 R16」）
- @Auditor 的 optimization_suggestions 可作為提案 §三 內容輸入，但需經 @Retro 根因分析篩選

### Step 5：閉環驗證（@Auditor 後續介入）

- User 採納提案 → @Lead 執行 → 完成後通知 @Auditor
- @Auditor 下次評審時優先檢視該維度，驗證改善是否成效
- 寫入 AUDIT_HISTORY.md 細項變化（如 3.2: 2.8 → 4.5）

## 衝突仲裁

若 @Auditor 建議與 @Retro 根因分析建議**不一致**：

- @Lead 仲裁：依「根因深度優先」原則 → 採 @Retro 方向
- 衝突記錄於 AUDIT_DECISION_LOG.md（依 PROPOSAL_027）

## 禁止行為

- **絕對禁止** @Auditor 越權撰寫提案（auditor.md §s05 已明文）
- **絕對禁止** @Retro 略過 @Auditor 觸發資訊獨立產提案
- **絕對禁止** User 同時採納 @Auditor 與 @Retro 兩方建議（必擇一，避免分歧）
```
