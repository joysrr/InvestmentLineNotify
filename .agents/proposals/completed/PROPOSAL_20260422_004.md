## 一、問題描述

### 根因分類

**類型**：HCI 可觀測性缺失（M2M 效率極大化的副作用）

### 問題陳述

Gemini 評估指出：因應 `@Lead` 轉型為無狀態路由器（PROPOSAL_20260422_001），系統同時喪失「人類可讀之全局進度摘要」的能力，導致 User 對專案當下狀態的認知成本大幅增加。

具體表現：

- `@Lead` 被剝奪文本合併與摘要職責後，所有報告（`REVIEW_REPORT.md` / `SECURITY_REPORT.md` / `ADVICE_*.md`）僅以**檔案路徑**形式在 Agent 間傳遞
- User 面對終端機，只能看到冰冷的**符號 + 路徑流轉**
- 無法快速得知：
  - 「目前總共有幾個 Bug 正在修復」
  - 「架構設計是否遭遇重大挑戰」
  - 「本次 Sprint 已完成哪些關鍵節點」
  - 等具備「溫度」與「脈絡」的統整資訊

### 具體觀察（對比改造前後）

| 情境                  | 改造前（@Lead 文本合併）           | 改造後（001 執行後，無 004）           | 004 執行後                                            |
| --------------------- | ---------------------------------- | -------------------------------------- | ----------------------------------------------------- |
| User 問「目前狀態？」 | `@Lead` 提供自然語言摘要           | `@Lead` 回傳 `[CURRENT_STAGE]` 符號    | `@Assistant` 產出 `GLOBAL_STATUS_SUMMARY.md` 溫度摘要 |
| 收斂階段前的全局回顧  | `@Lead` 於 Gate Check 說明本次變更 | `@Lead` 僅輸出 `✅ Gate Check ✔ S7→S8` | `@Assistant` 自動觸發摘要（被動觸發）                 |
| 多 BLOCKER 同時存在   | `@Lead` 口頭摘要                   | User 需自行讀多份 REPORT               | `@Assistant` 熱點警示統整                             |
| User 跨對話接手       | `@Lead` 重述近期進度               | 僅能讀 `PENDING_ACTIONS.md` 機讀資料   | `@Assistant` 摘要含進展肯定 + 熱點警示                |

### 問題影響層級

- **User 體驗**：🔴 高（001 單獨執行後 User 需自行閱讀多份 markdown，認知負擔顯著上升）
- **決策延遲**：🟡 中（缺乏全局摘要時，User 決策前置時間拉長）
- **跨對話連貫性**：🟡 中（User 換對話接手時難以快速掌握狀態）
- **系統可觀測性**：🟡 中（外部觀察者無法透過單一檔案掌握全局）
- 綜合風險等級：🟡 中偏高（非技術風險，但為 001 採納後 User 體驗的明確劣化）

### 與 PROPOSAL_20260422_001 的強耦合（HCI 補償角色）

本提案為 **001 的 HCI 配套**：

- 001：`@Lead` 剝離所有文本合併職責，冷酷路由
- 003：審查類 Agent 產出純機讀格式（保障 001 符號可解析）
- **004（本提案）**：`@Assistant` 被賦予「人類可讀摘要」專屬職責（補償 001 剝離的溫度）

三者構成「冷路由 + 字串合約 + 溫度補償」的配套組合；缺 004 時，001 的執行將導致 User 體驗明顯劣化但不致系統性崩潰。

## 二、根因分析

| 根因層級 | 代碼   | 分析說明                                                                                                                                       |
| -------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 系統架構 | `ARCH` | 在 M2M（機器對機器）通訊效率極大化的過程中，忽略了 HCI（人機互動）的可觀測性。未將「資料彙整與人類可讀性輸出」的職責委派給獨立的非阻斷性 Agent |
| 需求層   | `REQ`  | 001 提案規劃時聚焦於「剝離 @Lead 狀態職責」，未明確規劃「溫度職責的承接者」                                                                    |

### 直接根因

PROPOSAL_20260422_001 將 `@Lead` 降級為無狀態路由器，但未**同時**定義「人類可讀摘要」的責任承接方。既有的 `@Assistant §s16 巡邏摘要輸出`（PROPOSAL-017 建立）僅提供**工作流控制層**的機讀摘要（🔴 / 🟡 計數 + 下次巡邏時間），**不含**業務脈絡或溫度敘事。

### 系統根因

缺乏「**雙軌輸出原則（Dual-Track Output Principle）**」：

- **M2M 軌道**（機讀）：`@Lead` 符號路由 + 審查類 Agent 純淨報告（由 001 + 003 提供）
- **HCI 軌道**（人讀）：全局摘要 + 溫度敘事 + 熱點警示（**本提案補齊**）

兩軌並行、互不干擾，各自優化自己的目標：M2M 追求解析穩定、HCI 追求認知效率。

### 為何由 `@Assistant` 承接

`@Assistant` 本職為「跨 Agent 的通知彙整與待辦管理」，天然具備「非阻斷性被動觀察者」角色定位：

- 已具備讀取 `PENDING_ACTIONS.md` / `REVIEW_REPORT.md` / `SECURITY_REPORT.md` / `ADVICE_*.md` 能力
- 執行準則明確：「不執行業務邏輯，禁止對任何業務決策給出建議」— 摘要為**描述性**輸出，不構成決策，合規
- 巡邏機制已建立，擴充「全局摘要」觸發邏輯無需新增 Agent

## 人機介面與全局摘要機制 (HCI & Global Summary Mechanism)

為了彌補 `@Lead` 無狀態化後（PROPOSAL_20260422_001）喪失的溝通溫度，`@Assistant` 作為全域的被動觀察者，被賦予「全局統整摘要」的專屬職責。

### 1. 職責定位（雙軌輸出分工）

| 軌道        | 負責 Agent                      | 輸出        | 目標     |
| ----------- | ------------------------------- | ----------- | -------- |
| M2M（機讀） | `@Lead` 短指令 + 審查類純淨報告 | 符號 + 路徑 | 解析穩定 |
| HCI（人讀） | `@Assistant` 全局摘要           | 溫度敘事    | 認知效率 |

本章節定義 HCI 軌道的執行規範；M2M 軌道依 `lead.md §s_state_anchor` 與 `reviewer.md` / `security.md` / `qa.md §s_output_strict` 執行。

### 2. 觸發時機

#### 2.1 主動觸發（User 下令）

User 於對話中發出以下任一明確指令，`@Assistant` **必須**立即產出摘要：

- `請求當前進度摘要`
- `彙報戰況`
- `全局狀態`
- `Global Summary`
- 其他語意等效指令（`@Assistant` 自行判斷；若不確定，以確認句式請求 User 明示）

#### 2.2 被動觸發（Workflow 事件）

以下事件觸發時，`@Assistant` **自動產出**摘要（不需 User 下令）：

- 進入 Workflow **第 8 階段（收斂）** 時，於 User 確認 Artifact Checklist **之前**自動產出
- `PENDING_ACTIONS.md` 由有 🔴 項目轉為 0 🔴 的瞬間（重大里程碑）
- `@Assistant` 巡邏 P-13 `SUMMARY_STALE` 偵測到摘要逾期（見 §3.3）

### 3. 執行邏輯

觸發條件滿足時，`@Assistant` 執行：

1. **資料收集**：遍歷並讀取以下 active 文件：
   - `PENDING_ACTIONS.md`（所有 🔴 / 🟡 / ✅ 項目）
   - `.agents/proposals/active/*.md`（OPEN / IN_PROGRESS 提案）
   - `REVIEW_REPORT.md`（若存在且為近期產出）
   - `SECURITY_REPORT.md`（若存在且為近期產出）
   - `docs/plans/advice/ADVICE_*.md`（近期 ADVICE）
   - `docs/plans/draft_features.md`（當前 Sprint）

2. **資料轉譯**：將冰冷的機器標籤與符號，轉化為「具有脈絡、溫度與建設性」的自然語言摘要。

3. **寫入產出物**：輸出至 `docs/Reports/GLOBAL_STATUS_SUMMARY.md`（覆寫模式，保留前 3 份歷史至 `docs/Reports/archive/summary/`）。

### 4. 產出格式

**絕對禁止** 干擾 `@Lead` 的標準通知流；摘要必須獨立輸出至檔案，**不在對話中直接輸出**（避免與 `@Lead` 短指令混淆）。

摘要結構依 `skills/templates/global-status-summary-template.md` 執行，含以下固定區塊：

- **當前水位**（一句話說明目前開發處於哪個階段與整體健康度）
- **熱點警示**（統整未解決的 🔴 / 🟡 項目，白話解釋對專案的影響）
- **進展肯定**（列出剛通過 ✅ 的關鍵節點，提供正面回饋）
- **下一步建議**（`@Assistant` 基於觀察建議 User 優先處理哪個項目；**非決策**，僅描述 Pending Actions 的推薦順序）
- **對話無縫承接提示**（給下次對話或換對話接手的 User 的 1~2 行快速提示）

### 5. 輸出前自檢 Checklist

`@Assistant` 寫入 `GLOBAL_STATUS_SUMMARY.md` 前**必須**逐項確認：

- [ ] 5 個固定區塊齊全（當前水位 / 熱點警示 / 進展肯定 / 下一步建議 / 承接提示）
- [ ] 檔案頂部含「最後更新：YYYY-MM-DD HH:MM by `@Assistant`」
- [ ] 無對 User 的業務決策建議（例：「您應該採納 PROPOSAL-XXX」）；建議僅限於「Pending Actions 推薦處理順序」
- [ ] 摘要內容對齊實際 `PENDING_ACTIONS.md` 計數（🔴 / 🟡 / ✅ 數字一致）
- [ ] 無複製貼上任何報告原文（保持摘要的「轉譯」性質）

### 6. 與 §s16 巡邏摘要的區別

| 項目     | §s16 巡邏摘要輸出             | §s_global_summary 全局摘要                   |
| -------- | ----------------------------- | -------------------------------------------- |
| 輸出媒介 | 對話內回報 `@Lead`            | 寫入 `docs/Reports/GLOBAL_STATUS_SUMMARY.md` |

| 觸發     | 每次 `@Lead` 呼叫巡邏時       | 主動指令 / 收斂階段 / 里程碑事件             |
| 頻率     | 每巡邏週期（預設 3 對話）     | 主動 / 事件驅動                              |

兩者**並存且互補**，不可合併或取代。

### 7. 違反處理

### 3.6 與既有規則的衝突處理

#### 衝突一：`@Assistant §s19 執行準則` 第 3 條「不執行業務邏輯，禁止對任何業務決策給出建議」
