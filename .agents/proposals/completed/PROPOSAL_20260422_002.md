## 一、問題描述

### 根因分類

**類型**：職責邊界模糊（通用開發邏輯 vs 專案環境變數未分離）

### 問題陳述

Gemini 評估指出：現行 `.agents/rules/` 下所有 Agent 規則（特別是 `@Backend`、`@Frontend`）內直接硬編碼 **InvestmentLineNotify** 專案特定資訊，包含但不限於：

- 專案名稱（InvestmentLineNotify）
- 商業情境（Telegram 投資訊號推送、量化策略、策略權重 `strategyWeight`）
- 技術棧選型（Node.js ESM / Vue 3 / Oracle VM Free Tier / Telegram Mini App）
- 業務邏輯（初始 data 目錄、`data/` 正式環境、`.env.example` 位置）

### 問題影響層級

- **可移植性**：將框架套用至新專案（例：電商客服機器人、博客後台）時，必須逐份修改 13 份 rules，變更範圍約 ~2,000 tokens，出錯機率高
- **維護成本**：同一框架若同時服務多專案，rules 需分岔維護，無法單源升級
- **污染風險**：舊專案邏輯殘留（例：`strategyWeight` 在新專案可能不存在）導致 Agent 產出錯誤建議
- **審計盲點**：無法區分「通用規則違反」與「專案情境不符」，`@Retro` 審計成本上升
- 風險等級：🟡 中（非立即危害，屬系統演進品質與可擴展性）

## 二、根因分析

| 根因層級 | 代碼   | 分析說明                                                                                                                                                           |
| -------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 系統架構 | `ARCH` | 職責邊界模糊：Rules 系統混合承載「通用開發邏輯（Core Soul）」與「專案環境變數（Project Context）」兩種語意，缺乏標準化的專案初始化（Onboarding）機制與環境注入通道 |
| 需求層   | `REQ`  | 初期需求僅有單一專案 InvestmentLineNotify，未預留跨專案擴展設計；`RULES_DESIGN_GUIDE.md §五` 要求 Layer 3 技術棧錨定至當前專案，固化了單專案假設                   |

### 直接根因

`.agents/rules/` 最初設計時將 InvestmentLineNotify 視為**唯一服務對象**，業務脈絡三層次規範（What / When / How）要求直接綁定專案技術棧，作為防止 LLM 產生通用但偏離系統約束建議的保護機制。

### 系統根因

缺乏「**雙層分離原則**」：

1. **Core Soul 層**（通用、跨專案）：Agent 身份、行為鐵律、工作流程、審查框架、HITL 升級條件、DoD 自評機制 — 這些**本質上與專案無關**，應保持通用
2. **Project Context 層**（專案特定）：專案名稱、技術棧、業務邏輯、功能域、必測項、關鍵路徑、SC-XX 範疇 — 這些**隨專案變化**，應外部化

當前兩層混雜於同一份 rules，形成「通用規則與專案變數交織」的耦合結構。

### 設計思路（Gemini 原報告採納）

採 **混合黃金標準（Hybrid Approach）**：

- **策略 A（靜態注入）**：針對**原則、身分、技術環境**（Rules & Context）— 由 `@Lead` 於任務啟動前，預先合併通用的 `rules/*.md` + 專案專屬 `workspaces/*.md` 後才派發給子 Agent
- **策略 B（動態讀取）**：針對**程式碼與巨量產出物**（Data & Artifacts）— Agent 依策略 A 注入的指令路徑，使用 Read / Grep / Bash 工具動態讀取實際專案檔案

此設計與現有 `tech-stacks/` 與 `domains/` 的「動態注入」機制**同源**（`lead.md §資源與上下文映射表` 已建立先例），本提案為其**向上延伸至專案層**。

### 3.2 實作機制：混合黃金標準

#### 策略 A：靜態注入（Rules & Context）

**執行時機**：`@Lead` 接收 User 指令後、派發子 Agent 前

**合併規則**：

1. 讀取對應 rule 檔（例 `backend.md`）的「Core Soul」通用規則
2. 讀取當前 active workspace（由根目錄 `.agents/CURRENT_WORKSPACE` 指定）
3. 將 workspace 的 `PROJECT_CONTEXT` / `TECH_STACK` / `FUNCTIONAL_DOMAINS` 等欄位以「系統變數」形式拼接至 rule 之前，形成完整上下文後才派發

**範例派發指令**：

```
@Backend 請實作訊號計算模組。
─────────────────────────────
[PROJECT_CONTEXT 注入區塊]
- 專案名稱：InvestmentLineNotify
- 業務領域：量化投資訊號推送
- 核心資料結構：strategyWeight / signalPool
- 部署環境：Oracle VM Free Tier (1GB RAM)
[TECH_STACK 注入區塊]
- 後端：Node.js ESM
- 儲存：File-based JSON / CSV
- 對外：Telegram Bot API
─────────────────────────────
依據以上 PROJECT_CONTEXT 執行任務。
```

#### 策略 B：動態讀取（Data & Artifacts）

**執行時機**：子 Agent 實際執行任務時

**使用工具**：Read / Grep / Glob / Bash（`cat` / `ls` / `grep`）

**範例**：`@Backend` 收到指令後，依注入的 `PROJECT_CONTEXT.source_root` 路徑使用 Read 讀取實際程式碼，不由 rule 硬編碼路徑。

依各 rule 性質分三類處理：

#### 類型 A：完全通用型（無需改動 body，僅新增 §動態注入參考）

#### 類型 B：半通用型（body 改造 + PROJECT_CONTEXT 錨點）

**適用**：`lead.md` / `planner.md` / `architect.md` / `consultant.md` / `qa.md` / `security.md`

## 四、預期效益

### 量化效益

| 維度                   | 改善前                            | 改善後                            |
| ---------------------- | --------------------------------- | --------------------------------- |
| 跨專案複用成本         | 需改 13 份 rules（~2,000 tokens） | 僅建立新 workspace（~300 tokens） |
| 新專案 Onboarding 時間 | ~4 小時（全面改寫）               | ~30 分鐘（填 workspace 模板）     |
| Rules 通用度           | 約 30%（業務脈絡層硬綁 IMN）      | 約 90%（僅流程範例保留註記）      |
| 污染風險               | 🟡 中（舊專案邏輯可能殘留）       | 🟢 低（Core Soul 無專案依賴）     |
| 多專案並行維護         | ❌ 需 fork 整套 rules             | ✅ 同一 rules + 多 workspace      |

### 質化效益

- **清晰分層**：Agent 的「通用能力」與「專案情境」邏輯分離，Core Soul 升級與專案維護解耦
- **審計聚焦**：`@Retro` 審計時可分別評估「通用規則缺陷」與「workspace 填寫不完整」，責任歸屬明確
- **知識資產保值**：PROPOSAL-001~021 累積的設計智慧全部保留，以通用形式重用於任何新專案
- **符合 Anthropic / Claude Code 最佳實踐**：對齊 Subagent 設計哲學（單一職責 + 動態脈絡注入）

### 非效益與取捨（避免過度承諾）

- **Token 整體略增**：rules 本體略減（~-300 tokens），但新增 workspaces/ 與 tasks/project-onboarding.md（+~600 tokens），淨增約 +300 tokens
- **首次建置成本**：本提案執行本身需 ~5~6 小時（五個 Phase）
- **學習曲線**：User 需熟悉「workspace 切換」概念；現有開發流程多一個預步驟
- **過渡期風險**：遷移期間若 `CURRENT_WORKSPACE` 指向錯誤，Agent 可能輸出不合宜內容 → 需 `@Assistant` 巡邏偵測兜底
