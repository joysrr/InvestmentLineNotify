### 1.2 當前 Hotfix 流程職責盤點

| 職責 | 歸屬 | 依據 |
|-----|-----|-----|

### 1.3 三個結構性缺口

#### 缺口 A：診斷單點風險

- 當前：`@Backend` 或 `@Frontend` **單人**背負「根因定位 + 修復實作」兩職
- 問題：
  - **修復盲點**：寫出 bug 的人容易重複同樣思維誤判
  - **跨模組事故無整合視角**：後端排程故障連帶前端 WebApp 崩潰時無人協調
  - **缺診斷經驗時反覆試錯**：初階開發者面對 memory leak / race condition 易反覆改錯模組

#### 缺口 B：Hotfix 資安空窗（🔴 最嚴重）

- 現行 §3.3 `跳過階段：Planner / Consultant / Architect 全部跳過`
- 但 **`@Security` 也被完全跳過**，流程未提及
- 若事故涉及 PROPOSAL-020 `SC-01 ~ SC-10`：
  - SC-01 Token 時效 / SC-02 金鑰外洩 / SC-03 strategyWeight 違規
  - SC-04 資料刪除授權 / SC-05 API 授權 / SC-06 初始資料驗證
  - SC-07 錯誤訊息洩漏 / SC-08 併發原子性 / SC-09 第三方套件 / SC-10 Log 敏感資料
- → Hotfix 修復可能**二次引入資安漏洞**，而 `@Reviewer` 快速審查依 PROPOSAL-020 §防線 1 明文「審可讀性 / Memory Leak / 效能（**未涉及安全**）」無法填補

#### 缺口 C：@Backend / @Frontend 上下文散落

- 現行：`@Backend` 自己讀 `tech-stacks/*.md` + `workspaces/*.md` + `CRITICAL_PATHS`
- 問題：
  - Hotfix 時效緊；自己找上下文浪費時間
  - @Lead 派發時未規範附帶關鍵路徑 / 部署約束 / 相關 tech-stacks
  - 對「跨模組事故」更嚴重（不知從哪些 tech-stacks 下手）

### 1.4 量化影響

| 診斷單點盲點 | 100% 事故由造 bug 者自己診斷 | 🟡 中 |

```markdown
## 十九、Hotfix 診斷強化三支柱（依 PROPOSAL_20260423_003）

本節為 PROPOSAL_20260423_003 核心產物，補齊現行 Hotfix Fast Lane（`emergency-shutdown-playbook §三`）的三個結構性缺口：診斷單點盲點 / 資安空窗 / 上下文散落。

### A. 三支柱總覽

| 支柱 | 目標 | 核心機制 | 觸發 |
|------|-----|---------|-----|
| **支柱 1：診斷組（Diagnostic Pair）** | 消除診斷單點盲點 | 事故複雜度達標 → `@Backend` 或 `@Frontend` + `@Reviewer` 雙眼診斷 | §十九.B 條件 |
| **支柱 2：@Security 條件式介入** | 堵 Hotfix 資安空窗 | 事故涉及 `SC-01~SC-10` → @Security 強制平行介入 | §十九.C 條件 |
| **支柱 3：@Lead 上下文注入** | 減少診斷時間 | 派發訊息附結構化上下文包 | §十九.D 派發規範 |

### B. 支柱 1 — 診斷組觸發條件

任一條件滿足即強制組診斷組（`@Backend` / `@Frontend` 其一 + `@Reviewer`）：

| 條件 | 量化門檻 |
|------|---------|
| **D1** | 事故涉及 ≥ 2 個模組（跨後端 / 前端 / 排程 / 第三方 API） |
| **D2** | 疑似 race condition / memory leak / 併發問題 |
| **D3** | 同一模組 24h 內第 2 次 Hotfix（對齐 SYSTEM_THRESHOLDS `HOTFIX_RECURRENCE_WINDOW`） |
| **D4** | User 明示「複雜事故」 / 「跨層故障」 |

**排除條件**（任一滿足 → 維持單人診斷）：
- 事故限單一模組 + 首次發生
- 明確錯誤訊息指向特定函式（diff < 50 LOC 可定位）
- User 明示「簡單事故」

**診斷組協作規範**（見 `skills/diagnostic-playbook.md §三`）：
- 修復實作者（`@Backend` / `@Frontend`）主導，`@Reviewer` 提供「第二雙眼睛」診斷視角
- `@Reviewer` 在診斷階段**不做審查**（避免思維混淆；診斷與審查分離）
- 診斷共識達成後，修復實作者執行；`@Reviewer` 於 Step 2 回歸審查角色
- 職責切換明確：診斷 → 實作 → 審查 三段式

### C. 支柱 2 — @Security 條件式介入觸發

若事故涉及以下任一 SC 範疇（對齐 `skills/security-audit.md §1`），`@Lead` 必須於 Step 2 平行派發 `@Security`：

| SC 代碼 | 範疇 | Hotfix 典型情境 |
|---------|-----|---------------|
| SC-01 | Token 時效 | Session 失效 / Token refresh 故障 |
| SC-02 | 金鑰外洩 | ENV 洩漏 / log 敏感資料 |
| SC-03 | strategyWeight 違規 | 數值異動未授權 |
| SC-04 | 資料刪除授權 | 刪除流程繞過 HITL |
| SC-05 | API 授權 | 端點未驗證 initData / JWT |
| SC-06 | 初始資料驗證 | Telegram initData / Webhook signature |
| SC-07 | 錯誤訊息洩漏 | 堆疊訊息含路徑 / 敏感 field |
| SC-08 | 併發原子性 | File-based 寫入無鎖 |
| SC-09 | 第三方套件 | 依賴套件已知漏洞 |
| SC-10 | Log 敏感資料 | access log 含 Token / PII |

**派發時機**：@Lead 接收 Hotfix 指令後，**評估階段**判定 SC 觸發 → 於派發診斷組時**同時**派發 @Security（平行非序列）

**與 @Reviewer 共用 REVIEW_CYCLE_LIMIT**：Hotfix 模式下 @Security 複審次數依 PROPOSAL-020 §防線 4 規則（與 @Reviewer 共用計數，預設 2 次）
```

#### 2.1 核心內容

````markdown
# Skill: Diagnostic Playbook（系統性診斷 SOP）

> 由 PROPOSAL_20260423_003 建立。Hotfix 或生產事故發生時，`@Backend` / `@Frontend` / `@Reviewer`（診斷組成員）**必須**參照本 SOP。
> 對齊 `RULES_DESIGN_GUIDE §十九` 三支柱之支柱 1（診斷組）。

## 一、適用時機

- **主要場景**：Hotfix Fast Lane 觸發（`emergency-shutdown-playbook §三`）
- **次要場景**：正常流程開發階段遇到難以定位的 bug（@Architect 可選用）
- **不適用**：純功能開發 / 設計階段 / 規則提案討論

## 二、五步診斷 SOP

### Step 1：收集現象（Evidence Gathering）

- [ ] 事故發生時間、觸發條件、受影響範圍
- [ ] 錯誤訊息 / 堆疊追蹤（stack trace）完整複製
- [ ] 相關日誌（系統 log / PM2 log / 應用 log）時間窗口 ±10 min
- [ ] User 回報的重現步驟（若有）

### Step 2：最小重現（Minimal Reproduction）

- [ ] 能在本機 / staging 重現？若不能 → 標示「生產限定」並搜集生產環境差異（環境變數 / 資料量 / 併發量）
- [ ] 縮減重現步驟到最小集合
- [ ] 確認重現穩定性（100% / 間歇性 / 首次）

### Step 3：二分法定位（Bisection）

- [ ] `git log --oneline -30 <涉及檔案>` 找可疑 commit
- [ ] `git bisect` 若必要（適用回歸型 bug）
- [ ] 讀取相關 `tech-stacks/*.md` 確認語言 / 框架行為
- [ ] 讀取相關 `skills/*.md`（如 `concurrency-guard-pattern` 若涉併發）

### Step 4：根因假設驗證（Root Cause Hypothesis）

- [ ] 列出 ≥ 2 個可能根因假設（避免單一假設誤導）
- [ ] 每個假設標示支持證據 + 反證
- [ ] 選擇證據最強的假設作為主根因
- [ ] 記錄被排除假設（供未來類似事故參考）

### Step 5：影響範圍評估（Impact Scoping）

- [ ] 同樣根因是否存在於其他模組？（grep / 靜態分析）
- [ ] 修復是否需同步調整相關單元測試？
- [ ] 是否涉及資料遷移 / migration？
- [ ] 是否為資安敏感（SC-01~SC-10 任一）→ 觸發 `@Security` 平行介入（對齐 §十九.C）

## 三、診斷組協作規範

**組成**：修復實作者（`@Backend` 或 `@Frontend`）+ `@Reviewer`

**三段式職責切換**：

| 階段 | 實作者角色 | @Reviewer 角色 |
|-----|-----------|---------------|
| 診斷 | 主導 Step 1-5 | **第二雙眼睛**：質疑假設、補盲點；**不做審查** |
| 實作 | 修復實作 | 不介入 |
| 審查 | 接收審查 | 回歸審查角色（`hotfix-checklist Step 2`） |

**關鍵分離**：
- 診斷階段 `@Reviewer` 不評判「程式碼品質 / 風格」，只評判「根因假設是否站得住腳」
- 避免思維混淆：診斷 = 探索未知；審查 = 驗證對錯
- 職責切換時 `@Lead` 發 Gate Check 明示：「診斷完成 → 進入實作 → 審查」三個階段轉換點

**共識達成**：診斷組需達成「主根因 + 修復範圍」書面共識，才進入實作。共識未達成 → `@Lead` 升級 User 裁決。
````
