## 三、提案內容

### 3.1 新建 `.agents/tests/agent-drift-simulator.mjs`

**雙模式設計**（避免必須仰賴 LLM API）：

#### Mode A：靜態模擬（commit-time 可運行）

無需 LLM 呼叫；模擬 50 步任務序列，檢查：
1. 每步 prompt 注入時 rules 引用穩定性（解析 prompt 中對 §s_state_anchor / §s05 等 section 的引用次數）
2. 「絕對禁止」條款 trigger 點分布（grep prompt 觸發樣本）
3. PENDING_ACTIONS.md 狀態錨點變化軌跡

#### Mode B：動態 LLM 驗證（週期性，需 API key）

執行 50 步真實對話，檢查：
1. **Persona 一致性**：每步輸出開頭是否仍含「我是 @<AgentName>」或對應職稱
2. **指令解析準確率**：給定 PENDING_ACTIONS [CURRENT_STAGE] 是否觸發正確的下一階段派發
3. **邊界遵循率**：刻意誘導（如要求 @Lead 直接寫 src/）下是否拒絕

### 3.2 drift_score 計算公式

```javascript
drift_score = (
  persona_stability * 0.4 +   // 0-1
  instruction_accuracy * 0.4 + // 0-1
  boundary_adherence * 0.2     // 0-1
)
// drift_score < 0.7 → exit 1（warning）
// drift_score < 0.5 → exit 2（error）
```

### 3.3 整合策略

- **commit-time**：僅執行 Mode A 靜態模擬（< 5 秒）
- **週期性**（每週 / 每提案執行後）：執行 Mode B（含 LLM 呼叫，~$1-5/次）
- **AUDIT_HISTORY.md**：5.1 細項評分記錄 `drift_score` 數值

### 3.4 RULES_DESIGN_GUIDE §十一 補強

於 §十一「提案執行後版本更新義務」新增 Phase E.1：「若提案修改 rules/*.md 結構（章節新增/拆分/合併），執行後 24 小時內必須執行 `agent-drift-simulator.mjs --mode static` 並紀錄 drift_score 變化」

#### Mode B（動態 LLM 50 步對話驗證）— ❌ Claude Code 平台不適用
不適用原因：
1. **API key 不可得**：Claude Code 執行環境不暴露原始 ANTHROPIC_API_KEY
2. **session 架構不符**：獨立 50 步對話 session 與 Claude Code「單一 assistant 連續對話」架構衝突
3. **成本控制困難**：$1-5/次使用用戶訂閱額度
4. **客觀性不足**：用 Claude 驗證 Claude rules 屬自我驗證
5. **最佳實施環境**：CI/CD 外部環境 + 獨立 API key + 不同廠商模型（如 GPT-4 / Gemini）

#### Mode B 未來延伸路徑
