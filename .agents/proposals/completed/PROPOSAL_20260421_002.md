## 一、問題描述

### 根因分類
**類型**：單一 Rules 全維度設計弱點（系統最弱環節）

### 問題陳述
`frontend.md` 是整個系統唯一總分低於 20 分的 Rules（18/25），
在五個審計維度中有三個維度得分為 3 分或以下：

| 維度 | 得分 | 主要問題 |
|------|------|---------|
| 1.1 Persona 具體化 | 4/5 | 業務脈絡描述通用，缺乏投資視覺化場景 |
| 1.2 負面約束與邊界 | 4/5 | 禁止條款語氣偏弱，API 前置條件缺失 |
| 1.4 規則密度 | 3/5 | DoD 12 條過多 + 模板嵌入 |
| 4.2 HITL 干預機制 | 3/5 | 觸發點最少（3 個），無自動化兜底，無數值化終止 |
| 5.1 長程任務一致性 | 4/5 | 三種防漂移機制均缺失或最弱 |

### 問題影響

**業務風險（高）**：
`@Frontend` 負責 Telegram Mini App 的 UI 實作，
是投資策略視覺化的唯一實作者。
若 `frontend.md` 的 HITL 與防漂移機制不足，
長程任務中可能出現以下業務損害：

1. hardcoded 顏色未使用 ThemeParams →
   投資策略視覺化畫面在 Telegram 深色模式下破圖

2. UI 三態（Loading / Success / Error）缺失 →
   策略載入失敗時無錯誤提示，
   使用者誤以為系統正常運作

3. initData 驗證缺失 →
   Telegram Mini App 安全性受損，
   非授權使用者可能存取投資策略資料

4. API 規格未確認即開始實作 →
   前後端規格不一致，導致多次重工

## 二、根因分析

### 直接根因
`frontend.md` 設計時缺乏以下四個關鍵機制：
1. 外部文件錨定（驗收依據未定義）
2. 數值化終止條件（重工無上限）
3. @Assistant 自動化兜底（無監控）
4. 足夠的 HITL 觸發點（僅 3 個）

### 系統根因
與 PROPOSAL-001 共享同一系統根因：
整個 Agent 系統缺乏「新增 Rules 前置審查機制」，
無法在 Rules 設計階段攔截 HITL 不足與防漂移缺失問題。

### 特殊根因：平台複雜性低估
Telegram Mini App 的平台限制
（ThemeParams、initData、安全區域）
導致 DoD 條目過多（12 條），
但設計時未考慮以 Skill 文件承接平台規範細節，
造成密度過高問題。

## 三、提案內容

### 修改項目一：任務目標章節補充業務脈絡

```markdown
// frontend.md 任務目標章節新增（約 +40 tokens）

在 InvestmentLineNotify 中，@Frontend 的核心業務場景：
1. 投資策略視覺化（策略清單、績效圖表、策略開關）
2. 量化訊號觸發通知的前端管理介面
3. Telegram Mini App 環境的 ThemeParams 深淺色適配

最高優先級的三個合規要求：
1. ThemeParams 強制使用（hardcoded 顏色零容忍）
2. initData 驗證（每次 Mini App 啟動必須驗證）
3. UI 三態完整性（Loading / Success / Error 缺一不可）
```

---

### 修改項目二：負面約束補強

```markdown
// frontend.md 禁止行為清單新增兩條約束

新增約束一：
「API 規格未經 @Architect 確認前，
 禁止開始任何 UI 實作，無例外。」

新增約束二：
「hardcoded 顏色（含 RGB、HEX、CSS 命名色）
 屬於零容忍違規，無豁免空間，
 發現即為 BLOCKER 強制退件。」

語氣升級（現有條款）：
「建議使用 ThemeParams」
→「必須使用 ThemeParams，違反即為 BLOCKER」
```

---

### 修改項目三：DoD 精簡（12 條 → 8 條以內）

```markdown
// frontend.md DoD 精簡方案

合併方向一：
「ThemeParams 使用」+「禁止 hardcoded 顏色」
→ 合併為：
  「ThemeParams 強制使用，
   禁止任何形式的 hardcoded 顏色（零容忍）」（1 條）

合併方向二：
「Loading 狀態實作」+「Error 狀態實作」+「Success 狀態實作」
→ 合併為：
  「UI 三態完整性：Loading / Success / Error
   三個狀態均有實作，缺一視為未完成」（1 條）

外部化方向：
Telegram Mini App 合規條目（原 3 條）
→ 移至 .agents/skills/telegram-miniapp-pattern.md
→ DoD 中以單條參照取代：
  「Telegram Mini App 合規：
   參照 .agents/skills/telegram-miniapp-pattern.md
   的合規 Checklist，全部通過方為完成」（1 條）

精簡後 DoD（8 條）：
- [ ] UI 三態完整性（Loading / Success / Error）
- [ ] ThemeParams 強制使用（hardcoded 顏色零容忍）
- [ ] Telegram Mini App 合規（參照 skill 文件）
- [ ] initData 驗證已實作
- [ ] API 規格與 @Architect 確認版本一致
- [ ] 響應式佈局適配 Telegram 視窗尺寸
- [ ] 錯誤訊息使用者可讀（非技術性 Error Code）
- [ ] 所有 AC 均已通過（以 draft_features.md 為依據）
```

---

### 修改項目四：外部文件錨定補充

```markdown
// frontend.md 任務定義章節新增錨定聲明（約 +25 tokens）

UI 驗收以 draft_features.md 的驗收標準（AC）為唯一依據。
任何 UI 功能的「完成」定義以 AC 為準，
@Frontend 不可自行判斷或放寬驗收標準。

API 消費規格以 @Architect 最新確認版本為唯一依據，
版本存放於 docs/api/ 目錄，
@Frontend 在實作前必須確認已讀取最新版本。
```

---

### 修改項目五：HITL 觸發點補強（3 個 → 6 個）

```markdown
// frontend.md HITL 觸發條件章節新增三個觸發點

新增觸發點一（前置條件）：
「API 規格未經 @Architect 確認即開始實作
 → 強制停止，通知 @Lead 補完 API 設計流程」

新增觸發點二（數值化終止）：
「UI 實作重工 ≥ 2 次仍不符合 AC
 → 強制暫停，升級 User 確認 AC 定義是否需調整」

新增觸發點三（安全強制）：
「initData 驗證缺失被 @Reviewer 標注為 BLOCKER
 → 強制修復，不可豁免，修復後需 @Reviewer 複審」

現有觸發點確認（語氣升級）：
「hardcoded 顏色 → 建議修正」
→「hardcoded 顏色 → 強制退件，無豁免空間」
```

### 修改項目六：數值化終止條件新增

```markdown
// frontend.md 新增數值化終止條件（約 +30 tokens）

終止條件一：
UI 實作重工 ≥ 2 次
→ 強制暫停，向 User 說明重工原因，
  等待 User 確認調整方向後才可繼續。

終止條件二：
@Reviewer 複審 ≥ 2 次仍有 BLOCKER
→ 強制暫停，升級 @Lead 介入，
  評估是否需要重新進行 API 設計或需求釐清。
```

### 修改項目七：@Assistant 自動化兜底新增

```markdown
// frontend.md 新增 @Assistant 偵測機制（約 +45 tokens）

@Assistant 巡邏將於下次收斂時自動偵測：

偵測項目一：
REVIEW_REPORT 中存在 frontend 相關 BLOCKER
且狀態為未修復
→ 產生 🔴 FRONTEND_BLOCKED 通知

→ 產生 🟡 FRONTEND_PENDING_REVIEW 通知

偵測項目三：
UI 重工記錄達 2 次但未升級 User
→ 產生 🔴 FRONTEND_OVERRUN 通知
```
