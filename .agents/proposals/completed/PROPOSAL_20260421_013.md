## 一、問題描述

### 根因分類

**類型**：豁免行為缺乏記錄機制（MT-05）

### 問題陳述

系統各 Agent 的 Rules 定義了多項
「禁止」與「需升級」條件，
但缺乏「當這些條件被豁免時，
如何記錄豁免原因與授權來源」的規範。

#### 具體問題場景

```
場景一：@Consultant 建議修改 strategyWeight，
@Lead 基於緊急情況授權例外執行。
現況：授權僅存在於當次對話記憶，
      對話結束後豁免記錄消失，
      @Retro 審計時無法識別「這是例外」
      還是「Rules 被違反」。

場景二：@Architect 設計觸發複雜度門檻
（PROPOSAL-009 定義），
@Lead 評估後決定不升級 User 直接推進。
現況：@Lead 的豁免決策無記錄，
      若後續出現問題無法追溯授權依據。

場景三：@Backend 執行超過資料異動門檻的操作，
@Lead 已口頭授權但未書面記錄。
現況：口頭授權在多輪對話後難以追溯，
      @QA 或 @Reviewer 無法確認授權存在。

共同問題：
豁免行為發生在「規則層」與「執行層」之間的灰色地帶，
缺乏系統級的豁免記錄機制，
導致：
① @Retro 審計時無法區分「違規」與「授權豁免」
② 豁免行為累積後形成隱性規則漂移
③ User 無法在事後審查豁免歷史
```

### 問題影響層級

- 影響範圍：所有涉及豁免授權的 Agent 行為
- 風險分類：審計可追溯性
  （豁免記錄缺失導致 @Retro 審計結果
  無法區分「正常豁免」與「Rules 違反」）
- 風險等級：🟡 中風險

## 二、根因分析

### 直接根因

系統設計時聚焦於「正常流程」的規範，
未預期「豁免流程」需要獨立的記錄機制。

### 系統根因

豁免行為本質上是「臨時性規則例外」，
若無記錄機制，豁免行為會逐漸成為
「不受規則約束的慣例」，
最終侵蝕整個 Rules 系統的約束力。

### 連結分析

PROPOSAL-004 全局阻斷條件三（安全邊界觸碰）
是最後防線，本提案的豁免記錄機制
是「安全邊界觸碰前的授權確認與追蹤層」，
兩者共同構成縱深防禦架構的中間層。

## 三、提案內容

### 豁免記錄標準格式（全系統統一）

```markdown
// EXEMPTION_LOG 標準格式

【豁免記錄】
豁免編號：EX-{YYYYMMDD}-{序號}（如：EX-20260421-001）
豁免時間：{對話時間戳或對話序號}
申請 Agent：@{Agent}
豁免規則：{被豁免的具體規則條文來源，如 backend.md §資料異動門檻}
豁免原因：{具體業務原因}
授權來源：@Lead 授權 / User 明確授權
授權記錄：「{授權者的原始授權語句}」
影響範圍：{本次豁免涉及的資料或系統範圍}
有效期：{單次有效 / 本次 Sprint 有效}
```

豁免記錄寫入位置：
`PENDING_ACTIONS.md` 中的
「豁免記錄」區塊（由 @Lead 統一維護）

```markdown
// 修改位置：lead.md 豁免授權章節（新增）

## 豁免授權與記錄機制

### 豁免授權流程

當任何 Agent 申請豁免其 Rules 中的
「禁止」或「需升級」條件時：

Step 1：Agent 向 @Lead 提出豁免申請，
說明豁免規則、原因、影響範圍

Step 2：@Lead 評估後決策：- 核准：說明授權範圍與有效期 - 拒絕：說明拒絕原因，維持原規則

Step 3（核准時）：@Lead 必須執行豁免記錄：
將豁免記錄以 EXEMPTION_LOG 格式
寫入 PENDING_ACTIONS.md 豁免區塊

Step 4：豁免行為完成後，
@Lead 在豁免記錄上標注「已執行」

### 豁免授權邊界

以下條件的豁免必須升級至 User 確認，
@Lead 無權單獨授權：

1. strategyWeight 任何數值異動
2. .agents/ 原始 Rules 文件直接修改
3. 任何金鑰 / Token 相關操作
4. 破壞性架構變更（PROPOSAL-009 定義）

### 豁免累積警示

當 PENDING_ACTIONS.md 豁免區塊
累積 ≥ 5 筆未歸檔記錄時，
@Lead 必須通知 @Retro 執行豁免審計，
評估是否需要將高頻豁免場景
正式納入 Rules 更新。
```

### consultant.md 修改項目

```markdown
// 修改位置：consultant.md 豁免申請章節（新增）

## 豁免申請規範

當 @Consultant 評估認為當前情況
需要豁免 Rules 中的禁止條件時：

申請流程：

1. 明確說明豁免的具體規則條文
2. 提供業務緊急性說明
   （為何無法按正常流程執行）
3. 說明豁免的影響範圍與風險評估
4. 等待 @Lead 或 User 的明確授權回應

禁止：
未獲得明確授權回應前，
不得以「情況緊急」為由自行執行
被豁免的操作。

豁免有效期：
@Consultant 申請的豁免
預設為「單次有效」，
不得延伸至後續任務。
```

## 七、備註

- 本提案是整個提案體系中
  「縱深防禦架構」的中間層：
  Rules 禁止條文（各 Agent Rules）
  → 豁免記錄機制（本提案）
  → 全局緊急阻斷（PROPOSAL-004）
  三層共同構成完整的安全邊界保障。

- EXEMPTION_LOG 豁免編號格式
  EX-{YYYYMMDD}-{序號} 設計為全系統唯一，
  方便 @Retro 審計時按時間序追蹤豁免歷史。

- 豁免累積 ≥ 5 筆觸發 @Retro 審計的機制
  是本提案最具長期價值的設計：
  高頻豁免場景代表 Rules 與業務現實的落差，
  應定期轉化為 Rules 正式更新，
  避免豁免記錄成為「影子規則系統」。

- 4 份文件合計新增約 +220 tokens，
  均為非 AlwaysOn 文件，Token 預算寬鬆。
  lead.md 需特別注意總 Token 是否接近上限
  （lead.md 為核心文件，歷次修改累積較多）。
