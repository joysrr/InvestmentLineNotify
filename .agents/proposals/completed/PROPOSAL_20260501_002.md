# PROPOSAL_20260501_002：Iron Themes — 跨切不可變治理

## 基本資訊

- 提案編號：**PROPOSAL_20260501_002**
- scope：**framework**
- 提案日期：2026-05-01
- tier：**full**（影響 frontmatter schema + 2 validator + 13 rules + 5-6 新 iron-rules/ 檔 + ADR-0037）
- priority：**P3**（架構升級；ROI 有限；但永續性收益高）
- 觸發：PROPOSAL_20260501_001 收尾發現 11/13 需 exception；4 方案分析後選 Option E（架構 + 永續性最佳）

## 一、問題（架構視角）

### 1.1 真正的 SoT 違反

當前 15 個 `immutable="true"` sections 散落於 8 rules，含**真實重複**：

| 跨切主題                             | 散布處                                                                                | 嚴重度                     |
| ------------------------------------ | ------------------------------------------------------------------------------------- | -------------------------- |
| **機讀產出物 5 條鐵律**              | review.md s_output_strict / qa.md s_output_strict / security.md s_output_strict       | 🔴 同名同內容 3 處複製     |
| **資料刪除 + strategyWeight 零容忍** | backend.md s06 / consultant.md s07 / security.md s02 / lead.md s11 / system-prompt.md | 🔴 5 處散布；變更要動 5 檔 |
| **平行審查職責互斥**                 | reviewer.md s10 / security.md s02 + s07                                               | 🟡 2-3 處                  |

修改任一條鐵律 → 必同步多處；漏改即漂移。當前無機械化偵測（schema-validator 只查單檔 immutable diff，不查跨檔一致性）。

### 1.2 immutable 是 convention 不是 structural

當前不可變性靠**屬性宣告** `immutable="true"` + reviewer 自律。風險：

- 開發者不察覺 immutable 屬性 → 順手改了
- schema-validator 只能查 commit-time diff；不能阻止「先改後 commit」
- 跨檔重複的 immutable 被改一處沒改另一處 → silent drift

### 1.3 immutable 與 mutable 在同檔混雜

- 同一 rule.md 內既有 mutable 操作細則又有 immutable 鐵律
- token budget 計算時兩者混算
- review 時兩者用同套流程（但本應有不同嚴格度）

## 二、設計：Iron Themes（Option E 全細節）

### 2.1 核心概念

把跨切的不可變鐵律從 `rules/*.md` 抽出為 **first-class artifact**：`.agents/iron-rules/<theme>.md`。

每個 theme 是**單一職責**的不可變鐵律集合；跨多 Agent 共用 → 真正 SoT。

Rule frontmatter 用 `applies_iron_themes: [...]` 宣告引用；context loader 在注入 rule 時自動載入相關 themes。

### 2.2 Theme 清單（依 §1 跨切分析）

#### 主要跨切 themes（≥ 2 rules 共用；強烈建議抽）

| Theme                            | 路徑                                         | 共用 rules                                             | 估計 size   |
| -------------------------------- | -------------------------------------------- | ------------------------------------------------------ | ----------- |
| **machine-readable-output**      | `iron-rules/machine-readable-output.md`      | review / qa / security                                 | ~250 tokens |
| **data-deletion-zero-tolerance** | `iron-rules/data-deletion-zero-tolerance.md` | backend / lead / security / consultant / system-prompt | ~200 tokens |
| **parallel-review-boundary**     | `iron-rules/parallel-review-boundary.md`     | reviewer / security                                    | ~180 tokens |

#### Solo themes（單 rule 但結構性高；可選抽）

| Theme                            | 共用 rules | 抽出收益                                |
| -------------------------------- | ---------- | --------------------------------------- |
| **state-anchor**                 | lead       | structural immutability + audit clarity |
| **assistant-block-policy**       | assistant  | 同上                                    |
| **hci-global-summary**           | assistant  | 同上                                    |
| **auditor-rubric-iron**          | auditor    | 同上                                    |
| **exemption-authority-boundary** | lead       | 同上（被多檔引用，可能升級為跨切）      |

決策：**Phase A 先抽 3 主要跨切；Phase F 視效果決定是否續抽 solo**。

#### 不抽（保留 inline）

各 Agent 的「核心禁止條款 (Anti-Rules)」內容因 Agent 而異（consultant 唯讀 / qa 職責隔離 / reviewer 退件上限 etc.）；雖結構同模式但內容不重複，無 SoT 違反；保留 inline 不抽。

### 2.3 Iron Theme 檔案結構

```yaml
# iron-rules/machine-readable-output.md frontmatter
---
theme_id: machine-readable-output
file_type: iron_theme    # 新 type；ADR-0022 schema 升級
version: v1.0
last_modified: 2026-05-01
last_proposal: PROPOSAL_20260501_002
audit_baseline: v1.0
immutable: true          # 整檔不可變
applies_to: [reviewer, qa, security]   # 哪些 Agent rules 引用本 theme
modification_policy: |
  本檔變動必經提案流程；commit-time validator 檢查 diff；
  違反觸發 system-prompt.md §全局緊急阻斷條件三
---

# Iron Theme: Machine-Readable Output

> 跨切不可變鐵律；review-class agents 共用。

## 5 條鐵律（保留原文；不可改詞）

1. **零對話原則** ...
2. **符號絕對錨點** ...
3. **嚴格模板對齊** ...
4. **違反處理** ...
5. **純淨度自檢** ...
```

### 2.4 Rule 引用機制

```yaml
# rules/security.md frontmatter
---
agent_id: security
applies_iron_themes:
  - machine-readable-output # 替代 §s_output_strict
  - data-deletion-zero-tolerance # 替代 §s02 部分
  - parallel-review-boundary # 替代 §s02 / s07 部分
---
```

Rule 內保留 1-行入口指向 theme：

```markdown
<section id="s_output_strict_ref" priority="critical">
## 機讀產出物強制規範

**完整 5 條鐵律**：`iron-rules/machine-readable-output.md`（不可變主題；本 Agent 適用）

</section>
```

或更簡：直接從 rule 移除該 section，由 frontmatter `applies_iron_themes` 隱式注入。

**選擇**：保留 1-行入口 section（方案 A）。理由：

- 維持 rule 自足性（讀者看 rule 知道有 theme 存在）
- schema-validator section count 不變
- 入口 section priority=critical（不可降級）

### 2.5 Validator 升級

#### schema-validator

- 識別 `applies_iron_themes` frontmatter；驗證每個 theme 存在
- 計算 token：rule 自身 + 引用的 theme 內容（取 union；多 rule 共用 theme 不重複算）
- Budget 套用：rule 自身 ≤ agent_rule budget（嚴格 1000）；theme 不計入 rule budget（因 theme 是共用資產）

#### iron-theme-validator（新增）

- 掃 `iron-rules/` 所有檔案
- 驗證 theme 內容自上次 commit 是否有 diff（無提案則 fail）
- 驗證 `applies_to` 列出的 rules 都有 `applies_iron_themes` 引用本 theme（雙向一致）
- 計入 `run-all.sh` 第 13 個 validator

#### rule-token-budget-validator

- Rule budget = 自身 mutable bytes（theme 內容由 iron-theme-validator 另算）
- 簡化：移除「exception 機制」（理論上不再需要；只在極端情境保留）

### 2.6 Context loader 整合

當 @Lead 注入 `rules/security.md` 給子 Agent 時：

1. 讀 rule 主檔
2. 讀 `applies_iron_themes` 列表
3. 自動載入對應 `iron-rules/*.md`
4. 整體作為 prompt context

實作：`scripts/lib/rule-loader.mjs`（新建）；@Lead 派發前 require 此 lib。

**達 budget 結果**（Phase A 抽 3 主要 themes 後）：

- 達嚴格 1000 budget：3/13（system-prompt + consultant + 約 reviewer）
- 仍超 budget：10/13（但已從 11 降至 10；改善有限）

⚠️ **單獨 E 不是萬靈丹**：仍有 7-10 rules 含「mutable content 本身就 heavy」（retro/planner/frontend/architect/qa/backend/security/lead/assistant 等）。

但 E 達成的核心價值：

- ✅ 15 immutable sections → ~6 themes（60% 數量縮減）
- ✅ 跨切重複（output-strict 3 處 / data-deletion 5 處 / parallel-arbitration 2 處）100% 消除
- ✅ structural immutability（檔案 + 路徑）強過 attribute convention
- ✅ Cross-cutting concerns 升為 first-class artifact（DDD shared-kernel 模式）
- ✅ 修改鐵律時 git diff 集中於 `iron-rules/` 一處；audit 痕跡清晰

剩餘 over-budget 是「mutable content 重」的合理問題；exception flag 機制保留作該情境的 escape hatch（語意更清晰：exception = mutable 太大，不再混 immutable）。

### 2.8 與 ADR-0036 關係

ADR-0036（4 patterns）規範**怎麼縮 mutable content**；本提案 / ADR-0037 規範**immutable 怎麼治理**。兩者正交：

| 軸             | 方案              | 範圍                                  |
| -------------- | ----------------- | ------------------------------------- |
| Mutable 縮減   | ADR-0036          | rule 內 mutable content 的 4 patterns |
| Immutable 治理 | 本提案 / ADR-0037 | 跨切 immutable 抽至 themes            |

採納本提案後 ADR-0036 仍生效；token_budget_exception 仍保留（但用途變成「mutable 自身過 budget」的明確情境，不再混 immutable）。

## 四、風險（架構視角）

| 風險                                      | 緩解                                                                                                                  |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| context loader 複雜度                     | 提供標準 lib；@Lead 派發前必呼叫；schema-validator 強制                                                               |

| theme 過度切細                            | 4 條判定原則：(1) ≥ 2 rules 共用 OR (2) > 200 tokens immutable content OR (3) 跨 Agent 安全邊界 OR (4) ≥ 3 個禁止鐵律 |

| Rule 自足性破壞（讀者看 rule 不知 theme） | 保留 1-行入口 section（priority=critical）；frontmatter `applies_iron_themes` 顯式宣告                                |
| Solo themes 抽出 ROI 低                   | Phase H 評估；可選抽；不影響 Phase A-G 主體價值                                                                       |

## 註：Theme 判定原則（採納後寫入 ADR-0037）

抽出為 iron theme 的條件（任一）：

1. **跨切共用**：≥ 2 rules 含同名同內容 immutable section
2. **大尺寸**：單一 immutable section > 200 tokens（脫離 mutable budget 影響大）
3. **跨 Agent 安全邊界**：涉及 strategyWeight / 資料刪除 / 金鑰 / 鐵律性禁止
4. **鐵律密度**：≥ 3 個獨立的「絕對禁止」/「絕對不可」條款

不抽（保留 inline）：

- 內容因 Agent 而異的「核心禁止條款 (Anti-Rules)」（結構同模式但內容不重複）
- 與 rule mutable 內容緊密耦合的 immutable（抽出後 mutable 失語意）
