# PROPOSAL_20260423_016：導入 ADR Pattern — 規則去 PROPOSAL 化

## 一、問題描述

`.agents/rules/` + `skills/` + `tasks/` 中**累計 471 處 PROPOSAL_XXX 引用**，其中：

- **Type A**（frontmatter audit trail）：~30 處；低可攜性影響
- **Type B**（段落 inline 標頭「（依 PROPOSAL_XXX）」）：~350 處；中等影響
- **Type C**（規則條款嵌入提案編號，語義依賴）：~90 處；🔴 高可攜性影響

每次 LLM 任務平均讀到 ~40 PROPOSAL 引用；其中 ~7 處 Type C 需實際展開 proposals/ 才能理解規則本意。

### 核心風險

1. **LLM 語義負擔**：讀規則需同時展開多份歷史提案
2. **可攜性斷鏈**：新專案搬運時 471 處引用若不帶 proposals/ 即失效
3. **維護耦合**：改動一條規則需同步維護多處 PROPOSAL 引用
4. **違反產業範式**：Linux Kernel / Kubernetes / IETF RFC 等均採「規則 vs 歷史分離」架構

## 二、根因分析

- **歷史堆疊**：框架自 2026-04-21 起快速演進；每條規則都標註「依 PROPOSAL_XXX」作為設計溯源
- **缺決策層**：未建立 ADR（Architecture Decision Records）機制承接「為何這樣設計」
- **單一審計軌跡設計**：PROPOSAL 同時承擔「決議記錄」+「設計說明」+「驗收軌跡」三重角色

## 三、提案內容

### 3.1 三層職責清晰分離

| 層         | 位置                                                            | 用途（WHAT/WHY/HOW）     | LLM 載入時機      |
| ---------- | --------------------------------------------------------------- | ------------------------ | ----------------- |
| **規則層** | `rules/*.md` + `RULES_DESIGN_GUIDE.*.md` + `skills/` + `tasks/` | 當前行為規範（**WHAT**） | 每任務必讀        |
| **決策層** | `decisions/ADR-XXXX.md`                                         | 為何這樣設計（**WHY**）  | 需要時才讀        |
| **歷史層** | `proposals/completed/*.md`                                      | 官方決議審計軌跡         | 審計 / 溯源時才讀 |

### 3.2 ADR 標準格式

```markdown
---
adr_id: ADR-XXXX
title: <短標題>
status: Accepted | Superseded | Deprecated
date: YYYY-MM-DD
supersedes: [ADR-YYY]
superseded_by: [ADR-ZZZ]
related_proposals: [PROPOSAL_XXX, ...]
referenced_by: [rules/lead.md#section, ...]
---

# ADR-XXXX: <title>

## Status

Accepted | Superseded | Deprecated (YYYY-MM-DD)

## Context

<問題情境；當時面臨什麼決定>

## Decision

<選擇了什麼方案>

## Consequences

- 正面：<影響>
- 負面：<tradeoffs>

## Alternatives Considered

<替代方案（可選）>

## Related Proposals

- PROPOSAL_XXX（原始提案）
- PROPOSAL_YYY（擴充提案）

## Referenced By

- rules/lead.md §s_state_anchor
- rules/assistant.md §巡邏
```

### 3.3 執行批次

| 批次  | 內容                                                          | 預估   | Review 節點  |
| ----- | ------------------------------------------------------------- | ------ | ------------ |
| **1** | 提案立案 + `decisions/` 基礎設施 + generator + validator      | 1.5 hr | 結構檢視     |
| **2** | Type B 機械清理（~200 處 inline 標頭 → 檔案底部 footer）      | 2.5 hr | 抽查誤殺     |
| **3** | 識別 + 撰寫 ~30 個 ADRs（最核心；涵蓋 ~90 Type C 決策）       | 5 hr   | ADR 草稿全集 |
| **4** | 重構 `rules/*.md` 13 檔（Type C 條款改為自我解釋 + ADR 連結） | 3 hr   | 抽驗 5 條    |
| **5** | 重構 `skills/*.md` + `tasks/*.md`（選有 Type C 引用者）       | 2 hr   | 抽驗         |
| **6** | adr-validator + 文件更新 + version bump（v5.1 → v6.0）+ 關閉  | 2 hr   | 最終驗收     |

**總計**：~16 小時工作 + 6 個 review 節點

### 3.4 保留策略

- **Type A frontmatter `last_proposal`**：保留（作 audit trail）
- **歷史 `proposals/completed/*.md`**：**不改寫**（60+ 檔案作為官方決議記錄）
- **PROPOSAL_INDEX §🔗 意圖繼承**：保留（可升級為指向 ADR）
- **新提案起**：frontmatter 加 `generates_adr: true/false` 標示是否產生 ADR

### 3.5 新規則（立案時 SOP 更新）

`retro.md §s06` 新增：

- 提案起草時評估「是否產生 ADR」
- 產生 ADR 的提案 Phase G 必含「寫 ADR」步驟
- Lite Proposal 通常不產 ADR（除非新增不可逆決策）

### 4.2 質化

- 決策追溯性提升（ADR 專門記錄 context/consequences）
- 未來 ADR 可獨立更新（superseded_by 鏈路）
