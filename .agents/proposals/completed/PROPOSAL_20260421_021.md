## 一、問題描述

### 根因分類

**類型**：Rules 結構化程度不足（LLM 注意力 + 機器可讀性雙重限制）

### 問題陳述

User 提出的原始觀察（部分與 PROPOSAL-020 後的現況需再校準）：

#### 問題一：指令偏移（Instruction Drift）

Rules 累積至 ~24,000 tokens（13 份文件）後，長對話情境下 LLM 對中段條款的注意力下降。現有 `##` 章節標題 + `<!-- END: xxx -->` 註解僅為視覺標記，**對 LLM 的 attention 強度偏弱**（Anthropic 官方文件明確建議使用 XML 標籤）。

#### 問題二：Token 密度不足（部分）

敘事性說明（業務脈絡、設計意圖、絕對禁止語氣）有其存在必要，但**章節 metadata**（版本、觸發條件、引用關係、工作流階段）仍以散文或表格描述，缺乏結構化表達。

#### 問題三：跨檔案 metadata 無統一 schema

現況各 rules 頂部僅有：

```yaml
---
trigger: manual
---
```

加 PROPOSAL-019 的版本標頭：

```
***
版本：v1.x
最後修改：2026-04-21
修改提案：PROPOSAL-xxx
修改摘要：...
審計基準：v1.0
***
```

但**缺少 agent 身份、workflow 階段、引用關係、category** 等結構化欄位，未來若開發自動化工具（User Q4 提及「可以開發程式專門維護」）缺乏 schema 基礎。

#### 問題四（User Q2 強制要求）：格式應統一

目前部分 rules 用 YAML frontmatter、部分僅用 markdown `##` 標題，**格式不一致**。User 明確要求「統一規範格式要相同」，避免混用造成混亂。

### 問題影響層級

- **主要問題（問題一）**：每次對話 LLM 執行準確度受影響
- **次要問題（問題二~四）**：長期可維護性、自動化工具開發阻礙
- 風險等級：🟡 中（非立即危害，屬系統演進品質）

## 二、根因分析

### 直接根因

Rules 早期設計採 markdown 為唯一格式（PROPOSAL-003 §一「Rules 標準結構」確立六章節規範）。隨著系統演進（現有 22 份 PROPOSAL DONE），metadata 需求逐漸浮現（版本標頭、引用關係、觸發條件、workflow 整合等），但仍以散文或表格描述，未提煉為 schema。

### 系統根因

缺乏**「文件結構的兩層設計原則」**：

1. **人類可讀層**（markdown body）：保留完整說明、業務脈絡、設計意圖、語氣鐵律
2. **機器可讀層**（YAML frontmatter + XML section 標記）：提供 LLM 注意力錨點 + 未來工具使用的結構化資訊

### User 選擇的解決方向

User 決策採 **方案 C + F 組合**（Q1 選項）：

- **方案 C**：每份 rules 擴充 YAML frontmatter 為完整 metadata schema（機器可讀層上半）
- **方案 F**：每份 rules body 章節以 `<section>` XML 標籤包覆（機器可讀層下半，對齊 Anthropic 建議）

兩者**並存**於同一份 markdown 文件，**不破壞既有 body 內容**（保留人類可讀性、不推翻既有 22 份 PROPOSAL 的敘事成果）。

User 同時要求**一次到位**（不分階段試點）+ 產出 `RULES_METADATA_SCHEMA.md`（給 User 與未來工具使用的格式說明書）。

## 二、YAML Frontmatter Schema

### 2.1 共用欄位（所有 Rules 必備）

| 欄位               | 型別        | 必要 | 範例                                        | 說明                                 |
| ------------------ | ----------- | ---- | ------------------------------------------- | ------------------------------------ |
| `agent_id`         | string      | ✅   | `project_lead`                              | 小寫底線格式；`system_prompt` 為特例 |
| `agent_name`       | string      | ✅   | `@Lead`                                     | 顯示用                               |
| `file_type`        | enum        | ✅   | `agent_rule` / `always_on` / `design_guide` | 區分三類                             |
| `version`          | semver-like | ✅   | `v1.1`                                      | 對齊 PROPOSAL-019                    |
| `last_modified`    | date        | ✅   | `2026-04-21`                                | ISO 格式                             |
| `last_proposal`    | string      | ✅   | `PROPOSAL-021`                              | 最近影響此檔的提案                   |
| `audit_baseline`   | version     | ✅   | `v1.0`                                      | 上次 `@Retro` 審計時版本             |
| `trigger`          | enum        | ✅   | `manual` / `always_on`                      | 載入時機                             |
| `token_budget_ref` | string      | ⭕   | `TOKEN_ONDEMAND_LIMIT`                      | 引用 §十四                           |

### 2.2 Agent 專屬欄位（`file_type: agent_rule`）

| 欄位              | 型別   | 必要 | 範例                    | 說明                            |
| ----------------- | ------ | ---- | ----------------------- | ------------------------------- |
| `workflow_stages` | list   | ⭕   | `[審查, 資安審查]`      | 此 Agent 在 Workflow 參與的階段 |
| `reports_to`      | string | ⭕   | `@Lead`                 | 回報對象                        |
| `interacts_with`  | list   | ⭕   | `[@Reviewer, @Backend]` | 協作 Agent                      |
| `produces`        | list   | ⭕   | `[SECURITY_REPORT.md]`  | 產出物                          |
| `references`      | map    | ⭕   | 見下文                  | 引用其他文件                    |
| `constraints_ref` | map    | ⭕   | 見下文                  | 引用 §十四 參數                 |

### 2.3 引用欄位格式（`references` / `constraints_ref`）

```yaml
references:
  system_thresholds: RULES_DESIGN_GUIDE.md#十四
  notification_standard: RULES_DESIGN_GUIDE.md#九
  parallel_review: lead.md#平行審查與衝突仲裁規則

constraints_ref:
  review_cycle_limit: !ref RULES_DESIGN_GUIDE.md#REVIEW_CYCLE_LIMIT
  token_budget: !ref RULES_DESIGN_GUIDE.md#TOKEN_ONDEMAND_LIMIT
```

`!ref` 為專屬語法標記，表示該值應從目標位置動態讀取。
（目前人工維護；未來工具可自動解析驗證）

## 三、XML Section 標籤 Schema

### 3.1 標籤基本語法

```html
<section id="task_goal" priority="normal">
  ## 任務目標 （markdown 內容）
</section>
```

### 3.2 標籤屬性

| 屬性        | 型別    | 必要 | 值                                      | 說明                                         |
| ----------- | ------- | ---- | --------------------------------------- | -------------------------------------------- |
| `id`        | string  | ✅   | `task_goal`、`parallel_review`          | 小寫底線，每份 rules 內唯一                  |
| `priority`  | enum    | ✅   | `critical` / `high` / `normal` / `info` | LLM 注意力權重提示                           |
| `immutable` | boolean | ⭕   | `true`                                  | 標記此章節需透過提案才能修改（如零容忍條款） |
| `cross_ref` | list    | ⭕   | `["lead.md#平行審查"]`                  | 跨檔案關聯                                   |

### 3.3 優先級使用指引

- `critical`：全局阻斷條款、零容忍禁止、豁免授權邊界
- `high`：核心工作流、HITL 觸發條件、DoD 自評機制
- `normal`：一般規範、審查準則、產出物定義
- `info`：補充說明、備註、維護規範
