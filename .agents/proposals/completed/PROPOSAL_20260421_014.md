## 一、問題描述

### 根因分類
**類型**：設計意圖缺乏說明（QW-10）

### 問題陳述
`reviewer.md` 定義了複審上限機制
（同一任務最多複審 N 次），
但缺少對該上限設計意圖的說明，
導致 @Reviewer 在執行時
可能誤解上限的目的——
將「複審上限」理解為「品質妥協許可」，
而非「流程保護機制」。

#### 具體問題條文
```
現況：
「同一任務最多複審 3 次，
 超過上限後升級 @Lead 處理。」

缺失：
① 未說明為何設定 3 次上限
   （避免無限複審迴圈 vs. 品質妥協？）
② 未說明「升級 @Lead 後」@Lead 應如何處理
③ 未說明達到上限但任務仍未通過時，
   是否可以強制標注「有條件通過」

影響：
@Reviewer 在第 3 次複審時
可能因為「反正到上限了」
而降低審查標準，
違背複審上限作為「流程保護」
而非「品質妥協許可」的設計意圖。
```

### 問題影響層級
- 影響範圍：@Reviewer 每次執行複審判斷
- 風險分類：設計意圖執行偏差
  （規則存在但被誤解導致行為偏差，
   比規則缺失更難被 @Retro 審計識別）
- 風險等級：🟢 低風險（P3）
  （現有上限機制仍有保護作用，
   意圖說明為品質強化而非補漏）

## 二、根因分析

### 直接根因
Rules 設計時傾向於「What（做什麼）」
的規範，缺少「Why（為何如此設計）」
的說明。
複審上限是少數需要設計意圖說明的機制之一，
因為上限數字本身容易被誤解為品質許可。

### 系統根因
缺乏「Rules 設計意圖說明規範」，
PROPOSAL-003（RULES_DESIGN_GUIDE）
建立後應將本提案的處理方式
作為「機制設計意圖說明」的標準範例。

## 三、提案內容

### 修改項目：複審上限設計意圖補充

```markdown
// 修改位置：reviewer.md 複審上限章節

// 修改前
同一任務最多複審 3 次，
超過上限後升級 @Lead 處理。

// 修改後
## 複審上限機制

### 上限設定
同一任務最多複審 3 次。

### 設計意圖（重要）
複審上限的設計目的是：
「防止審查流程陷入無限迴圈，
 保護系統執行效率」。

上限【不代表】：
- 第 3 次複審可以降低審查標準
- 達到上限即視為品質通過
- @Reviewer 可以因「次數已到」
  而接受不符合 DoD 的任務

上限【代表】：
- 同一任務反覆複審 ≥ 3 次是異常信號
- 問題根因可能超出 @Backend / @Frontend
  的執行層，需要更高層級介入判斷

### 達到上限後的處理流程

Step 1：第 3 次複審完成後，
        無論結果如何，
        @Reviewer 向 @Lead 輸出複審上限報告：

```
【複審上限報告】
任務：{任務描述}
複審次數：3 / 3（已達上限）
當前狀態：✅ 通過 / ❌ 仍有 {n} 項未解決
未解決項目：{具體描述或「無」}
根因推測：{執行問題 / 需求不明確 / 設計問題 / 其他}
建議處理：{具體建議}
```

Step 2：@Lead 依複審上限報告決策：
        - 若仍有未解決項目：
          → 評估根因，決定是否升級 User
          → 或重新拆分任務後重啟流程
        - 若已通過：
          → 記錄「歷經 3 次複審通過」
            於 PENDING_ACTIONS.md，
            標注為需 @Retro 關注的品質信號

Step 3：禁止處理方式：
        @Lead 不得以「已達複審上限」
        為由強制標注未通過任務為通過。
        品質標準不因複審次數而降低。

### 複審次數重置條件
以下情況視為新任務，複審次數重置為 0：
- @Lead 決定重新拆分任務後重啟
- 任務需求描述有實質性變更
  （非小幅修正）
- @Architect 重新輸出技術規格
```
