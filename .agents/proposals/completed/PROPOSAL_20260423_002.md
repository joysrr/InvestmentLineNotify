## 一、問題描述

### 1.1 User 真實案例（2026-04-23 痛點）

> 「某專案都快結案了，在做美化，後面才由使用者發現提議導入[現成套件]，如果由 Agents 在分析時就能夠發現，會減少大量的開發時間。」

### 1.2 當前流程缺口

現行 Workflow 從 `draft_features.md` → `@Architect` API Spec → `@Backend` / `@Frontend` 實作，**無任何階段強制執行「此功能是否已有成熟套件 / 平台原生方案」的檢索**。

| Agent 現行 DoD                 | 是否包含「生態掃描」                        | 缺口                     |
| ------------------------------ | ------------------------------------------- | ------------------------ |
| `@Planner` User Story          | ❌ 僅描述「做什麼」，不問「是否已存在」     | 早期介入點缺失           |
| `@Consultant` 領域審查         | ❌ 僅審業務邏輯衝突，不涉技術生態           | 角色邊界正確，但留下空白 |
| `@Architect` API Spec          | ⚠️ 設計內部架構，未強制「外部套件優先評估」 | **關鍵缺口**             |
| `@Backend` / `@Frontend` 實作  | ❌ 依 Spec 實作，不重新質疑選型             | 太晚                     |
| `@Reviewer` / `@Security` 審查 | ❌ 審既有程式碼，不審「應該用什麼」         | 太晚                     |

### 1.3 三層風險

| 風險層級     | 具體損失                                                           |
| ------------ | ------------------------------------------------------------------ |
| **工時損失** | 自建 2-5 天功能 vs 採納套件 30 分鐘 → 每次重工成本 3-10x           |
| **維護負擔** | 自建程式碼需長期維護 vs 社群套件社群維護 → 技術債累積              |
| **功能深度** | 自建版本常缺 edge case 處理 vs 成熟套件已被社群驗證 → 產品品質落差 |

### 1.4 為何 LLM 知識截止是額外限制（非藉口）

- Claude 知識截止為 Jan 2026；快速演進的套件生態（NPM 每月新版 / PyPI 週更新）超出此時點的資訊不在 LLM 內部知識
- 若 LLM 單獨推薦套件可能過時 → 必須由 **User 透過 WebSearch / NPM / PyPI 官方頁 cross-check**
- 此為強制 HITL 設計的原因（非可選 Bypass）

### 1.5 量化影響

| 問題維度             | 當前狀態                                     |
| -------------------- | -------------------------------------------- |
| 前置生態掃描覆蓋     | 0%（無任何 DoD 項目）                        |
| 重工風險偵測         | 僅靠 User 事後察覺（如本痛點案例）           |
| 套件評估歷史保留     | 無；每次任務重頭來                           |
| 跨功能套件決策一致性 | 無共同記錄；不同功能可能採不同套件解同類問題 |

## 十八、Prior Art Scan 強制程序（依 PROPOSAL_20260423_002）

| 條件 | 量化門檻                                                                                                                       |

- `bugfix` / `hotfix` / `style` / `doc` / `typo` / `rename` / `refactor-minor`

## 三、評估矩陣（強制填寫）

每候選方案依 5 維度評分（1-5 分；5 最佳）：

| 維度 | 判定方法 | 權重 |
|-----|---------|-----|
| **維護活躍度** | GitHub 最近 commit < 90 天 = 5；< 180 天 = 4；< 365 天 = 3；> 365 天 = 2；> 2 年 = 1 | 25% |
| **社群規模** | GitHub stars：> 10k = 5；> 3k = 4；> 1k = 3；> 300 = 2；< 300 = 1 | 20% |
| **License 相容** | 與專案 `BUSINESS_RULES.license_preference` 欄位比對（預設 MIT / Apache 2.0 = 5；BSD = 5；LGPL = 4；GPL = 2；專有 = 1）| 15% |
| **依賴衝突** | 新增依賴數 < 5 = 5；5-10 = 4；10-20 = 3；20-50 = 2；> 50 = 1 | 20% |
| **客製成本** | 開箱即用 = 5；少量 wrapper = 4；中等客製 = 3；大幅客製 = 2；幾乎重寫 = 1 | 20% |

**總評公式**：`(活躍度 × 0.25) + (社群 × 0.20) + (License × 0.15) + (依賴 × 0.20) + (客製 × 0.20)`
- 總評 ≥ 4.0 → 🟢 強烈推薦
- 總評 3.0 ~ 4.0 → 🟡 可採納但需評估客製
