## 一、問題描述

### 根因分類
**類型**：核心文件架構性膨脹（LT-02）

### 問題陳述
`lead.md` 是系統中使用頻率最高的 Rules 文件，
隨著系統迭代，歷次修改累積導致文件結構
出現以下問題：

#### 問題一：章節職責重疊
```
現況：
「任務派發流程」與「協調邊界」章節
部分內容重複描述相同的判斷邏輯，
@Lead 執行時需要在兩個章節間
交叉確認，降低執行效率。

例：
「任務派發流程」：「高風險任務需升級 User」
「協調邊界」：「涉及安全邊界需升級 User」
→ 兩者描述的是同一判斷，但分散在不同章節
```

#### 問題二：HITL 條件分散
```
現況：
lead.md 中的 HITL 升級條件
散落在三個不同章節：
① 任務派發流程章節（內嵌在流程步驟中）
② 協調邊界章節（以邊界定義形式出現）
③ 緊急情況章節（以例外條件出現）

影響：
@Lead 在判斷「是否需要升級」時
需要檢索三個章節，
認知負擔高，且容易遺漏邊界條件
```

#### 問題三：歷次提案累積的章節碎片化
```
現況：
PROPOSAL-004（系統業務脈絡）
PROPOSAL-011（業務脈絡錨點）
PROPOSAL-013（豁免授權機制）
三份提案均在 lead.md 新增章節，
但新增章節與原有章節的結構關係未整理，
形成「補丁式堆疊」而非「有機整合」
```

#### 問題四：Token 使用效率低
```
現況預估：
lead.md 原始 Token：~400
+ PROPOSAL-004 新增：+15
+ PROPOSAL-011 新增：+60
+ PROPOSAL-013 新增：+80
累計預估：~555 tokens

問題：
若 lead.md 為 AlwaysOn 文件，
555 tokens 超過 500 tokens 上限；
即便為非 AlwaysOn，
重複與碎片化內容造成
有效資訊密度下降
```

### 問題影響層級
- 影響範圍：@Lead 每次執行任務協調
- 風險分類：執行效率與可維護性
  （lead.md 為最高頻使用文件，
   結構問題的累積效應最為顯著）
- 風險等級：🟢 低風險（P3）
  （現有功能仍正常，架構精簡為長期優化）

## 二、根因分析

### 直接根因
lead.md 在系統演進過程中採用
「增量補丁」模式更新，
缺乏定期的結構性重整機制。

### 系統根因
PROPOSAL-003（RULES_DESIGN_GUIDE）
尚未建立，缺乏「Rules 文件結構標準」
作為重整的參照基準。
本提案應在 PROPOSAL-003 執行後，
以 RULES_DESIGN_GUIDE 的標準結構
為基礎進行重整。

### 前置依賴
本提案的執行依賴以下提案先完成：
- PROPOSAL-003（RULES_DESIGN_GUIDE 建立）
  → 提供重整的結構標準
- PROPOSAL-004（system-prompt.md 修補）
  → 確認業務脈絡描述已在上層統一
- PROPOSAL-011（業務脈絡錨點）
  → 確認 lead.md 業務脈絡補強內容已定稿
- PROPOSAL-013（豁免授權機制）
  → 確認豁免章節內容已定稿

## 三、提案內容

### 重整原則

```
原則一：合併重疊內容
  → HITL 升級條件統一集中於一個章節

原則二：結構對齊 RULES_DESIGN_GUIDE
  → 依標準章節順序重排（Persona → 模式
    → 工作流程 → DoD → HITL → 安全邊界）

原則三：精簡而非刪除
  → 保留所有功能性內容，
    僅移除重複描述與冗餘說明

原則四：補丁整合
  → PROPOSAL-004 / 011 / 013 新增的內容
    整合進對應章節，不以獨立補丁存在
```
