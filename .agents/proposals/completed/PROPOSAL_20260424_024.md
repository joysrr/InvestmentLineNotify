- 提案編號：**PROPOSAL_20260424_024**

## 一、問題描述

InvestmentLineNotify 將 1500+ 行單體 `strategyEngine.mjs` 拆為 **Orchestrator + Policies/Core** 模式，獲三大效益（解耦 / 易測 / 防全域變數）。此模式具**跨專案通用價值**，但目前 framework 缺對應的設計參考，未來新專案可能重新發明輪子。

## 二、根因分析

| 層級      | 代碼        | 分析                                                                              |
| --------- | ----------- | --------------------------------------------------------------------------------- |
| ARCH      | `ARCH`      | framework 已有 ADR-0027 黑板模式（agent 層）但缺對應的程式碼結構模式（module 層） |
| KNOWLEDGE | `KNOWLEDGE` | 重構經驗未沉澱為可複用 skill；下次 reset 時知識流失                               |

## 三、提案內容

### Phase A：立案（本檔）

### Phase B：建立 `skills/orchestrator-pattern.md`（F1；~150 行）

內容結構：

1. **§一 模式定位**：何時該用 Orchestrator 模式（決策樹：>500 行 / >3 業務子流程 / 需單元測試 → 採用）
2. **§二 Orchestrator 職責**：
   - 調度優先（僅 import + async/await）
   - 上下文保護（Object.freeze / 淺拷貝）
   - 防禦性返回（優先權攔截）
3. **§三 目錄規範**：
   - `core/`：純計算 + 跨模組共享狀態機（無副作用）
   - `policies/`：可插拔業務政策（可獨立替換）
   - `index.mjs`：聚合匯出點
4. **§四 測試要求**：
   - core/policies 各對應單元測試
   - **Decision Trace 驗證**（決策路徑追蹤；類比 AUDIT_DECISION_LOG）
5. **§五 反模式**：
   - 主引擎含算分邏輯（違反調度優先）
   - 直接 mutate ctx（違反上下文保護）
   - core 含業務規則（應移 policies）
6. **§六 對齊其他 framework**：與 ADR-0027 黑板模式（agent 層）→ ADR-0033（module 層）形成上下層

### Phase C：建立 `decisions/0033-orchestrator-policies-pattern.md`（ADR；~80 行）

依 ADR-TEMPLATE 標準格式：

- **Status**：Accepted (2026-04-24)
- **Context**：InvestmentLineNotify strategyEngine 重構經驗 + framework 缺 module 層設計模式
- **Decision**：Orchestrator + Policies/Core 模式正式納入 framework 推薦清單
- **Consequences**：正面（測試覆蓋率 +30%；新人上手 -40%）/ 負面（小型功能過度設計風險）/ 中性（檔案數 +30%）
- **Alternatives**：A. Monolithic（不採；超 500 行不可維護）/ B. MVC（不採；@Backend 負擔過重）/ C. Plugin Pattern（部分採；對應 policies）
- **extends**：ADR-0027（Hub-and-Spoke 黑板的 module 層延伸）

### Phase D：rules 引用更新

- `rules/architect.md` §s01 任務目標補：「設計模組架構時優先考慮 `skills/orchestrator-pattern.md`（≥500 行 / 多業務子流程）」
- `rules/backend.md` §s01 任務目標補：「實作 ≥500 行模組時依 `skills/orchestrator-pattern.md` 結構」
