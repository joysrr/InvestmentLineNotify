## 一、問題描述

### 根因分類
**類型**：AlwaysOn 文件三個獨立缺口
        （業務描述過時 + 模式歧義 + 全局兜底缺失）

### 問題陳述
`system-prompt.md` 是整個系統唯一的 AlwaysOn 文件，
每次對話均會載入，對全系統的行為基準影響最深遠。

審計識別出三個獨立缺口：

#### 缺口一：業務描述過時（QW-01）
```
現況：「核心功能為透過 Line Notify 推送量化投資訊號」
實況：系統已遷移至 Telegram Bot + Telegram Mini App
影響：AlwaysOn 業務脈絡與系統實際狀態不符，
      @Lead 協調任務時的技術選型判斷可能基於過時資訊
```

#### 缺口二：模式混合指令處理未定義（QW-03）
```
現況：討論模式與執行模式有關鍵字觸發機制，
      但缺少「同一指令同時觸發兩種模式」的處理規則
影響：當 User 發出「解釋一下然後幫我執行」類型的混合指令時，
      @Lead 行為不確定——可能直接執行（跳過討論），
      也可能只討論（忽略執行觸發信號）
```

#### 缺口三：全局緊急阻斷機制缺失（QW-02）
```
現況：各 Agent 的 HITL 終止條件定義在各自 Rules 中，
      但系統層級缺少「協調失敗」的全局緊急阻斷
影響：若 @Lead 本身在協調任務時出現連續失敗，
      沒有任何系統層級機制能強制介入，
      只能依賴 @Lead 自身的自律性停止——
      而這正是 AlwaysOn 層級應防範的最高風險
```

### 問題影響層級
由於 `system-prompt.md` 為 AlwaysOn 文件，
三個缺口的影響範圍是**全系統每次對話**，
而非特定任務或特定 Agent。

## 二、根因分析

### 缺口一根因
系統遷移（Line Notify → Telegram Bot）
是業務演進的自然結果，
但 AlwaysOn 文件未在遷移時同步更新。
根因為缺乏「系統重大遷移後的 Rules 同步審查機制」。

### 缺口二根因
雙模式設計在初始版本中假設 User 的指令
永遠可以被明確分類為「討論」或「執行」，
未預期混合指令場景。
隨著 User 使用習慣趨向自然語言，
混合指令的出現頻率增加，但 Rules 未同步更新。

### 缺口三根因
系統設計哲學為「各 Agent 自律 + HITL 分散保障」，
但缺少最後一道系統層級的兜底機制。
@Assistant 的巡邏可以偵測 Agent 漂移，
但無法處理「@Lead 協調邏輯本身出錯」的場景。

### 共同根因
三個缺口均源自同一個設計盲點：
> AlwaysOn 文件在系統演進過程中缺乏定期審查的觸發機制。

`retro.md` 的歷史比對機制以功能問題為主要偵測對象，
對「Rules 是否反映系統當前狀態」的審查覆蓋不足。

## 三、提案內容

### 修改項目一：業務描述更新（缺口一）

```markdown
// 修改位置：system-prompt.md 系統業務脈絡章節

// 修改前
核心功能為透過 Line Notify 推送量化投資訊號，
系統部署於 Oracle VM Free Tier。

// 修改後
核心功能為透過 Telegram Bot 推送量化投資訊號，
並提供 Telegram Mini App 進行投資策略視覺化管理。
系統部署於 Oracle VM Free Tier，
採用 Node.js ESM + File-based 資料儲存架構。
```

**修改說明**：
- 將 `Line Notify` 替換為 `Telegram Bot`
- 新增 `Telegram Mini App` 功能描述
- 補充技術棧摘要，作為全局技術脈絡錨點
- 新增約 15 tokens，AlwaysOn 總 Token 預算不超標

---

### 修改項目二：模式混合指令處理規則（缺口二）

```markdown
// 修改位置：system-prompt.md 模式判斷章節末尾新增

## 混合指令處理規則

當單一指令同時包含討論觸發信號與執行觸發信號時
（例如：「解釋一下 X，然後幫我執行 Y」），
依以下優先順序處理：

Step 1：優先進入討論模式
        完整回應討論部分，確認 User 理解

Step 2：主動詢問確認
        「已完成說明，是否確認啟動執行模式執行 Y？」

Step 3：獲得明確確認後
        切換執行模式，啟動 Workflow Engine

禁止：未獲得 User 明確確認前，
      直接從討論模式切換至執行模式。
```

**修改說明**：
- 新增約 80 tokens
- 消除混合指令下的行為不確定性
- 「禁止」語言確保即使在長程任務中
  LLM 也不會因為「效率考量」跳過確認步驟

---

### 修改項目三：全局緊急阻斷機制（缺口三）

```markdown
// 修改位置：system-prompt.md 唯一鐵律章節後方新增

## 全局緊急阻斷

以下情境觸發全局緊急阻斷，
優先級高於所有 Agent 的個別執行邏輯：

### 觸發條件
條件一（協調失敗）：
@Lead 連續 3 次未能完成任務派發
（任務退回 / 派發對象錯誤 / 派發後無回應）
→ 強制暫停所有 Workflow

條件二（系統狀態不一致）：
@Assistant 巡邏發現 PENDING_ACTIONS.md 存在
超過 2 個週期未處理的 🔴 項目
→ 強制暫停新任務派發

條件三（安全邊界觸碰）：
任何 Agent 執行動作涉及以下任一項：
- 直接修改 .agents/ 原始 Rules 文件
- 直接修改 strategyWeight 數值
- 在程式碼中寫入金鑰或 Token
→ 強制停止，等待 User 確認

### 觸發後行動
1. 立即停止當前所有 Workflow 執行
2. 向 User 輸出當前系統狀態摘要：
   - 觸發阻斷的具體條件
   - 當前未完成任務列表
   - 建議的恢復步驟
3. 進入等待模式，不執行任何新任務，
   直到 User 明確發出恢復指令

### 恢復指令
User 發出「系統恢復」或「繼續執行」
→ @Lead 重新確認 PENDING_ACTIONS.md 狀態後恢復
```

**修改說明**：
- 新增約 150 tokens
- 三個觸發條件對應三個不同的系統風險層次：
  協調失敗 / 狀態不一致 / 安全邊界觸碰
- 條件三與 `retro.md`、`consultant.md`、
  `backend.md` 的業務安全邊界保持一致，
  在 AlwaysOn 層級形成最高優先級保障
