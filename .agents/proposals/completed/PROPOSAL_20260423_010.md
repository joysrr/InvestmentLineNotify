## 一、問題描述

### 1.1 User 檢視結論（2026-04-23）

> 「6 個提案在一天內執行 = 36+ phase 操作；新人接手難度高。引入 Lite Proposal（1-2 phase 流程；用於 typo / 文檔小修 / 路徑更新等）」

### 1.2 量化證據

| 情境                      | 當前 Full Proposal | 典型 Phase 數         |
| ------------------------- | ------------------ | --------------------- |
| 新架構元件                | Full Proposal      | 6-8 Phase             |
| 新 Rule 章節              | Full Proposal      | 6-8 Phase             |
| 新 skill/task             | Full Proposal      | 5-7 Phase             |
| **Typo 修正**（1 行）     | Full Proposal      | 5-7 Phase（**過度**） |
| **路徑更新**（引用變更）  | Full Proposal      | 5-7 Phase（**過度**） |
| **版本號 bump**（手動補） | Full Proposal      | 5-7 Phase（**過度**） |
| **移除已棄用欄位**        | Full Proposal      | 5-7 Phase（**過度**） |

本日 8 提案實測：

- `PROPOSAL_001 ~ 008`：平均 6 Phase × 7 檔同步 = 42+ 操作
- 其中約 15-20% 操作為「純文字 / 路徑 / 版本號同步」（機械化可自動；不需完整提案）

### 1.3 風險：繁瑣促使 bypass

User 在以下情況可能傾向「跳過提案直接改 .agents/」：

- 發現 typo（1 行）
- 引用路徑錯誤（重構殘留）
- 版本號不一致（RULES_VERSION_INDEX 與 rule frontmatter 不同步）
- 命名拼寫錯誤

**繞過提案 = 失去**：

- 歷史追溯（PROPOSAL_INDEX 記錄）
- 派生視圖同步（agents-overview / CHANGELOG）
- drift_score 驗證（PROPOSAL_025 §十二 Phase E.1）
- `@Retro` 根因分析（反覆問題識別）

### 1.4 對齊既有警示機制

`tasks/periodic-design-review.md`（PROPOSAL_008 新建）警示維度 #3 明文：

> | 3 | 提案平均 Phase 數 | > 8 | 引入 Lite Proposal（1-2 phase）|

```markdown
## 二十一、提案輕重分級（依 PROPOSAL_20260423_010）

本節為 PROPOSAL_20260423_010 核心產物。依變更複雜度區分 **Lite Proposal** 與 **Full Proposal** 兩類；前者走快速 1-2 phase，後者走完整 5-8 phase。

### A. 兩類定義

| 類型                 | 適用場景                                                      | 平均 Phase | 模板                                                     |
| -------------------- | ------------------------------------------------------------- | ---------- | -------------------------------------------------------- |
| 🟢 **Lite Proposal** | typo / 引用路徑更新 / 版本號 bump / 單行補強 / 移除已棄用欄位 | 1-2        | `skills/templates/rule-update-proposal-lite-template.md` |
| 🔴 **Full Proposal** | 新架構 / 新章節 / 新 Agent / 新 validator / 結構性重組        | 5-8        | `skills/templates/rule-update-proposal-full-template.md` |

### B. 判定決策樹（預設 Full；全滿足排除才落為 Lite）
```

1. 先假設 Full
2. 逐一確認以下條件 → 否則 Full 鎖定：
   - 不新增 rules / skills / tasks / validators / scripts（純修改既有）
   - 不新增 RULES_DESIGN_GUIDE 章節（可補既有章節小段）
   - 不新增 Agent / patrol rule / 機制性變更
   - 不改動 drift_score 基準（不觸及 rules/ 結構）
   - 不改動 workspace schema 欄位
   - diff ≤ 50 行（單檔或相關跨檔合計）
   - 不改 @Auditor 評鑑項目
3. 全部 OK → Lite 啟用

```

### C. Lite Proposal 標準結構（對齊 lite-template）

強制最小欄位（共 7 項）：
1. 提案編號 / scope / 提案日期 / 狀態 / 優先級
2. 一句話問題描述（含具體檔案 + 行號）
3. 一句話變更內容（含目標與手段）
4. 執行動作清單（≤ 5 項；機械化可驗證）
5. 驗收（checkbox；包含 run-all.sh 通過）
6. 意圖繼承聲明（若有則列；可 "無"）
7. User 採納指令

**禁止**於 Lite Proposal 出現的章節：
- §根因分析（Lite 不需根因；直接修）
- §預期效益量化（Lite 不需計分）
- §執行計畫多 Phase（Lite 僅 1-2 Phase）
- §整合性分析（Lite 不涉跨提案衝突）
- §未來延伸（Lite 不預判）

### D. Lite 提案 Phase 結構

```

Phase A（必要；10-30 分）：執行動作清單

- 依 §C.4 清單逐項執行
- 每項可機械化驗證（grep / file-exists / checksum）

Phase B（可選；10 分）：派生視圖 + 索引同步 + 移至 completed/

- 使用 generators 自動化（PROPOSAL_007）
- bash run-all.sh --regenerate-indexes
- PROPOSAL_INDEX / CHANGELOG / FRAMEWORK_VERSION 自動或手動 minor bump

```

### E. Lite Proposal 限制

| 限制 | 說明 |
|-----|-----|
| Phase 數量 | **≤ 2**（A 動作 + B 同步）|
| diff 範圍 | **≤ 50 行**（跨檔合計）|
| Agent 行為影響 | **0**（不改任何 Agent DoD 或行為）|
| drift_score 影響 | **0**（不改 rules/ 結構）|
| validators 數量影響 | **0**（不加 / 不減 validator）|
| 時效 | **≤ 1 小時**（從 OPEN 到 DONE）|

### F. 禁止行為

- **絕對禁止** 以 Lite Proposal 名義執行 Full 範圍變更（屬流程違規；@Retro 根因分析強制觸發）
- **絕對禁止** Lite Proposal 跳過 run-all.sh 驗證（Phase B 為選項但驗證必跑）
- **絕對禁止** Lite Proposal 省略意圖繼承聲明（即使填「無」也需明文）
- **絕對禁止** @Retro 未經提案直接修改 `.agents/` 檔案（即使 typo 也需最小 Lite Proposal）

### G. 違規偵測

- `@Retro` 審計時比對 `proposals/completed/` 的 diff 大小 vs 宣稱 tier
- 若 Lite Proposal 實際 diff > 50 行或含禁止章節 → 🟡 升級為「Full 錯標 Lite」警示
- 累積 ≥ 3 次錯標 → 觸發 `@Retro` 根因提案
```

## 四、預期效益

### 4.1 量化

| 指標                                      | 現況（全 Full）   | 目標（導入 Lite） | 估算依據                     |
| ----------------------------------------- | ----------------- | ----------------- | ---------------------------- |
| 微型提案平均長度                          | ~400 行           | ~70 行            | 7 欄必填 × 10 行             |
| 微型提案撰寫時間                          | ~45 分鐘          | ~10 分鐘          | 省略 §根因 / 效益 / 計畫細分 |
| 微型提案審查時間                          | ~15 分鐘          | ~3 分鐘           | 只看 Why + Change + Impact   |
| 年度節省（估 12 次 typo/路徑/token 修正） | —                 | **~8 小時**       | (45-10) × 12 + (15-3) × 12   |
| PROPOSAL_INDEX 可讀性                     | OPEN 項目混雜輕重 | `tier` 標記分類   | 新增 frontmatter 欄位        |

### 4.2 質化

- **降低心理門檻**：typo / 明顯筆誤可直接發 Lite 提案而非「懶得寫提案直接改」→ 改善歷史追溯
- **保留中型變更嚴謹度**：Full 仍是預設，決策樹強制「所有例外才落 Lite」→ 避免濫用
- **強化 §🔗 意圖繼承**：Lite 也強制填 `基於` → 不因簡化而斷鏈
- **Dogfooding Skills 檢索**：lite-template 是首個「F1 但有嚴格決策自檢」skill；可成為後續 Skills 設計範式

### 4.3 非目標（Non-Goals / Tradeoffs）

| 情境                                 | 處置      | 理由                                              |
| ------------------------------------ | --------- | ------------------------------------------------- |
| 移除 Full Proposal 任何必填欄位      | ❌ 不做   | Lite 是 Full 的**精簡子集**；Full 仍為預設        |
| Lite 可變更 Agent 行為               | ❌ 禁止   | Agent 行為屬「規則變更」→ 需 Full 的根因分析      |
| Lite 可跨多個 rules/ 檔              | ❌ 禁止   | 跨檔即為中型變更 → 走 Full                        |
| 完全自動判定 Lite/Full（LLM 省判斷） | ⚠️ 暫不做 | 先靠決策樹 + validator 攔截；後續可考慮 heuristic |
| 歷史 DONE Full 提案回頭改 Lite       | ❌ 不做   | 歷史不改寫；相容註記足夠                          |

### 4.4 風險緩解貢獻

| 風險類型                         | 緩解效果        | 說明                                                    |
| -------------------------------- | --------------- | ------------------------------------------------------- |
| 「懶得寫提案直接改」導致失序變更 | 🟢 顯著降低     | 10 分鐘門檻 vs 45 分鐘 → 提升提案率                     |
| Lite 被濫用吞噬中型變更          | 🟡 需監控       | 靠決策樹 + periodic review §5 觀察 Lite 比例            |
| Full/Lite 重複內容維護成本       | 🟢 低           | Lite 是 Full 子集；Full 變更時 Lite 只需確認 7 欄未影響 |
| 歷史引用斷鏈                     | 🟢 相容註記處理 | 舊名檔 → 新名檔頂部保留說明                             |

### 4.5 Dogfooding 與教學價值

- **本提案自身**：PROPOSAL_010 本身是 Full（規則變更 + 新 Skill + 既有改名 → 不符 Lite 條件）
