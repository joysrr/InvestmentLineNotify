## 一、問題描述

### 根因分類

**類型**：審查類 Agent 產出物純淨度不足（Output Purity Deficit）+ Machine-to-Machine 字串合約缺失

### 問題陳述

Gemini 評估指出：配合 `@Lead` 轉型為**無狀態路由器**（PROPOSAL_20260422_001 核心方案），系統對**機讀符號**的依賴度將達到 **100%**。若審查類 Agent（`@Reviewer` / `@Security` / `@QA`）在產出報告時：

1. **擅自改變 Markdown 標頭格式**（例：將 `## 審查結論` 改為 `## 我的審查發現`）
2. **將符號包裝在冗長句子中**（例：「經過仔細評估後，我的結論是 🔴 退件」，符號非第一行）
3. **未嚴格套用既有模板**（`skills/templates/review-report-template.md` / `skills/templates/test-report-template.md`）
4. **在產出物頂部添加自然語言前言**（例：「好的，我已經審查完畢...」）
5. **在產出物尾端添加結語或自我解釋**（例：「希望這對你有幫助」）

將直接造成 `@Lead` 的 regex / grep 級別符號掃描**失敗**，系統進入無狀態路由後**工作流斷鏈**。

### 具體觀察（引用自現行審查類 rules）

| Agent       | 產出物                              | 現行規範                                                                                                       | 機讀合約缺口                                                     |
| ----------- | ----------------------------------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `@Reviewer` | `REVIEW_REPORT.md`                  | `reviewer.md §s03` 僅參照 `skills/templates/review-report-template.md`，無純淨度條款                           | 未限制前言/結語；未強制第一行為符號；未禁止自訂章節              |
| `@Security` | `SECURITY_REPORT.md`                | `security.md §s04` 內嵌格式（未外部化）；格式含 `【@Security 資安審查報告】<級別符號>` 標頭                    | 未禁止 LLM 在 frontmatter 前額外添加對話文字；未禁止自行增減章節 |
| `@QA`       | `TEST_SPEC_*.md` / `TEST_REPORT.md` | `qa.md §s07 / §s08` 參照 `skills/templates/test-spec-template.md` / `skills/templates/test-report-template.md` | 同 @Reviewer 問題：無純淨度條款                                  |

### 問題影響層級

- **系統穩定性**：🔴 高（PROPOSAL_20260422_001 採納後，格式偏差即等於工作流當機）
- **Token 浪費**：🟡 中（客套話與自我解釋平均每份報告浪費 ~100~300 tokens）
- **LangGraph 遷移前置**：🔴 高（未來 LangGraph 腳本以字串解析為主；純淨度不足直接導致腳本脆弱）
- **跨對話一致性**：🟡 中（不同對話輪次下，LLM 產出格式漂移機率上升）
- 綜合風險等級：🔴 高（PROPOSAL-001 採納後隱含前置條件）

### 與 PROPOSAL_20260422_001 的強耦合

本提案為 **001 的配套防禦**：

- 001：`@Lead` 降級為無狀態路由器，僅掃描 `🔴 BLOCKER` 等符號
- 003（本提案）：保證下游審查 Agent 產出符號可被精準掃描

若只採納 001 而不採納 003，`@Lead` 將面臨「我需要掃描符號，但符號格式不穩」的執行矛盾。

## 二、根因分析

| 根因層級 | 代碼   | 分析說明                                                                                                                                    |
| -------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 系統架構 | `ARCH` | 缺乏對審查類 Agent「輸出純淨度（Output Purity）」的強制約束。過去過度依賴大模型的語意包容力，未落實 Machine-to-Machine（M2M）嚴格的字串合約 |
| 設計層   | `ARCH` | 現行 `skills/*-template.md` 僅定義結構，未定義「純淨度協議」；rules 本體引用模板但未強制「禁對話」條款                                      |

### 直接根因

審查類 rules 的設計假設是「`@Lead` 有語意理解能力，能容錯處理非標格式」。PROPOSAL_20260422_001 推翻此假設後（`@Lead` 降級為 grep 級路由器），既有容錯設計變為系統性漏洞。

### 系統根因

缺乏「**M2M 嚴格合約（Strict M2M Contract）**」原則：

- **現況模型**：產出物為「LLM 產生給 LLM 讀」，容許自然語言包裝
- **本提案模型**：產出物為「LLM 產生給腳本/路由器讀」，要求結構化純淨輸出（類似 API 端點）

此原則確立後，**所有機讀產出物**（不只審查類）未來皆可套用相同規範，但本提案聚焦於 001 直接衝擊的三個 Agent。

### 範疇限定說明（為何不全面推行 M2M）

本提案**不涵蓋**以下 Agent 的產出物：

| Agent                    | 產出物                                    | 不納入理由                                                         |
| ------------------------ | ----------------------------------------- | ------------------------------------------------------------------ |
| `@Consultant`            | `ADVICE_*.md`                             | 消費者主要為 User 與 `@Planner`（非 @Lead 路由器），容許敘事性內容 |
| `@Architect`             | `docs/api/*.md`                           | 給開發者閱讀的 API 規格，自然語言說明有其必要                      |
| `@Planner`               | `draft_features.md` / `ideas_features.md` | User Story + 需求描述，需敘事完整性                                |
| `@Retro`                 | `PROPOSAL_*.md`                           | 本提案即為範例；審查對象為 User 決策，需完整說明                   |
| `@Backend` / `@Frontend` | DoD 自評 / 部署指令                       | 已由 `§DoD 自評機制` 提供結構化回報區塊（對齊 PROPOSAL-012）       |
| `@Assistant`             | `PENDING_ACTIONS.md` / 巡邏摘要           | 已由 PROPOSAL-017 強制標頭格式                                     |

納入者共通特徵：**產出物於 Workflow 6 / 6.5 / 7 階段被 `@Lead` 在 Gate Check 時直接掃描**，且 001 執行後 `@Lead` 僅做符號 grep。

### 3.1 `reviewer.md` 新增章節

**插入位置**：§s02「動態審查範疇機制」之後、§s03「REVIEW_REPORT 標準格式」之前

**immutable**：`true`

#### 新章節原文（完整寫入 reviewer.md）

```markdown
<section id="s_output_strict" priority="critical" immutable="true">
## 機讀產出物強制規範 (Machine-Readable Output Strictness)

配合系統之無狀態路由架構（PROPOSAL_20260422_001），`@Reviewer` 在產出 `REVIEW_REPORT.md` 時，**必須**視自己為一個 API 端點，而非聊天機器人。絕對遵守以下鐵律：

### 1. 零對話原則（No Small Talk）

- **絕對禁止** 在產出物中包含任何前言、結語或自我解釋
- **絕對禁止** 示例：「好的，我已經審查完畢...」、「希望這對你有幫助」、「經過仔細評估後...」
- **絕對禁止** 在報告外的對話回覆中夾帶報告原文（對齊 `lead.md §s_state_anchor` 禁止文本合併原則）

### 2. 符號絕對錨點（Symbol Absolute Anchor）

- `REVIEW_REPORT.md` 的**第一行**必須嚴格依照 `RULES_DESIGN_GUIDE.md §九` 之定義，**單獨輸出**五級通知符號之一：
  - 🔴 CRITICAL
  - ❌ BLOCKED
  - 🟡 WARNING
  - ✅ DONE
  - 🟢 INFO
- **絕對禁止** 於符號前後附加修飾詞（例：「**🔴** 審查結果：」或「🔴 經判斷為退件」）
- **絕對禁止** 在首行前插入 YAML frontmatter 以外的任何內容
- 允許例外：若 `@Reviewer` 本系統已採 YAML frontmatter（未來提案），frontmatter 區塊之後第一行必須為符號

### 3. 嚴格模板對齊（Strict Template Alignment）

- 必須 **100% 遵守** `skills/templates/review-report-template.md` 的 Markdown 結構
- **絕對禁止** 自行增減章節（H1 / H2 標題不得新增或刪除）
- **絕對禁止** 改變既有標題名稱（例：將 `## 審查結論` 改為 `## 我的審查發現`）
- 若模板不足以表達特殊情境，**必須** 依 `.agents/rules/retro.md §提案提交時機` 提案擴充模板，**不可** 於單次報告中臨時自訂章節

### 4. 違反處理

任一違反以上三項鐵律的報告，視為產出物**未完成**：

- `@Lead` 於符號掃描時發現格式漂移 → 退件並要求 `@Reviewer` 重新產出
- 退件計入 `REVIEW_CYCLE_LIMIT`（與本身複審計數共用；對齊 `reviewer.md §退件後重提流程`）
- `@Assistant` 巡邏（P-01）偵測同功能連續 ≥ 2 次格式違規時，產生 🔴 `REVIEW_QUALITY`

### 5. 純淨度自檢 Checklist

通知 `@Lead` 前**必須**逐項確認：

- [ ] 報告第一行為五級符號之一（無修飾詞）
- [ ] 無任何前言（「好的」/「我」/「經過」等開場字樣）
- [ ] 無任何結語（「希望」/「以上」/「請參考」等收尾字樣）
- [ ] H1 / H2 標題與模板 100% 一致
- [ ] 無自行新增或刪除的章節

<!-- END: 機讀產出物強制規範 -->
</section>
```

### 3.5 與既有規則的衝突處理

#### 衝突一：現行 rules 允許 `@Reviewer` / `@Security` 在報告中「說明豁免原因」

現行 `reviewer.md §s04 審查退件等級` 中提到：

> `[WARNING]` 項目若決定豁免，說明理由

本提案**不禁止豁免理由記錄**，但要求記錄於**模板內**既有欄位（例「豁免說明」欄），而非自由格式新增章節。於 Phase A~C 執行時，確認模板已有對應欄位；若無，併入 Phase D 模板更新。

#### 衝突二：`@Assistant` 巡邏僅偵測「複審次數」，未偵測「格式違規」

現行 `assistant.md §s05 巡邏規則表` P-01 僅依「審查結論為退件 + 複審 ≥ `REVIEW_CYCLE_LIMIT`」觸發。本提案**不擴充 P-01**，而是：

- 將「格式違規」視為「未通過」的一種，由 `@Lead` 在符號掃描階段判定退件
