## 問題描述

**發現位置**：`.agents/rules/lead.md` 與 `.agents/rules/qa.md`
**問題摘要**：`@Lead` 在執行模式下直接修改了 Agent Rules 文件，繞過了提案採納工作流。
**詳細描述**：在處理「建立程式與測試連結」的需求時，`@Lead` 為了追求 DoD 效率，直接將 `docs/TEST_MAPPING.md` 的引用寫入 `.agents/rules/` 目錄。這違反了「Agent 規則演進必須經過提案與 User 採納」的核心安全性原則。

## 根因分析

| 根因層級 | 代碼   | 分析說明                                                                                         |
| -------- | ------ | ------------------------------------------------------------------------------------------------ |
| 需求層   | `REQ`  | 使用者要求「建立連結或提案」，`@Lead` 優先解讀為「建立連結（實作）」而忽略了規則更新的特殊流程。 |
| 開發層   | `DEV`  | `lead.md` §s10 的例外條款語意不清，且缺乏「自動攔截規則修改」的內部檢查機制。                    |
| 架構層   | `ARCH` | 系統對於「基礎設施連結」與「Agent 行為規則」的邊界定義在執行時容易發生偏移。                     |

## 建議修改對象與內容

### 1. 採納測試映射基建

**目標檔案**：[TEST_MAPPING.md](file:///Users/han/Project/InvestmentLineNotify/docs/TEST_MAPPING.md)
**內容**：正式將此映射表作為專案驗證的「單一事實來源 (SSOT)」。

### 2. 更新 @Lead 規則 (lead.md)

**修改位置**：`§s13 資源與上下文映射表` 與 `§s10 行為準則`
**建議新增規則**：

- 在 `§s13` 測試情境中加入 `docs/TEST_MAPPING.md` 引用。
- 在 `§s10` 加入：**「絕對禁止」** 在非執行 `PROPOSAL_ADOPT` 任務時修改 `.agents/` 目錄下任何文件。若 User 指令涉及規則異動，必須先派發 `@Retro` 產出提案，禁止直接實施。

### 3. 更新 @QA 規則 (qa.md)

**修改位置**：`§s10 執行準則`
**建議新增規則**：

- 執行測試前必須查閱 `docs/TEST_MAPPING.md` 確保覆蓋範圍完整。

## 預期效果

1. **防止規則黑箱化**：確保所有的 Agent 行為變更都在 User 的可見與授權範圍內。
2. **強化測試聯動**：後續 Agent 修改代碼時，將有明確的映射表指引應執行的測試。
3. **明確化 @Lead 權限**：消除「為了效率而直接改規則」的灰色地帶。
