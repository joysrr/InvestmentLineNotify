## 一、問題描述

### 根因分類
**類型**：系統演進缺乏版本追蹤機制（LT-06）

### 問題陳述
系統目前有 19 份 Rules 文件
（含 system-prompt.md 及各 Agent Rules），
隨著提案體系成熟（本次審計即產出 19 份提案），
Rules 文件的版本追蹤需求已浮現：

#### 具體問題
```
問題一：無法識別 Rules 文件的當前版本
  現況：Rules 文件無版本號標記，
        無法快速判斷「這是最新版本嗎？」
  影響：當多份提案陸續執行後，
        各 Rules 的修改歷史難以追溯，
        @Retro 審計時無法確認
        「上次審計後哪些 Rules 已變更」

問題二：提案執行後缺乏文件版本更新記錄
  現況：提案執行後，
        Rules 文件本身無對應的版本變更記錄，
        只能透過 Git commit log 追溯，
        但 .agents/ 目錄未必有 Git 管理

問題三：@Retro 審計基準不明確
  現況：@Retro 執行審計時，
        無法確認「上次審計基準版本」
        與「當前版本」的差異範圍，
        可能重複審計已修正的項目，
        或遺漏自上次審計後新增的變更

問題四：Rules 回滾機制缺失
  現況：若提案執行後發現問題，
        無明確的回滾流程，
        只能依賴 User 的記憶或對話歷史
```

### 問題影響層級
- 影響範圍：所有 Rules 文件的長期維護
- 風險分類：系統長期可維護性
  （版本控制是系統穩定後的基礎設施需求）
- 風險等級：🟢 低風險（P3）
  （觸發時機：系統穩定後，
   提案執行累積 ≥ 10 份後）

## 二、根因分析

### 直接根因
系統初期規模小，
Rules 文件版本控制需求不明顯，
設計時未納入考量。
隨著提案體系建立（19 份提案），
版本追蹤需求已達觸發門檻。

### 系統根因
.agents/ 目錄的版本管理
依賴外部工具（Git）但未強制要求，
Rules 本身缺乏自描述的版本資訊，
導致在無 Git 環境下版本追蹤完全缺失。

### 設計哲學
Rules 版本控制應採「輕量自描述」方案：
在每份 Rules 文件中嵌入版本標頭，
無需依賴外部工具，
任何環境下均可識別版本狀態。

## 三、提案內容

### 修改項目一：Rules 文件版本標頭標準

```markdown
// 寫入位置：RULES_DESIGN_GUIDE.md（PROPOSAL-003 建立）
// 所有 Rules 文件必須在文件頂部包含此標頭

## Rules 文件版本標頭標準

### 標頭格式
每份 Rules 文件的第一個章節前，
必須包含以下版本標頭：

***
版本：v{major}.{minor}
最後修改：{YYYY-MM-DD}
修改提案：{PROPOSAL-XXX}（最近一次修改的提案編號）
修改摘要：{一句話描述本次修改的核心內容}
審計基準：v{major}.{minor}（上次 @Retro 審計時的版本）
***

### 版本號規則
major 版本（+1）：
  - 章節結構重組（如 PROPOSAL-015 lead.md 重整）
  - Persona 或角色邊界重大調整
  - 向下不相容的規則變更

minor 版本（+1）：
  - 新增章節或條文
  - 修改現有條文語意
  - 修正錯誤或補充說明

### 初始版本
所有現有 Rules 文件在首次加入版本標頭時
統一標注為 v1.0，
修改日期為實際加入版本標頭的日期。
```

## 提案執行後版本更新義務

每份提案執行完成後，
@Lead 在合併前必須執行以下版本更新：

Step 1：識別本次提案修改的所有 Rules 文件

禁止：
提案執行合併後，
對應 Rules 文件的版本標頭未更新。
版本標頭更新是提案執行 DoD 的必要項目。

### 修改項目四：Rules 回滾機制

```markdown
// 修改位置：retro.md 版本管理章節（新增）

## Rules 回滾機制

### 回滾觸發條件
提案執行後發現以下任一情況，
觸發回滾評估：

1. 🔴 CRITICAL：
   Rules 修改導致 Agent 行為出現
   系統性偏差（連續 ≥ 2 次任務異常）

2. 🟡 WARNING：
   Rules 修改與其他 Rules 產生語意衝突
   （@Retro 審計或 @Lead 協調時發現）

3. 🟡 WARNING：
   User 明確要求回滾至指定版本

### 回滾流程

Step 1：@Retro 或 @Lead 識別回滾需求，
        向 User 回報：
        【回滾評估報告】🟡 / 🔴
        受影響文件：{文件名}
        當前版本：v{x.y}
        建議回滾至：v{x.y-1}
        回滾原因：{具體描述}
        回滾影響：{會失去哪些修改}

Step 2：User 確認回滾指令

Step 3：@Lead 執行回滾：
        依 RULES_VERSION_INDEX.md 記錄，
        還原 Rules 文件至指定版本
        更新版本標頭：
        版本：v{回滾後版本}
        修改摘要：「回滾至 v{x.y}，原因：{原因}」

Step 4：回滾完成後，
        @Retro 執行增量審計，
        確認回滾後系統狀態一致

禁止：
未經 User 確認執行任何 Rules 文件回滾。
回滾操作屬於 PROPOSAL-013 豁免記錄
需記錄的授權行為。
```

### 修改項目五：@Retro 審計時的版本確認步驟

```markdown
// 修改位置：retro.md 審計流程章節（新增步驟）

## 審計前版本確認

@Retro 每次執行審計前，
必須先執行版本確認步驟：

Step 1：讀取 RULES_VERSION_INDEX.md
        確認「版本差異速查」區塊

Step 2：識別自上次審計後有版本變更的文件

Step 3：審計策略調整：
        - 有版本變更的文件：執行完整審計
        - 無版本變更的文件：執行輕量審計
          （確認無環境變化導致規則失效即可）

Step 4：審計完成後更新 RULES_VERSION_INDEX.md：
        - 更新所有文件的「審計基準版本」
          為當前版本
        - 填寫「本次審計日期」

輕量審計定義：
僅確認文件的現有規則
在當前系統狀態下仍然有效，
不執行評分或改善識別。
預計時間：每份文件 ≤ 5 分鐘
```

## 七、備註

- 本提案是 19 份提案中
  唯一涉及「所有 Rules 文件同時修改」的提案
  （為 12 份文件加入版本標頭），
  建議以批次腳本方式執行，
  確保格式一致性。

- 版本標頭採「輕量自描述」設計哲學：
  5 個欄位（版本、最後修改、修改提案、
  修改摘要、審計基準）在不依賴任何外部工具的情況下
  提供足夠的版本追蹤資訊。

- RULES_VERSION_INDEX.md 與
  PROPOSAL_INDEX.md（PROPOSAL-016）
  共同構成系統「元資訊層」：
  PROPOSAL_INDEX.md 追蹤「計畫做什麼」，
  RULES_VERSION_INDEX.md 追蹤「已做了什麼」，
  兩者合用可完整呈現系統的演進狀態。

- 審計分層策略（完整審計 vs. 輕量審計）
  是本提案對 @Retro 審計效率的直接優化：
  當系統穩定後，大多數 Rules 文件
  在多個審計週期中不會有版本變更，
  輕量審計可將這些文件的審計時間從
  每份 ~30 分鐘降至 ≤ 5 分鐘，
  顯著提升審計整體效率。

- 本提案新增約 +200 tokens 至 retro.md，
  RULES_DESIGN_GUIDE 新增約 +120 tokens，
  均在預算範圍內。
  RULES_VERSION_INDEX.md 為獨立管理文件，
  不計入 Rules Token 預算。
