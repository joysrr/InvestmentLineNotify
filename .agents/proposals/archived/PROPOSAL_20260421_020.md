## 一、問題描述

### 根因分類

**類型**：系統性職責分散 + 數值門檻硬寫分散（多層級架構缺陷）

### 問題陳述

#### 問題一：安全審查職責分散（主要問題）

現行系統的安全相關判斷分散於三個層級，缺乏專責 Agent：

| 層級          | 文件                                                                                                  | 承擔的安全職責                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Rules 層      | `reviewer.md` §「審查準則」第 3 條（安全性審查思維）+ §「系統關鍵路徑錯誤處理 Checklist」5 條關鍵路徑 | 金鑰暴露 / initData 驗證缺失 / 錯誤訊息洩漏 / Token 時效 / strategyWeight 審計 / 併發原子鎖 |
| Task 層       | `tasks/security-review.md`                                                                            | 金鑰憑證 / Telegram-Token 時效鐵律 / API 端點安全 / 併發與原子性                            |
| Tech-stack 層 | `tech-stacks/file-based-storage.md` / `tech-stacks/telegram-mini-app.md`                              | 原子鎖鐵律、initData 24h 時效                                                               |

**影響**：

1. `@Reviewer` 需同時兼顧**程式碼品質** + **安全性** + **DoD Checklist**，專注力分散可能導致資安判斷被當作次要項目
2. 新增資安範疇條目時需修改多處（rules/reviewer.md + tasks/security-review.md + 各 tech-stacks），難以維護
3. 安全判斷缺乏**專業視角聚焦**，`@Reviewer` 為全域審查角色，不專精於資安威脅模型

#### 問題二：數值門檻硬寫分散於多份 Rules

系統中多項可調整的數值門檻（複審上限、重測上限、巡邏週期、過期門檻、提案規模警示等）**散落於多份 Rules 且硬寫**，缺乏單點配置：

| 門檻類型             | 當前硬寫位置                        | 分散數         |
| -------------------- | ----------------------------------- | -------------- |
| 審查複審上限（2 次） | `reviewer.md` + `assistant.md` P-01 | 2 處           |
| QA 重測上限（3 次）  | `qa.md` + `assistant.md` P-02       | 2 處           |
| 豁免累積警示（5 筆） | `lead.md` + `assistant.md` P-10     | 2 處           |
| 巡邏週期（3 對話）   | `assistant.md` + `retro.md`         | 2 處           |
| 巡邏超時（5 對話）   | `assistant.md`                      | 1 處           |
| PENDING 三狀態過期   | `assistant.md`                      | 1 處           |
| 提案規模警示 3 門檻  | `retro.md`                          | 1 處           |
| Token 預算 2 項      | `RULES_DESIGN_GUIDE.md` §二         | 1 處（已集中） |

**影響**：User 欲調整任一門檻（如將審查複審上限從 2 改為 3）需同時修改多份 Rules 文件；遺漏任何一處會造成 Agent 行為不一致。

### 問題影響層級

- **主要問題（問題一）**：影響範圍為每次程式碼審查階段；資安風險識別可靠性下降
- **次要問題（問題二）**：影響門檻維護作業；易產生規則配置不一致
- 風險等級：🟡 中（非立即危害，屬系統演進品質）

## 二、根因分析

### 直接根因（問題一）

系統演進早期（PROPOSAL-001~019 期間），安全判斷設計**依附於 `@Reviewer` 的通用審查職責**，未視為獨立領域。隨著系統新增 Token 時效（PROPOSAL-020_001）+ 資料刪除零容忍（PROPOSAL-009）+ strategyWeight 縱深防禦（PROPOSAL-005/013）+ 併發原子性（PROPOSAL-020_001）等多項資安專業規範後，資安範疇已累積到需專責 Agent 統籌的規模。

### 直接根因（問題二）

各 Rules 在建立時獨立引入各自的數值門檻，設計時未預期「這些門檻將來可能需統一調整」。每次新增門檻都採「在使用處硬寫」的模式，累積成分散現況。

### 系統根因

缺乏兩項設計模式的明文規範：

1. **Agent 職責分離原則**（Single Responsibility for Agents）：當某領域（如安全）跨越多個觸發情境且需要專業視角時，應提煉為獨立 Agent 而非讓現有 Agent 兼差。
2. **系統參數集中配置原則**（Config Centralization）：所有可調整數值門檻應集中於單一配置點，各 Rules 僅引用不硬寫。

PROPOSAL-020 執行後，這兩個設計模式應納入 `RULES_DESIGN_GUIDE.md` 作為未來新 Agent 或新門檻的指引。

### User 已識別的額外設計風險

在提案討論階段，User 明確提出須防範 `@Security` 與 `@Reviewer` **循環退件分歧**的風險。本提案在設計中納入**四層防線**（職責互斥 + 平行審查 + 衝突仲裁 + 共用計數器），避免兩個審查 Agent 間的乒乓退件。

```markdown
4. `@Frontend` / `@Backend` **一次性修正**所有問題後重新送審
5. 複審時再次**同時派發**，計入 `REVIEW_CYCLE_LIMIT` 共用計數（依 `RULES_DESIGN_GUIDE.md §十四`）

**絕對禁止** `@Lead` 序列派發（先 @Reviewer 退件 → 修正 → 送審 → 再 @Security 退件），造成雙重循環。

### 衝突仲裁規則（防線 3）

若兩份報告建議**互相矛盾**（例：@Reviewer 建議快取、@Security 要求每次驗證不得快取），依優先級：

| 衝突類型                         | 仲裁規則                                                                                                   |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 安全性 vs 可讀性                 | **`@Security` 優先**（零容忍，無例外）                                                                     |
| 安全性 vs 效能                   | **`@Security` 優先**，但 `@Security` 必須提供 **3 個緩解方案**（含效能折衷選項）供 @Backend/@Frontend 選擇 |
| 皆無明確歸屬                     | `@Lead` 升級 User 裁決                                                                                     |
| 越界審查（任一方審對方專屬範疇） | `@Lead` 判定該項**無效**，不計入 BLOCKER，通知越界方撤回                                                   |

### 共用計數器規則（防線 4）

- `@Reviewer` + `@Security` 複審次數**共用**一個計數器（`REVIEW_CYCLE_LIMIT`）
- 任一方於同一任務的複審都會 +1
- 達上限時，**哪一方未通過就產對應通知**（`REVIEW_QUALITY` 或 `SECURITY_AUDIT_FAIL`）
- 兩方皆未通過時同時產出雙通知
- 可調整：修改 `RULES_DESIGN_GUIDE.md §十四` 之 `REVIEW_CYCLE_LIMIT` 即生效
```
