## 一、問題描述

### 根因分類

**類型**：業務脈絡錨定缺失（QW-06）

### 問題陳述

`reviewer.md` 的審查標準與 Checklist 採用通用描述，
缺乏與系統實際業務脈絡（Telegram Bot、
投資訊號推送、Node.js ESM 架構）的明確錨定。

#### 具體問題條文

```
現況（通用描述）：
「審查程式碼是否符合最佳實踐」
「確認功能實作符合需求」
「檢查錯誤處理是否完整」

問題：
「最佳實踐」未定義為哪個技術棧的最佳實踐
「符合需求」未說明需求來源（Planner ticket？User 指令？）
「錯誤處理」未列出系統關鍵路徑
  （Telegram API 錯誤 / 投資訊號計算失敗 / 資料寫入失敗）
→ @Reviewer 在執行審查時缺乏系統專屬的判斷錨點，
  可能對關鍵業務路徑的問題評估不足
```

### 問題影響層級

- 影響範圍：@Reviewer 每次執行程式碼審查
- 風險分類：審查品質不足（系統專屬關鍵路徑
  若未被明確列出，審查可能流於形式）
- 風險等級：🟡 中風險

## 三、提案內容

### 修改項目一：技術棧錨定

```markdown
// 修改位置：reviewer.md 審查標準章節

// 修改前
審查程式碼是否符合最佳實踐。

// 修改後
審查程式碼是否符合本系統技術棧最佳實踐：

- 語言：Node.js ESM（import/export，禁止 require）
- 架構：File-based 資料儲存（JSON / CSV，無資料庫）
- 非同步：async/await 優先，禁止 callback hell
- 模組化：單一職責，禁止單檔超過 300 行
```

### 修改項目二：需求來源明確化

```markdown
// 修改位置：reviewer.md 審查標準章節

// 修改前
確認功能實作符合需求。

// 修改後
確認功能實作符合以下需求來源（依優先順序）：

1. @Planner 產出的 Sprint Ticket 驗收標準（DoD）
2. @Architect 產出的技術規格文件
3. User 在本次對話中的明確指令
4. 上述三者均無描述時，報告為「需求來源不明」，
   暫緩審查並向 @Lead 請求確認
```

### 修改項目三：關鍵業務路徑錯誤處理 Checklist

```markdown
// 修改位置：reviewer.md 審查 Checklist 章節（新增）

## 系統關鍵路徑錯誤處理 Checklist

以下路徑必須有明確的錯誤捕捉與處理邏輯，
缺失任一項視為審查不通過：

### Telegram 推送路徑

- [ ] Telegram Bot API 呼叫失敗有 try/catch
- [ ] API 失敗有重試機制（建議 ≤ 3 次）
- [ ] 重試失敗後有錯誤日誌寫入
- [ ] 不得因推送失敗導致程序崩潰

### 投資訊號計算路徑

- [ ] 計算輸入值有型別驗證
- [ ] 除零、NaN、Infinity 情況有防護
- [ ] 計算異常不得影響其他訊號的正常推送

### 資料寫入路徑

- [ ] File-based 寫入有 try/catch
- [ ] 寫入失敗有備援或回滾機制
- [ ] 不得在寫入失敗時靜默忽略錯誤

### strategyWeight 異動路徑

- [ ] 數值變更前有現有值讀取與記錄
- [ ] 變更後有驗證邏輯（數值範圍 / 加總限制）
- [ ] 異動記錄寫入審計日誌
```
