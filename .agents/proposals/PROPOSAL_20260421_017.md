## 一、問題描述

### 根因分類
**類型**：跨 Agent 通知標準不一致（LT-04）

### 問題陳述
`assistant.md` 的巡邏回報機制
與系統中其他 Agent 的回報通知格式
缺乏統一的分級標準，
導致 @Lead 在接收來自不同 Agent 的通知時
需要適應不同的格式與優先級語言。

#### 具體問題
```
現況：
@Assistant 巡邏回報：使用 🔴 / 🟡 / 🟢 三色分級
@Backend DoD 自評：使用 ✅ / ⚠️ 二元標記
@QA 測試回報：使用 通過 / 失敗 文字描述
@Reviewer 複審報告：使用 ✅ / ❌ 二元標記
@Planner Sprint 回報：使用自由格式

問題一：
同一優先級概念在不同 Agent 使用不同符號，
@Lead 需要在腦中做格式轉換：
「⚠️ 是什麼程度的問題？
 等同於 🟡 還是 🔴？」

問題二：
PROPOSAL-010（@Assistant 異常分級）
定義了 🔴 / 🟡 / 🟢 三級，
但其他 Agent 的回報未對齊此分級，
系統層級缺乏統一的通知語言。

問題三：
@Lead 在彙整多個 Agent 的回報時，
格式不一致增加了彙整判讀的認知負擔，
尤其在多任務並行時最為明顯。
```

### 問題影響層級
- 影響範圍：所有 Agent 向 @Lead 回報的通知
- 風險分類：跨 Agent 溝通效率
  （格式不一致本身不造成功能錯誤，
   但在高頻使用時累積顯著認知負擔）
- 風險等級：🟢 低風險（P3）
  （觸發時機：MT-01 完成後，
   系統進入穩定期時統一優化）

## 二、根因分析

### 直接根因
各 Agent Rules 在不同時期由不同角度撰寫，
回報格式各自獨立設計，
未參照統一的通知分級標準。

### 系統根因
系統缺乏「跨 Agent 通訊協定」，
RULES_DESIGN_GUIDE（PROPOSAL-003）
建立後應將通知分級標準
作為必要章節納入，
確保未來新 Agent 的回報格式從一開始就對齊。

### 前置依賴
- PROPOSAL-010（@Assistant 異常分級）：
  三色分級 🔴 / 🟡 / 🟢 已在此提案定義，
  本提案以此為基礎向全系統擴展。
- PROPOSAL-003（RULES_DESIGN_GUIDE）：
  通知分級標準應同步寫入 RULES_DESIGN_GUIDE，
  建議在 PROPOSAL-003 執行時一併納入。

## 三、提案內容

### 全系統統一通知分級標準

```markdown
// 系統通知分級標準（System Notification Level Standard）
// 寫入位置：RULES_DESIGN_GUIDE.md（由 PROPOSAL-003 建立）
// 各 Agent Rules 引用此標準

## 通知分級定義

| 級別 | 符號 | 含義 | @Lead 處理時限 |
|------|------|------|--------------|
| CRITICAL | 🔴 | 需立即處理，可能阻斷系統執行 | 本次對話立即處理 |
| WARNING | 🟡 | 需關注，不阻斷但有潛在風險 | 本次對話結束前處理 |
| INFO | 🟢 | 資訊性通知，無需立即行動 | 下次巡邏前處理或記錄 |
| DONE | ✅ | 任務 / 項目已完成 | 無需處理，確認即可 |
| BLOCKED | ❌ | 執行被阻斷，需要外部解除 | 本次對話立即處理 |

## 通知格式標準

所有 Agent 向 @Lead 的回報
必須在標題行包含對應級別符號：

格式：
【@{Agent} {回報類型}】{級別符號} {簡短描述}

範例：
【@Backend DoD 自評】✅ 任務完成，全數通過
【@Backend DoD 自評】⚠️ → 🟡 WARNING：{n} 項待說明
【@Assistant 巡邏摘要】🔴 CRITICAL：發現高優異常
【@QA 測試回報】❌ BLOCKED：P0 必測失敗，需修正後重測
【@Reviewer 複審報告】✅ 通過（歷經 2 次複審）
```

### lead.md 修改項目

```markdown
// 修改位置：lead.md 通知接收章節（新增）

## 通知接收與處理優先級

@Lead 接收到各 Agent 回報時，
依通知分級標準處理：

| 收到符號 | 處理優先級 | 標準動作 |
|---------|----------|---------|
| 🔴 CRITICAL | 最高，立即處理 | 暫停其他任務，處理阻斷原因 |
| ❌ BLOCKED | 最高，立即處理 | 確認阻斷原因，派發修正任務 |
| 🟡 WARNING | 高，本對話內處理 | 評估影響，決定是否升級 |
| ✅ DONE | 一般，確認即可 | 更新 PENDING_ACTIONS.md 狀態 |
| 🟢 INFO | 低，記錄即可 | 寫入巡邏日誌或待辦 |

### 多通知並行處理順序
同一對話收到多個 Agent 回報時：
1. 先處理所有 🔴 / ❌ 通知
2. 再處理 🟡 通知
3. ✅ / 🟢 通知在前兩類處理完後統一確認

禁止：
@Lead 在存在未處理 🔴 通知的情況下
繼續派發新任務。
```

### 各 Agent 回報格式對齊說明

本提案不逐一修改每份 Rules 的回報格式，
而是透過以下機制實現漸進對齊：

```markdown
// 對齊機制

階段一（本提案執行時）：
在 RULES_DESIGN_GUIDE 建立通知分級標準
在 assistant.md 更新巡邏摘要格式
在 lead.md 新增通知接收處理規則

階段二（各 Agent Rules 下次修改時）：
各 Agent Rules 在下次執行相關提案時，
同步將回報格式對齊通知分級標準
（PROPOSAL-012 DoD 自評格式已部分對齊，
 ⚠️ 符號可直接映射為 🟡 WARNING）

階段三（PROPOSAL-015 lead.md 重整時）：
確認 lead.md 通知接收章節
與所有 Agent 回報格式完整對齊
```

## 七、備註

- 本提案採用「漸進對齊」策略而非
  「一次全面修改所有 Rules」，
  原因是格式統一是基礎設施工作，
  應在各 Rules 的功能性修改中自然完成，
  避免為了格式統一而產生大量
  純格式修改的 commit，增加審查負擔。

- 5 個通知符號（🔴 ❌ 🟡 ✅ 🟢）
  設計為直覺可識別：
  紅色系 = 需立即行動
  黃色 = 需關注
  綠色系 = 正常狀態
  此設計無需額外記憶，降低 @Lead 的認知負擔。

- 本提案中「禁止 @Lead 在存在未處理 🔴 通知
  的情況下繼續派發新任務」是整個通知系統
  最重要的約束條款，確保 CRITICAL 級別
  通知不會在多任務並行中被遺漏。

- 兩份文件合計新增約 +130 tokens，
  均在預算範圍內。
  RULES_DESIGN_GUIDE 新增章節
  不計入任何 Agent Rules 的 Token 預算。
