## 問題描述

**發現位置**：`webapp/package.json`、`package.json`、`webapp/src/api/index.js`、`src/test/` 目錄

**問題摘要**：後端 API 與前端 Mini App 之間完全沒有整合測試，API 回傳格式異動或新增 endpoint 後，前端是否能正確消費完全依賴人工部署後目視驗證，導致「上線才知道壞了」。

**詳細描述**：

**現況完整盤點：**

`webapp/package.json` 中 `dependencies` 僅有 Vue 3、ECharts、vue-router，**無任何測試套件**（無 Vitest、無 Playwright、無 Testing Library）。`npm test` 的 script 定義為 `vitest run src/test`，只執行後端邏輯測試，API server 層與 webapp 層均不在覆蓋範圍 。

**Mini App 呼叫了 11 個 API endpoints**，分散於 `webapp/src/api/index.js` ：

| Endpoint | 用途 |
|---|---|
| `GET /api/reports` | 每日報告列表 |
| `GET /api/reports/weekly` | 週報 |
| `GET /api/reports/monthly` | 月報 |
| `GET /api/reports/snapshots` | 日粒度快照 |
| `GET /api/reports/snapshots/weekly` | 週粒度快照 |
| `GET /api/reports/snapshots/monthly` | 月粒度快照 |
| `GET /api/news` | 新聞 |
| `GET /api/status` | 系統狀態 |
| `GET /api/report/news` | 報告新聞 |
| `GET /api/strategy-config` | 策略設定 |
| （`X-Telegram-Init-Data` header 認證） | 每個請求都帶 |

**此次問題的根本結構**：API 回傳 schema 異動或 endpoint 路徑改動時，沒有任何機制在「部署前」攔截。開發者調整了 API 或 webapp，兩者的整合狀況只能等到 Telegram Mini App 被實際開啟時才被肉眼發現，且錯誤訊息在 Telegram WebView 中無法輕易取得（不像桌面瀏覽器有 DevTools）。

***

## 根因分析

| 根因層級 | 代碼 | 分析說明 |
|---------|------|---------|
| 需求層（Requirements） | `REQ` | 從未定義 API ↔ Webapp 整合測試的 DoD 條件，「API 調整完要跑整合測試」這條規範不存在 |
| 開發層（Development） | `DEV` | webapp 目錄在建立時未配置任何測試框架，沒有基礎建設，自然沒有測試習慣 |

## 建議修改對象與內容

本提案拆成三個獨立執行的修改，由易到難排序：

***

### 修改一（P0）：後端 API Contract 測試
**在現有 Vitest 中加入 API server 的 contract 測試，確保每個 endpoint 的回傳 schema 結構正確**

**目標 Agent**：`@Backend` + `@QA`
**目標文件**：`src/test/integration/apiContract.test.mjs`（新建）
**需要安裝的套件**：

```bash
# 根目錄執行（後端）
npm install --save-dev supertest
```

> `supertest` 是 Node.js 後端 HTTP 測試的業界標準，直接對 Fastify instance 發 request，**不需要啟動真實 server**，與現有 Vitest 完全相容，零環境依賴。

**建議新建的測試檔案骨架**：

```javascript
// src/test/integration/apiContract.test.mjs
// API Contract Test — 驗證每個 endpoint 回傳的 schema 結構符合 webapp 的消費預期
// 使用 supertest 直接注入 Fastify app，不依賴真實網路或外部服務

import { describe, it, expect, beforeAll, afterAll } from 'vitest';
import supertest from 'supertest';
import { buildApp } from '../../api/server.mjs'; // 需確認匯出方式

let app;
let request;

beforeAll(async () => {
  app = await buildApp(); // Fastify app factory
  await app.ready();
  request = supertest(app.server);
});

afterAll(async () => {
  await app.close();
});

// ── /api/status ────────────────────────────────────────────────
describe('GET /api/status', () => {
  it('回傳 200 且包含 status 欄位', async () => {
    const res = await request
      .get('/api/status')
      .set('X-Telegram-Init-Data', 'dev-bypass')
      .expect(200);

    expect(res.body).toHaveProperty('status');
  });
});

// ── /api/reports ───────────────────────────────────────────────
describe('GET /api/reports', () => {
  it('回傳陣列且每筆包含 date 與 content 欄位', async () => {
    const res = await request
      .get('/api/reports?limit=1')
      .set('X-Telegram-Init-Data', 'dev-bypass')
      .expect(200);

    expect(Array.isArray(res.body)).toBe(true);
    if (res.body.length > 0) {
      expect(res.body[0]).toHaveProperty('date');
    }
  });
});

// ── /api/reports/snapshots ─────────────────────────────────────
describe('GET /api/reports/snapshots', () => {
  it('回傳陣列且 schema 符合 snapshotAggregator 定義', async () => {
    const res = await request
      .get('/api/reports/snapshots?limit=1')
      .set('X-Telegram-Init-Data', 'dev-bypass')
      .expect(200);

    expect(Array.isArray(res.body)).toBe(true);
    if (res.body.length > 0) {
      const s = res.body[0];
      // 驗證 snapshotAggregator.normaliseSnapshot 定義的必要欄位
      expect(s).toHaveProperty('date');
      expect(s).toHaveProperty('qty0050');
      expect(s).toHaveProperty('qtyZ2');
      expect(s).toHaveProperty('totalLoan');
    }
  });
});

// ── /api/strategy-config ──────────────────────────────────────
describe('GET /api/strategy-config', () => {
  it('回傳 200 且包含策略設定物件', async () => {
    const res = await request
      .get('/api/strategy-config')
      .set('X-Telegram-Init-Data', 'dev-bypass')
      .expect(200);

    expect(typeof res.body).toBe('object');
    expect(res.body).not.toBeNull();
  });
});

// 其餘 endpoints（/api/news, /api/report/news, weekly/monthly）依樣補齊
```

### 修改二（P1）：webapp 加入 Vitest + Vue Test Utils 元件測試
**確保關鍵 Vue 元件在 API 回傳格式異動時能早期失敗**

**目標 Agent**：`@Frontend` + `@QA`
**需要安裝的套件**：

```bash
# webapp 目錄下執行
cd webapp
npm install --save-dev vitest @vue/test-utils @vitejs/plugin-vue jsdom
```

**建議更新 `webapp/package.json`**：

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "test": "vitest run",
    "test:watch": "vitest"
  },
  "devDependencies": {
    "@vitejs/plugin-vue": "^5.2.1",
    "@vue/test-utils": "^2.4.6",
    "jsdom": "^25.0.0",
    "vite": "^8.0.8",
    "vitest": "^4.1.4"
  }
}
```

**建議新建 `webapp/vite.config.js` 補充 test 設定**：

```javascript
// webapp/vite.config.js
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';

export default defineConfig({
  plugins: [vue()],
  test: {
    environment: 'jsdom',
    globals: true,
  },
});
```

**測試策略**：使用 `vi.mock` 攔截 `webapp/src/api/index.js`，注入固定 mock 資料，驗證元件在 API 資料更改 schema 時是否 render 正確或優雅降級。

### 修改三（P2）：`TEST_MAPPING.md` 加入 API + Webapp 整合測試條目

**目標 Agent**：`@QA`
**目標文件**：`docs/TEST_MAPPING.md`

**建議新增的映射列**：

```markdown
| `src/api/server.mjs` + 所有 route handlers | `src/test/integration/apiContract.test.mjs` | 整合測試 | API Contract 驗證：endpoint 可達性、回傳 status code、schema 結構 |
| `webapp/src/api/index.js` + 關鍵 Views | `webapp/src/test/` (新建目錄) | 單元測試 | Vue 元件消費 API mock 資料時的 render 正確性 |
```

**建議新增的 `API 異動 SOP`**：

```markdown
## API 異動 SOP（異動後必做）

修改以下任一項目後，**必須在 merge 前**執行 `npm test`（後端 contract 測試）與 `cd webapp && npm test`（前端元件測試）：

- `src/api/` 下任何 route handler 的回傳 schema
- `webapp/src/api/index.js` 的 endpoint 路徑或參數
- `swagger.json` 的 schema 定義

> ⚠️ 若僅在 Telegram Mini App 實際開啟後才發現問題，代表整合測試不足，需回補對應測試案例。
```

## 預期效果

套用此提案後，Mini App 顯示失敗問題的被發現時間點從「部署後目視驗證」提前為「PR merge 前 CI 失敗攔截」：

```
【現行流程】
調整 API/webapp → commit → 部署 VM → 開啟 Telegram Mini App → 發現壞了 → 不知道哪裡錯

【提案後流程】
調整 API/webapp → npm test 失敗 → 馬上知道哪個 endpoint / 哪個元件壞了 → 修完再 commit
```

此外，`supertest` 的測試輸出會明確顯示哪個 endpoint 回傳了 4xx 或 schema 不符，**不再需要在 Telegram WebView 中猜錯誤原因**。

***

## 套件選擇理由

| 套件 | 用途 | 選擇理由 |
|---|---|---|
| `supertest` | 後端 API contract 測試 | 與 Fastify 原生相容；不啟動真實 server；在現有 Vitest 中直接使用，零學習成本 |
| `@vue/test-utils` | Vue 元件單元測試 | Vue 官方測試工具，與 Vite + Vitest 生態完全整合 |
| `jsdom` | 前端測試 DOM 環境 | Vitest browser 環境模擬，輕量無需 Playwright |

> Playwright E2E 測試（真實 browser + 真實 server）屬於更進階的做法，此提案暫不納入，待基礎整合測試建立後再評估是否需要。
