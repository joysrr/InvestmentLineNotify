### DEC-01: 正向模擬 - `priceZ2` 選填時的預設行為

**背景**: API 允許只傳 `price0050`，`priceZ2` 為選填 (D1 決定按比例聯動)

| 選項                       | 說明                                                                   |
| -------------------------- | ---------------------------------------------------------------------- |
| **A: 當前比例聯動** (推薦) | `priceZ2 = price0050 * (currentZ2 / current0050)` 使用**即時最新比例** |
| B: 固定歷史平均比例        | 用過去 30 天平均比例，較穩定但可能過時                                 |
| C: 固定 1:0.5 (理論槓桿比) | 00675L 理論上是 0050 的 0.5 倍，忽略溢價/折價                          |

**優缺點分析**:

| 選項  | 優點                               | 缺點                                       | 風險      |
| ----- | ---------------------------------- | ------------------------------------------ | --------- |
| **A** | 反映當前市場真實聯動、溢價自動納入 | 比例可能因單日波動而噪聲大                 | ⭐ 低     |
| B     | 平滑單日異常                       | 需額外儲存/計算平均比例、延遲反應          | ⭐⭐ 中   |
| C     | 簡單、理論正確                     | 忽略溢價/折價，長期偏差大 (實際常 0.6-0.7) | ⭐⭐⭐ 高 |

**我的推薦**: **A - 當前比例聯動**
**理由**: 最貼近「如果 0050 以此價收盤，00675L 會在哪裡」的真實市場邏輯。溢價變化本身就是市場情緒指標，納入模擬反而更真實。若擔心噪聲，可在 UI 顯示「假設聯動比例: 1:0.66 (當前)」讓用戶知情。

### DEC-02: 正向模擬 - `highArr` / `lowArr` 最後一根 K 棒的處理

**背景**: §16.3 程式碼使用 `Math.max(high, simulatedPrice)` / `Math.min(low, simulatedPrice)`

| 選項                        | 說明                                                                                |
| --------------------------- | ----------------------------------------------------------------------------------- |
| **A: 當前邏輯** (推薦)      | `high = max(原high, 模擬價)`, `low = min(原low, 模擬價)` - 確保模擬價在高低價區間內 |
| B: 高低價同比例調整         | `high = 原high * (模擬價/原close)`, `low = 原low * (模擬價/原close)` - 保持振幅比例 |
| C: 高低價不變，僅替換 close | 僅 `close = 模擬價`，high/low 維持原值 (可能導致 close > high 或 close < low)       |

**優缺點分析**:

| 選項  | 優點                                                         | 缺點                                                         | 風險      |
| ----- | ------------------------------------------------------------ | ------------------------------------------------------------ | --------- |
| **A** | 保證 OHLC 邏輯自洽、ATR/KD 計算不會因 close 超出高低價而異常 | 縮小當日振幅，可能低估波動指標                               | ⭐ 低     |
| B     | 保持原始振幅特性                                             | 若模擬價遠離原 close，產生不合理的高低價 (如漲停卻 low 極低) | ⭐⭐ 中   |
| C     | 最忠實保留原始資料                                           | 違反 OHLC 定義，導致指標計算錯誤 (RSI/KD/ATR 會噴錯)         | ⭐⭐⭐ 高 |

**我的推薦**: **A - 當前邏輯 (max/min 夾住)**
**理由**: OHLC 定義要求 `low ≤ close ≤ high`。選項 A 是唯一保證此不變量的方法。雖然縮小振幅，但模擬本質是「單一收盤價情境」，當日內部波動結構無法從單一價格推導，保守處理較安全。

| 選項  | 優點                                                                | 缺點                                                                  | 風險      |

| 選項  | 優點                                                     | 缺點                                                     | 風險    |

### DEC-05: 歷史資料月份缺失時的處理策略

**背景**: §16.3 需 13 月 OHLCV，實際檔案可能遺漏某月

| 選項                                     | 說明                                                                    |
| ---------------------------------------- | ----------------------------------------------------------------------- |
| **A: 嚴格模式 - 缺月即 409** (推薦)      | 任一必要月份檔案不存在 → 回傳 409 `歷史資料不完整，無法模擬`            |
| B: 寬鬆模式 - 向前填補                   | 缺月用前一個月最後收盤價生成扁平 OHLCV，標記 `fallback: 'filled_flat'`  |
| C: 部分可用模式 - 僅檢查核心指標所需月份 | RSI/KD/MA20/ATR 只需 2 月、MA60 需 3 月、MA240 需 12 月，依目標動態判斷 |

**優缺點分析**:

| 選項  | 優點                                         | 缺點                                                                  | 風險      |
| ----- | -------------------------------------------- | --------------------------------------------------------------------- | --------- |
| **A** | 行為可預測、強迫資料管線修補缺口、無靜默錯誤 | 缺月時完全不可用、用戶體驗中斷                                        | ⭐ 低     |
| B     | 服務可用性高                                 | 扁平資料會扭曲 RSI/KD/MACD (無波動)、MA240 嚴重失真、給用戶虛假安全感 | ⭐⭐⭐ 高 |
| C     | 彈性                                         | 複雜度高、同一請求不同目標可用性不同、邏輯難測試                      | ⭐⭐ 中   |

**我的推薦**: **A - 嚴格模式**
**理由**: 模擬器是「精確計算工具」，非「盡力服務」。缺月代表資料管線有問題，應回 409 強迫修補，而非產出不可信結果。UI 可顯示「資料更新中，請稍後再試」引導用戶。

### DEC-06: MA240 Fallback 觸發條件與行為

**背景**: §5.2 規定 MA240 不足 240 筆時 fallback，但未定義具體邏輯

| 選項                          | 說明                                                                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **A: 分級 Fallback** (推薦)   | 1) ≥240 筆 → 正常 MA240 2) 60-239 筆 → MA60 做代理 3) 20-59 筆 → MA20 代理 4) <20 筆 → `null` + `fallback: 'insufficient_data'` |
| B: 單一 Fallback - 用 MA60    | 不足 240 筆統一用 MA60，標記 fallback                                                                                           |
| C: 無 Fallback - 不足即不可用 | <240 筆直接回傳 `ma240: null, fallback: 'need_240_bars'`                                                                        |

**優缺點分析**:

| 選項  | 優點                                               | 缺點                                                                       | 風險    |
| ----- | -------------------------------------------------- | -------------------------------------------------------------------------- | ------- |
| **A** | 盡量提供最佳可用近似、漸進式降級、資料品質標籤精確 | 邏輯較複雜、需測試各臨界點                                                 | ⭐ 低   |
| B     | 簡單                                               | 60 筆時用 MA60 合理，但 100 筆時用 MA60 浪費資料                           | ⭐⭐ 中 |
| C     | 最誠實、無誤導                                     | 13 月資料 (約 260 筆) 正常應足夠，但新上市/資料遺漏時完全無 MA240 相關功能 | ⭐ 低   |

**我的推薦**: **A - 分級 Fallback**
**理由**: 實務上 13 月約 260 筆通常足夠，但為了系統健壯性，分級 fallback 確保「有資料就給最好的估算」。對應 §5.2 表格「可依現有邏輯 fallback，但必須顯示 fallback 標籤」。

### DEC-07: 指標計算函式的來源與版本鎖定

**背景**: §16.3 稱 `calculateIndicators(history)` 完整重算，但專案可能有多版本指標邏輯

| 選項                                                  | 說明                                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------------------ |
| **A: 復用現有 `src/modules/indicators/` 模組** (推薦) | 直接 import 策略引擎用的同一套計算函式，保證一致性                       |
| B: 複製一份到 simulator 目錄                          | 獨立演進、不受策略引擎重構影響                                           |
| C: 參數化注入                                         | `dataAdapter` 接收 `indicatorCalculator` 函式作為參數，測試時可注入 mock |

**優缺點分析**:

| 選項  | 優點                                                        | 缺點                                                   | 風險      |
| ----- | ----------------------------------------------------------- | ------------------------------------------------------ | --------- |
| **A** | **單一真實來源**、策略引擎修正 bug 自動同步模擬器、零重複碼 | 策略引擎 breaking change 會波及模擬器 (但這通常是好事) | ⭐ 低     |

**我的推薦**: **A - 復用現有模組**
**理由**: 模擬器核心價值在於「與實際策略引擎完全一致」。任何指標邏輯差異都是 bug。測試時直接用真實 `calculateIndicators`，整合測試驗證一致性即可。

## 3. 解析型反向推導參數

### DEC-08: 維持率反推 - 00675L (Z2) 價格假設

**背景**: §16.4.1 程式碼註解有 `fixedZ2Ratio` 參數，D1 決定正向模擬用同比例，反向是否一致？

| 選項 | 說明 |
| -------------------------------------------- | -------------------------------------------------------------- | ------------------- |
| **A: 同比例聯動 (fixedZ2Ratio=true)** (推薦) | `priceZ2 = price0050 * (currentZ2/current0050)` 與正向模擬一致 |
| B: Z2 價格固定 (fixedZ2Ratio=false) | 僅 0050 價格變動、00675L 鎖定當前價 |
| C: 使用者可選 | API 參數 `z2Mode: 'ratio'                                      | 'fixed'` 讓用戶決定 |

**優缺點分析**:

| 選項  | 優點                                      | 缺點                                                                   | 風險    |
| ----- | ----------------------------------------- | ---------------------------------------------------------------------- | ------- |
| **A** | 正向/反向邏輯對稱、心智模型一致、實作簡單 | 同樣有相關性破裂風險 (見 D1 分析)                                      | ⭐⭐ 中 |
| B     | 保守、風險可控                            | 不符合「0050 漲則 Z2 也漲」直覺、反推價格會偏高 (因 Z2 不分擔估值增長) | ⭐ 低   |
| C     | 彈性                                      | API 複雜化、用戶難以理解差異、需雙維護                                 | ⭐⭐ 中 |

**我的推薦**: **A - 同比例聯動**
**理由**: 正向/反向必須是可逆運算：`forward(reverse(target)) ≈ target`。若正向用比例、反向用固定，驗證步驟會失敗。相關性破裂風險在「假設」欄位揭露即可 (DEC-01 同)。

### DEC-10: MA240 偏離反推 - 迭代驗證次數上限

**背景**: §16.4.3 註解「需再正向模擬驗證，因 ma240 可能受新價格影響」

| 選項                        | 說明                                                            |
| --------------------------- | --------------------------------------------------------------- |
| **A: 單次驗證** (推薦)      | 估算 → 正向模擬一次 → 若誤差 < 容忍度 (0.1%) 回傳，否則標記近似 |
| B: 迭代修正 (最多 3 次)     | 估算 → 模擬 → 依誤差調整 → 再模擬 → ... 收斂或達上限            |
| C: 無驗證，直接回傳解析估算 | 最快，但可能因 MA240 更新導致偏離                               |

**優缺點分析**:

| 選項  | 優點                                                              | 缺點                                                                   | 風險      |
| ----- | ----------------------------------------------------------------- | ---------------------------------------------------------------------- | --------- |
| **A** | 簡單、一致性 (所有解析解皆「估算+單次驗證」)、成本可控 (1 次模擬) | 極端情況誤差較大                                                       | ⭐ 低     |
| B     | 精度最高                                                          | 複雜度高、可能震盪不收斂、增加延遲                                     | ⭐⭐ 中   |
| C     | 最快                                                              | **不可接受**：解析解假設 MA240 不變，但新價格會進入 MA240 窗口改變均線 | ⭐⭐⭐ 高 |

**我的推薦**: **A - 單次驗證**
**理由**: MA240 窗口 240 筆，單一新價格權重 1/240 ≈ 0.4%，對均線影響極小。單次驗證誤差通常 < 0.05%，遠小於容忍度。迭代邊際收益遞減不值得複雜度。

### DEC-11: RSI 反推 - 二分搜尋初始搜尋範圍

**背景**: §16.4.4 程式碼用 `±30%`，D5 決定採用二分搜尋

| 選項                    | 說明                                                    |
| ----------------------- | ------------------------------------------------------- |
| **A: 固定 ±30%** (推薦) | `low = current * 0.7, high = current * 1.3` 簡單固定    |
| B: 動態依 ATR 計算      | `range = max(0.3, ATR/current * 3)` - 波動大時擴大搜尋  |
| C: 指數級擴展           | 從 ±10% 開始，找不到 → ±20% → ±40% → ±80% (D5 分析建議) |

**優缺點分析**:

| 選項  | 優點                                                     | 缺點                                                   | 風險    |
| ----- | -------------------------------------------------------- | ------------------------------------------------------ | ------- |
| **A** | 實作最簡單、99% 情況足夠 (RSI 30-70 對應價格通常在 ±20%) | RSI 目標極端 (如 5 或 95) 時可能搜尋不到               | ⭐ 低   |
| B     | 適應波動率                                               | 需額外計算 ATR、邏輯較複雜                             | ⭐ 低   |
| C     | 保證找到 (若存在)                                        | 可能多次完整模擬、最壞情況 4 輪 × 50 迭代 = 200 次模擬 | ⭐⭐ 中 |

**我的推薦**: **A - 固定 ±30% + 找不到即不可達**
**理由**: RSI 物理意義上 0-100 對應極端價格，±30% 已覆蓋幾乎所有合理 RSI 目標 (RSI=30 約 -15%，RSI=70 約 +15%)。若目標 RSI=5 要求 -50% 股價，本質上就是「不可達」，直接回傳 `reachable: false` 並給最近結果更誠實。

### DEC-12: 掃描方向 - 價單邊 vs 雙邊

**背景**: §16.5 `rangePct: 0.15` 定義 ±15%，但某些目標只需單邊

| 選項                   | 說明                                                       |
| ---------------------- | ---------------------------------------------------------- |
| **A: 雙邊掃描** (推薦) | 固定 `current * (1-range) 到 current * (1+range)` 共 60 步 |
| B: 目標導向單邊        | RSI 目標 30 (超賣) → 只掃下跌方向；KD 金叉 → 掃漲方向      |
| C: 自適應雙邊          | 先雙邊粗掃，發現目標單邊則細掃該側                         |

**優缺點分析**:

| 選項  | 優點                               | 缺點                                               | 風險    |
| ----- | ---------------------------------- | -------------------------------------------------- | ------- |
| **A** | 實作最簡單、覆蓋所有可能、結果對稱 | 浪費 ~50% 算力在不可能方向                         | ⭐ 低   |
| B     | 效率高 (30 步)                     | 需為每種目標硬編碼方向邏輯、KD/MACD 交叉方向不固定 | ⭐⭐ 中 |
| C     | 平衡                               | 複雜度高、邊界情況難測試                           | ⭐ 低   |

**我的推薦**: **A - 雙邊掃描**
**理由**: 60 步 × 50ms = 3 秒完全可接受。單邊優化省 1.5 秒但引入「目標→方向」映射表維護成本。KD 金叉在下跌途中也可能發生 (K/D 同步下行再轉折)，單邊假設不成立。

### DEC-13: 掃描步距 - 線性 vs 對數

**背景**: §16.5 `stepPct: 0.005` (0.5% 線性步距)

| 選項                   | 說明                                                                          |
| ---------------------- | ----------------------------------------------------------------------------- |
| **A: 線性步距** (推薦) | 價格等差數列：170, 170.85, 171.7, ...                                         |
| B: 對數步距            | 價格等比數列：每步漲 0.5% → 170, 170.85, 171.71, ... (實際上 0.5% 已接近對數) |
| C: 自適應步距          | 靠近目標時縮小步距                                                            |

**優缺點分析**:

| 選項  | 優點                    | 缺點                                                          | 風險    |
| ----- | ----------------------- | ------------------------------------------------------------- | ------- |
| **A** | 簡單、均勻覆蓋、好理解  | 高價股步距絕對值大、低價股步距小 (但 0.5% 相對步距已自動調整) | ⭐ 低   |
| B     | 理論更正確 (百分比思維) | 0.5% 相對步距本質上已是對數式、差異極微                       | ⭐ 低   |
| C     | 精度好                  | 複雜、需先知道「靠近目標」在哪                                | ⭐⭐ 中 |

**我的推薦**: **A - 線性相對步距 (0.5%)**
**理由**: `stepPct: 0.005` 本質上就是相對步距 (每步漲 0.5%)，已具備對數步距特性。絕對價格差隨價格自動縮放，無需額外邏輯。

### DEC-14: 掃描「完全符合」的判定條件

## 10. 效能與快取策略

### DEC-28: 股價歷史快取失效策略 (補充 DEC-06/D6)

**背景**: D6 決定「記憶體 Map + 5 分鐘 TTL + mtime 版本檢查」

| 選項 | 說明 |
| ---------------------------------- | ------------------------------------------------- | --- | ----------------------------------------------------- |
| **A: TTL + mtime 雙重檢查** (推薦) | `if (Date.now() > entry.expires                   |     | fs.stat(path).mtime > entry.mtime) cache.delete(key)` |
| B: 僅 TTL | 簡單但檔案更新 5 分鐘內不生效 |
| C: 檔案監聽 | `fs.watch` 即時失效、但需處理跨平台、進程重啟遺漏 |

**優缺點分析**:

| 選項  | 優點                                                 | 缺點                                             | 風險    |
| ----- | ---------------------------------------------------- | ------------------------------------------------ | ------- |
| **A** | 即時性 (檔案改即生效) + 安全網 (TTL 防 fs.stat 失敗) | 每次讀取額外 `fs.stat` (同步、<1ms)              | ⭐ 低   |
| B     | 無額外 I/O                                           | 盤中資料更正 5 分鐘不生效                        | ⭐⭐ 中 |
| C     | 真正即時                                             | 複雜、Node `fs.watch` 可靠性差、進程重啟丟失監聽 | ⭐⭐ 高 |

**我的推薦**: **A - TTL + mtime 雙重檢查**
**理由**: `fs.stat` 同步極快 (<1ms)，成本可忽略。盤後資料更新常見，mtime 檢查確保模擬器立即見到最新資料。TTL 為備援。

### DEC-29: 掃描器並行化策略

**背景**: §16.10 「可並行化批次模擬」，§16.5 60 次掃描 ~3-6 秒

| 選項                              | 說明                                 |
| --------------------------------- | ------------------------------------ |
| **A: 串行 (現狀)** (推薦)         | 簡單、可預測、無併發問題、3 秒可接受 |
| B: 分批並行 (Promise.all 批次 10) | 10 平行 × 6 批 = ~600ms 理論值       |
| C: Worker Threads                 | 真正多核、但序列化/反序列化開銷大    |

**優缺點分析**:

| 選項  | 優點                                 | 缺點                                                                         | 風險      |
| ----- | ------------------------------------ | ---------------------------------------------------------------------------- | --------- |
| **A** | 零複雜度、單執行緒無競態、記憶體穩定 | 3-6 秒用戶需等待                                                             | ⭐ 低     |
| B     | 理論 5-10x 加速                      | Node 單執行緒 CPU 密集並行無實質加速、反而增加 event loop 壓力、記憶體峰值高 | ⭐⭐ 中   |
| C     | 真多核                               | 開銷大、序列化 SimulationInput (含大陣列) 慢、調試困難                       | ⭐⭐⭐ 高 |

**我的推薦**: **A - 串行**
**理由**: 指標計算是 CPU 密集純 JS，Node 單執行緒下 `Promise.all` 並無並行效果 (除非釋放 event loop)，反而增加記憶體壓力。3 秒在用戶可接受範圍 (LIFF 內彈窗等待)。若未來需優化，可考慮 WASM 或原生模組，非 JS 並行。

### DEC-31: 融資利率變動對維持率計算的影響

**背景**: 維持率公式含 `totalLoan`，但利率變動影響利息成本，長期模擬需考慮

| 選項                           | 說明                                                            |
| ------------------------------ | --------------------------------------------------------------- |
| **A: 單日模擬忽略利息** (推薦) | 模擬器定位「單日收盤情境」，利息屬多日成本，不納入              |
| B: 估算日利息扣減              | `dailyInterest = totalLoan * annualRate / 365`，從現金/淨值扣除 |
| C: 使用者可輸入利率            | API 參數 `interestRate` 選填                                    |

**優缺點分析**:

| 選項  | 優點                                   | 缺點                                                             | 風險  |
| ----- | -------------------------------------- | ---------------------------------------------------------------- | ----- |
| **A** | 符合「單日情境」定義、簡單、無額外參數 | 長期持倉用戶可能誤以為維持率不含利息成本                         | ⭐ 低 |
| B     | 較真實                                 | 需知當前利率、單日利息極小 (年利 5% → 日息 0.014%)、噪聲大於訊號 | ⭐ 低 |
| C     | 彈性                                   | 參數蔓延、單日模擬不需此精度                                     | ⭐ 低 |

**我的推薦**: **A - 單日模擬忽略利息**
**理由**: 模擬器語意 §3.1「如果最新一根 K 棒以輸入價格收盤，在其他資料維持不變前提下」。利息非「其他資料」，且單日影響微乎其微 (<0.02%)。在 `assumptions` 註明「未含融資利息成本」即可。
