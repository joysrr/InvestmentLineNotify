
| 面向         | 說明                                               |

| 2020 疫情恐慌     | -30%      | -65%            | 2.17x           |

## D2: 指標重算方式 - **A: 完整重算 (13 月 OHLCV + calculateIndicators())**

### ✅ 您的選擇

從 `archiveManager.getStockHistory()` 抓 13 個月 OHLCV，替換最新收盤價，完整跑 `calculateIndicators(history)`

### 🟢 優點

| 面向                    | 說明                                                               |
| ----------------------- | ------------------------------------------------------------------ |
| **數學正確**            | Wilder 平滑 (RSI/KD/MACD/ATR) 具有路徑依賴，增量更新會產生累積誤差 |
| **MA240 Fallback 重評** | 完整重算會自然觸發 MA240 fallback 邏輯 (資料不足時用 MA60/收盤價)  |
| **一致性**              | 模擬結果與實際每日收盤後重算完全一致                               |
| **可審計**              | 相同輸入 → 相同輸出，便於回測驗證                                  |

### 🔴 缺點與風險

| 風險         | 影響                                      | 緩解方案                   |
| ------------ | ----------------------------------------- | -------------------------- |
| **I/O 延遲** | 讀 26 個月份檔案 (0050+00675L × 13月)     | 記憶體快取 (D6 已決定)     |
| **計算時間** | ~50-100ms/次 (含檔案讀取)                 | 可接受，模擬頻率低         |
| **記憶體**   | 13 月 × 2 標的 × ~20 筆/月 ≈ 500 筆 OHLCV | 極小 (< 1MB)               |
| **檔案遺漏** | 某月份檔案不存在會導致 409 錯誤           | dataAdapter 驗證月份完整性 |

### 💡 我的建議

> **堅持 A，這是正確的工程決策**
>
> 1. **快取鍵設計**: `${stockNo}_${monthKey}` → `OHLCV[]`
> 2. **缺月處理**: 連續缺月 > 2 個月 → 409；單月缺失 → 向前填補前月最後收盤價 (標記 fallback)
> 3. **效能基準**: 目標 < 100ms (含快取 hit)，首次 cold start < 300ms

## D3: 掃描步距 - **B: 0.5% 步距 (±15% = 60 步，約 3-6 秒)**

### ✅ 您的選擇

```javascript
const stepPct = 0.005; // 0.5%
const rangePct = 0.15; // ±15%
// 價格序列: currentPrice * (1 - 0.15) 到 currentPrice * (1 + 0.15)，每步 0.5%
```

### 🟢 優點

| 面向         | 說明                                             |
| ------------ | ------------------------------------------------ |
| **平衡點**   | 60 次模擬 × 50ms = 3 秒，用戶可接受              |
| **精度足夠** | 0.5% ≈ 0.9 元 (0050@180)，KD/MACD 交叉通常寬於此 |
| **實作簡單** | 線性等距掃描，無需自適應邏輯                     |

### 🔴 缺點與風險

| 風險               | 影響                                                  | 範例                                             |
| ------------------ | ----------------------------------------------------- | ------------------------------------------------ |
| **錯過窄交叉**     | KD 黃金交叉可能發生在 0.3% 區間內                     | K/D 從 19.8/20.1 → 20.2/19.9，跨越 20 但步距跳過 |
| **策略分數不連續** | 決策鏈有硬門檻 (如分數 60→65 觸發買入)，0.5% 可能踩空 | 價格 179.5→180.4 步距 0.9，中間分數 62 被略過    |
| **非線性區域**     | 維持率臨界點 (130%→140%) 附近敏感度高                 | 0.5% 步距可能導致邊界判斷誤差                    |

### 💡 我的建議

> **採用 B + 自適應細化 (Adaptive Refinement)**
>
> ```javascript
> // Phase 1: 粗掃 0.5% (60 步)
> // Phase 2: 若發現「跨越目標」(prev < target < curr)，在該區間細掃 0.1% (5 步)
> // Phase 3: 回傳最精確的 closestPrice
> ```
>
> - 額外成本: 極低 (多數情況不觸發細掃)
> - 精度提升: 邊界從 0.5% → 0.1%
> - 實作複雜度: 低 (在 scanner.mjs 內部處理)

## D4: 掃描上限 - **B: 200 次上限 (約 10-20 秒)**

### ✅ 您的選擇

```javascript
const maxIterations = 200;
```

### 🟢 優點

| 面向           | 說明                                       |
| -------------- | ------------------------------------------ |
| **安全閥充足** | 正常掃描 60 步，200 是 3.3x 安全係數       |
| **防禦性**     | 防止 bug 導致無限循環 (如 step=0 邏輯錯誤) |
| **未來擴充**   | 若未來擴大範圍至 ±30% (120 步) 仍有餘裕    |

### 🔴 缺點

| 風險         | 說明                                                   |
| ------------ | ------------------------------------------------------ |
| **錯誤掩蓋** | 若 step 計算錯誤導致無限循環，200 次後才失敗，延遲發現 |
| **資源浪費** | 極端情況下佔用 20 秒 Worker 時間                       |

### 💡 我的建議

> **維持 B，但加入「異常偵測」**
>
> ```javascript
> if (iterations > expectedMax * 1.5) {
>   logger.warn(
>     { iterations, expectedMax },
>     "Scanner 迭代異常，可能 step 計算錯誤",
>   );
> }
> ```
>
> 預期最大 = `Math.ceil(rangePct * 2 / stepPct)` = 60，1.5x = 90，遠小於 200。

## D5: RSI 反推演算法 - **A: 二分搜尋 (穩健、50 次內收斂)**

### ✅ 您的選擇

```javascript
// RSI 對價格單調遞增 (價格↑ → RSI↑)，適合二分搜尋
let low = currentPrice * 0.7,
  high = currentPrice * 1.3;
for (let i = 0; i < 50; i++) {
  const mid = (low + high) / 2;
  const rsi = calcRSI(replaceLastClose(history, mid));
  if (Math.abs(rsi - target) < 0.5) return mid;
  rsi < target ? (low = mid) : (high = mid);
}
```

### 🟢 優點

| 面向         | 說明                                              |
| ------------ | ------------------------------------------------- |
| **保證收斂** | RSI 對收盤價單調 (Wilder 平滑保持單調性)          |
| **實作簡單** | 無需導函數、無發散風險                            |
| **可控精度** | 50 次迭代 → 精度 (0.3/2^50) ≈ 0，實際 10 次內收斂 |

### 🔴 缺點

| 風險         | 影響                                      | 緩解                                  |
| ------------ | ----------------------------------------- | ------------------------------------- |
| **效能**     | 每次迭代需重算 RSI (含 14 期平滑)         | 50 × 0.1ms = 5ms，可忽略              |
| **邊界假設** | ±30% 搜尋範圍可能不夠 (極端目標 RSI=5/95) | 動態擴展邊界：若未收斂 → 擴大 2x 重試 |

### 💡 我的建議

> **採用 A + 動態邊界擴展**
>
> ```javascript
> // 初始 ±30%
> let range = 0.3;
> for (let attempt = 0; attempt < 3; attempt++) {
>   const result = binarySearch(low, high);
>   if (result) return result;
>   // 未找到 → 擴大範圍
>   range *= 2;
>   low = currentPrice * (1 - range);
>   high = currentPrice * (1 + range);
> }
> return null; // 真正不可達
> ```

## D6: 歷史資料快取 - **B: 記憶體 Map + 5 分鐘 TTL**

### ✅ 您的選擇

```javascript
const historyCache = new Map(); // key: "0050_202607" → OHLCV[]
const CACHE_TTL = 5 * 60 * 1000;
```

### 🟢 優點

| 面向           | 說明                                   |
| -------------- | -------------------------------------- |
| **熱資源優化** | 模擬器高頻讀取同個月份歷史，命中率極高 |
| **自動淘汰**   | 5 分鐘 TTL 避免記憶體洩漏、資料過期    |
| **簡單可靠**   | 無外部依賴 (Redis 等)，單機部署友善    |

### 🔴 缺點與風險

| 風險                 | 影響                                     | 緩解                   |
| -------------------- | ---------------------------------------- | ---------------------- |
| **多實例不一致**     | 若擴展為多 Pod，各自獨立快取             | 目前單機部署，無此問題 |
| **冷啟動慢**         | 重啟後首次請求需讀檔                     | 可接受 (< 300ms)       |
| **TTL 內資料不更新** | 日盤中資料更新 (如更正價) 5 分鐘內不生效 | 盤後跑模擬為主，影響小 |

### 💡 我的建議

> **採用 B + 版本號機制**
>
> ```javascript
> // 快取值包含版本號
> cache.set(key, {
>   data: ohlcv,
>   version: fileMtime,
>   expires: Date.now() + TTL,
> });
>
> // 讀取時檢查檔案 mtime 是否變更
> if (stat.mtime > cached.version) cache.delete(key); // 強制刷新
> ```
>
> 這樣「檔案更新」即時生效，不需等 TTL 過期。

延用 `initDataGuard` middleware，要求 `X-Telegram-Init-Data` header

### 🟢 優點

| 面向         | 說明                                   |
| ------------ | -------------------------------------- |
| **零成本**   | 復用現有中介軟體、錯誤處理、Rate Limit |
| **安全一致** | 同等級防護，無新攻擊面                 |
| **用戶體驗** | LIFF/Telegram 內無感驗證               |

### 🔴 缺點與風險

| 風險                       | 影響                                         | 緩解                                             |
| -------------------------- | -------------------------------------------- | ------------------------------------------------ |
| **開發/測試不便**          | 本機 curl、Postman、單元測試需 mock initData | **dev bypass**: `NODE_ENV=dev` 時允許無 initData |
| **非 Telegram 環境無法用** | 未來若要網頁版/獨立 App 需重構               | Phase 2 再擴充 JWT/API Key                       |
| **initData 過期**          | 24 小時後失效，長對話需重新授權              | 前端自動處理刷新                                 |

### 💡 我的建議

> **採用 A + 開發模式繞過**
>
> ```javascript
> // initDataGuard.mjs
> if (process.env.NODE_ENV === "dev" && !initData) {
>   return; // 開發環境允許無 initData (方便 curl 測試)
> }
> ```
>
> **單元測試**: mock `window.Telegram.WebApp.initData = 'test-data'`

## D8: 回應時間戳 - **C: 兩者皆含 (dataAsOf + timestamp)**

### ✅ 您的選擇

```json
{
  "dataAsOf": "2026-08-01", // 資料基準日 (最新戰報日期)
  "timestamp": "2026-08-02T10:30:00.000Z" // 計算完成時間
}
```

### 🟢 優點

| 面向             | 說明                              |
| ---------------- | --------------------------------- |
| **完整審計軌跡** | 知道「基於何時資料」+「何時計算」 |
| **除錯關鍵**     | 回測驗證時可對齊時點              |
| **用戶信任**     | 透明化資料新舊程度                |

### 🔴 缺點

| 風險 | 影響 |
| ---------------- | ---------------------------------------------- | ---------------- |
| **回應體積微增** | 約 +50 bytes，可忽略 |
| **時區混淆** | dataAsOf 為日期字串，timestamp 為 ISO 8601 UTC | 需文件化格式規範 |

### 💡 我的建議

> **採用 C + 格式標準化**
>
> - `dataAsOf`: `YYYY-MM-DD` (Asia/Taipei 交易日)
> - `timestamp`: ISO 8601 UTC (`YYYY-MM-DDTHH:mm:ss.sssZ`)
> - 文件化於 API 契約 (§16.7)
