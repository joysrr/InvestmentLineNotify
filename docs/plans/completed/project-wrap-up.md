## 五、後續維護的最小流程

### 每次改動前

```bash
npm --prefix webapp run lint
npm --prefix webapp run test
```

### 改動完成後（commit 前）

```bash
npm --prefix webapp run lint
npm --prefix webapp run test
npm --prefix webapp run build && node webapp/scripts/check-bundle-size.mjs
npx playwright test webapp/src/test/e2e/ --grep "360"
```

四項全綠才 commit。這是唯一的品質防線，不因「改動很小」而跳過。

### 部署前（Oracle VM）

```bash
npm run pre-deploy
```

### 不需要做的事

- 不需要為「未來可能的第二個使用者」準備任何東西
- 不需要追求 Lighthouse 分數、a11y 合規、跨瀏覽器相容
- 不需要為「可能永遠不會發生的場景」寫防禦性程式碼

## 六、遇到問題時的針對性修復原則

判斷流程

1. 有具體症狀嗎？（例如「某頁在深色主題下白底」）
   - 無 → 不修
   - 有 → 進入第 2 步
2. 症狀在你的使用場景中會發生嗎？（單一裝置、淺色、360px）
   - 不會 → 不修
   - 會 → 進入第 3 步
3. 修復成本 < 症狀影響 × 發生頻率嗎？
   - 是 → 修
   - 否 → 記錄為已知限制，不修

常見症狀與對應處理

| 症狀                               | 處理                                       |
| ---------------------------------- | ------------------------------------------ |
| 某頁在 360px 下橫向滾動            | 優先修（會影響日常使用）                   |
| 某個按鈕在特定機型被瀏海遮擋       | 修（加 safe-area padding）                 |
| 深色主題下某頁白底                 | 若不切深色主題 → 不修；若切 → 修該頁的令牌 |
| 某個元件在桌面版 Telegram 排版錯亂 | 不在桌面用 → 不修                          |
| 螢幕閱讀器無法讀取某區塊           | 不用螢幕閱讀器 → 不修                      |

## 八、專案的「完成」定義

本專案在以下條件下視為完成：

☑ 5 個一級入口可用（總覽 / 洞察 / 圖表 / 新聞 / 設定與帳戶）
☑ 核心決策鏈（新聞 → AI 分析 → 建議 → Telegram 通知）運作正常

☑ 360px 下無橫向滾動
☑ Bundle 在預算內
☑ 7 份 design 文件記錄了當前的設計決策

不在「完成」定義內的：

- 跨裝置相容（單一裝置）
- 無障礙合規（純自用）
- 深色模式完整覆蓋（淺色為主）
- 多使用者支援（純自用）
- 使用資料分析（無第二使用者）

## 九、為什麼停在這裡

這不是「沒做完」，是「做完了該做的，停在了正確的地方」。

階段一至五解決了：結構正確（5 個入口）、內容去重、逐頁精修、測試從 649 增至 710、Initial 從 155.4 KB 降至 104.2 KB。這些是「讓系統好用」的必要工作。

階段六、七解決的是：跨裝置、無障礙、多使用者、資料回饋。這些是「讓系統給更多人用」的工作，對單人自用是過度工程。

停在這裡，是為了讓系統保持簡單、可維護、不被「為未來準備」的複雜度拖垮。
